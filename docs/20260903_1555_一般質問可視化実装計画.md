## 0. 結論

一般質問は、まず「誰が多く質問したか」ではなく、**沼津市議会で、いつ、どのような
行政課題が取り上げられ、どの部局・役職が答弁したか**を会期横断で探せる形にする。

初期公開は、2004年6月以降の「本会議の報告」に付属する一般質問PDFを基幹資料とし、
現任期のうち公式資料が公開済みの会期を100%人手照合してから過去へ広げる。
1990年以降の会議記録は、本文の再掲載を
避け、公式記録へのリンク、開催事実、登壇枠、答弁者役職、運営者が定義した政策分野の
検証に使う。

次の表示は実装しない。

- 一般質問の件数、登壇回数、発言量による市議会議員ランキング
- 「質問が多いほどよく活動している」などの評価・スコア
- 発言時間、文字数、動画時間による個人比較
- 市議会議員別に発言本文を集積したアーカイブ

## 1. 目的

### 1.1 市民に提供する価値

- 今回の定例会・臨時会で扱われた一般質問のテーマを短時間で把握できる。
- 防災、子育て・教育、医療・福祉、産業・観光など、関心分野から過去の議論を探せる。
- 同じ政策分野がどの会期で繰り返し取り上げられたかを追える。
- 要約や分類だけで判断せず、元のPDF、会議記録、映像へ移動できる。
- どの期間・資料が取り込み済みか、欠けているかを判断できる。

### 1.2 運営側の目的

- PDF、会議記録、映像メタデータを、出典を失わずに共通の会議単位へ正規化する。
- 資料公開の遅れ、資料形式の変更、氏名表記の揺れを人手QAで安全に扱う。
- 将来、請願、パブリックコメント、市民意識調査、予算のテーマと接続できる政策分野
  マスタを整備する。

## 2. 利用者が答えを得たい問い

| 利用者の問い | 表示するもの | 表示しない・断定しないもの |
| :-- | :-- | :-- |
| 今の会期では何が問われたか | 登壇日、質問順、公式資料の項目、政策分野、答弁者役職 | 質問の優劣、市議会議員の採点 |
| 最近増えた市政課題は何か | 会期・年度別の政策分野構成、初出・継続テーマ | 件数増加を市民需要の増加とみなす因果推論 |
| 同じ登壇枠にどの分野と答弁者役職が掲載されたか | 登壇枠単位の政策分野×答弁者役職の共起 | 個別項目への答弁帰属、答弁の十分性、部局の成果評価 |
| 原文や映像を確認したい | 公式PDF、会議記録、議会中継へのリンク | 発言全文・映像の複製掲載 |
| 数字はどこまで揃っているか | 対象期間、取得日時、資料別カバレッジ、未取得表示 | 欠損を0件として補完したグラフ |

## 3. 対象・対象外と数え方

### 3.1 対象

- 本会議の一般質問
- 2月定例会等の代表質問と個人質問。区分は公式資料に従い、混ぜずに保持する。
- 登壇日、質問順、市議会議員名、議席番号、質問方式、質問項目、答弁者役職
- 会期、会議日、公式資料URL、取得日時
- 人手確認した政策分野、短い独自要約、分類根拠
- 一般質問が実施されなかったことを公式資料が明示している会期

### 3.2 対象外

- 議案質疑、委員会質疑、討論、動議を一般質問として数えること
- 発言全文、映像、議会だより紙面の転載
- 質問の「成果」「鋭さ」「市政への影響」の自動判定
- 市議会議員の住所、電話番号その他、本可視化に不要な個人情報
- 会派・党派を用いた質問内容の自動評価

### 3.3 指標の定義

「一般質問数」は資料ごとに粒度が違い曖昧なため、画面とデータ項目では次の語を使う。

| 指標 | 定義 | 解釈上の注意 |
| :-- | :-- | :-- |
| 一般質問実施日数 | published・verifiedで`status=held`・`held_on`ありの本会議について、QA済み一般質問実施を確認した異なる日数 | 会議時間や質問内容の量ではない |
| 登壇枠数 | 公式資料の質問順1枠を1とする | 項目数・発言回数とは異なる。個人ランキングには使わない |
| 質問項目数 | 公式PDFの最上位項目を数える | 書き方の細かさが会期・登壇者で異なるため、量の比較には使わない |
| 政策分野構成 | QA済み登壇枠または項目に付いた政策分野の構成 | 複数分野を許し、合計が100%にならない表示では明記する |
| 答弁者役職数 | 公式PDFに列挙された異なる役職数 | 答弁の回数、内容、十分性ではない |

### 4.2 取得・更新方針

- 索引は毎週1回、開会中は現在の会議のお知らせを毎日1回まで確認する。
- 会期終了後6か月は、一般質問PDFと会議記録の公開を毎週確認する。
- 6か月を過ぎた資料は月1回、URL・ETag・Last-Modified・内容ハッシュを確認する。
- 取得間隔は既存クライアントと同様に1秒以上とし、識別可能なUser-Agentを送る。
- 同じ取得版で、パーサー名・版・設定も同じ完了済み解析がある場合だけ再解析しない。
  取得内容または解析条件の変更時は、既存のQA済み値を無条件で上書きせず、
  差分をレビュー待ちにする。

### 5.1 再利用できるもの

| 現行実装 | 適合点 |

| `council_sessions` | 会期、開催期間、定例会・臨時会、公式URLを一般質問の親にできる |
| `council_members` | 氏名、議席番号、外部発言者IDとの任意の突合先にできる。突合不能時はnullを許す |
| `ingestion_runs` / `ingestion_sources` | 実行履歴、URL、内容ハッシュ、最終取得日時を再利用できる |

| `DiscussVisionClient` | 2022年以降の会議・発言メタデータ取得を補助に使える |
| Featureベース構成 | `web/src/features/general-questions/{server,client,shared}`として分離できる |
| `web/src/lib/routes.ts`と同期テスト | 新規ページのルート漏れを防げる |

### 5.2 解消が必要なギャップ

- 会議日単位の共通テーブルがなく、会期の中の「第何日」を保持できない。
- 一般質問PDFを探索・解析するfetcher/parser/serviceがない。
- 登壇枠、質問方式、質問項目、答弁者を保持するテーブルがない。
- `council_members`は現況中心で、改姓、字体、同姓同名、任期途中の交代を扱うalias・
  在任期間のモデルが不足している。
- AmiVoiceの既存パーサは議案説明・討論・委員会審査向けで、一般質問の区間認識や
  代表質問・個人質問の判定をしない。
- 公開前QA、分類バージョン、訂正履歴を表す仕組みがない。
- 公開画面・ローダー・Repository・Open Data API・サイトマップ・ナビゲーションがない。
- Webアプリに専用グラフライブラリはない。初期版はHTML/CSSと表を優先し、依存追加は
  アクセシビリティ、bundle size、Server Component適合を比較して別判断とする。

## 6. データモデル案

### 6.1 両可視化で共用する `council_meetings`

一般質問と委員会を別々の「日付文字列」で持たず、会議日単位を共通化する。
`council_meetings`自体は出典や訂正で変わらない安定した会議IDだけを表す。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | uuid | 主キー |
| `canonical_meeting_key` | text | QAで同一会議と確定した後も変えない内部安定キー |
| `created_at` | timestamptz | 正本作成日時 |

日付や表題だけから`canonical_meeting_key`を生成せず、ソース内出現の突合結果から同一会議を
確定する。`canonical_meeting_key`はNOT NULLかつUNIQUEとし、候補作成時もランダムな内部キーを
払い出して後から日付由来キーへ付け替えない。正規化した属性と公開版選択は追記型の
`council_meeting_revisions`へ置く。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `meeting_id` | uuid | revisionの主キーと安定会議ID |
| `revision_number` | integer | 会議内の追記番号。1以上 |
| `council_session_id` | uuid nullable | 定例会・臨時会。閉会中等で特定不能ならnull |
| `committee_id` | uuid nullable | 委員会会議のみ。一般質問を含む本会議ではnull |
| `kind` | enum | `plenary` / `committee` / `steering` / `all_members` / `other` |
| `scheduled_on` | date nullable | 公式日程上の予定日。予定資料が無ければnull |
| `held_on` | date nullable | 実開催を確認した日。予定段階ではnull |
| `day_number` | integer nullable | 本会議の第何日。資料に無い場合はnull |
| `scheduled_starts_at` | timestamptz nullable | 日程資料の予定開始日時 |
| `opened_at` / `closed_at` | timestamptz nullable | 公式記録にある場合のみ |
| `venue` | text nullable | 公式資料上の場所 |
| `display_title` | text | 複数資料を照合してQAした表示名。原表記は根拠側へ置く |
| `status` | enum | `scheduled` / `held` / `cancelled` / `unknown` |
| `source_support_status` | enum | `official_supported` / `empirical_verified` / `partial` / `unknown` |
| `qa_status` | enum | `pending` / `verified` / `rejected` |
| `publication_state` | enum | `draft` / `reviewed` / `published` / `superseded` |
| `verified_by` / `verified_at` | uuid / timestamptz nullable | 人手確認の監査情報 |

`(meeting_id, revision_number)`と`(id, meeting_id)`を一意にし、会議ごとにpublished revisionを
一つだけ許す。訂正時は旧publishedを残して新revisionをdraftで確認し、承認時に旧行を
`superseded`、新行を`published`へ同一トランザクションで切り替える。共通のQA・公開状態
CHECKを適用し、公開viewはpublished revisionだけを返す。

0Bは状態と日時にもCHECKを設ける。`status=held`は`held_on`を必須とし、非held状態では
`held_on / opened_at / closed_at`を禁止する。`scheduled / cancelled`は`scheduled_on`を
必須とする。`closed_at`がある場合は`opened_at`も必須で、`closed_at >= opened_at`とする。
published revisionの状態、実開催日、開閉時刻は、同じ会議のverified根拠に同じ観測値が
あることを`council_meeting_publication_guard`で要求する。根拠の削除・却下・値の差し替えでも
再検査する。一般質問実施日数はpublished・verified・held・`held_on is not null`の会議に、
同じ日のQA済み一般質問実施を結べた場合だけ集計する。
さらに`kind in ('committee', 'steering')`の場合だけ`committee_id`を必須とし、
`plenary / all_members / other`ではnullを要求する。`kind=steering`はsteering委員会、
`kind=committee`はstandingまたはspecial委員会を参照することを0Bの遅延guardで保証する。

同じ会議にPDF、会議記録、映像の複数資料があるため、共通基盤0Bでは次を分ける。

- `council_meeting_source_occurrences`: `meeting_id`、`ingestion_source_id`、
  `source_occurrence_key`、`source_system`、`external_id`を持つ。論理資料内では
  `(ingestion_source_id, source_occurrence_key)`を一意にし、AmiVoiceの`vcsv`等は
  `(source_system, external_id)`の部分一意制約で版やURLをまたいで同じ会議へ結ぶ。
- `council_meeting_source_evidence`: 対象`revision_id`、出現ID、`source_version_id`、
  `parse_run_id`、`role`、`meeting_id`、`ingestion_source_id`、`source_evidence_key`、
  `evidence_revision`、`locator`、
  `availability`、`qa_status`、`extraction_method`、`verified_by`、
  `verified_at`を持つ。さらに`observed_title`、
  `observed_scheduled_on`、`observed_held_on`、`observed_day_number`、
  `observed_starts_at`、`observed_opened_at`、`observed_closed_at`、`observed_venue`、
  `observed_status`等、取得版に記載された値を上書きせず追記する。

両テーブルは`id`を主キーにする。出現の`meeting_id`は`council_meetings.id`、
`ingestion_source_id`は`ingestion_sources.id`へ、根拠の出現IDは
`council_meeting_source_occurrences.id`、`source_version_id`は
`ingestion_source_versions.id`、`parse_run_id`は`ingestion_parse_runs.id`へ外部キーを張る。
出典と解析の監査先は`ON DELETE RESTRICT`とする。会議revisionにも
`(id, meeting_id)`を一意にし、根拠から`(revision_id, meeting_id)`へ複合外部キーを張る。
根拠行の出典側一意制約は対象revisionを含めず、
`(meeting_source_occurrence_id, source_version_id, parse_run_id, source_evidence_key,
evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。parser根拠の`evidence_revision`は1に
固定し、同じ物理根拠を別parse runで再解釈できるようにする。人手再確認は同じ
`source_evidence_key`の`evidence_revision`を増やして追記する。同じ一つの観測行を二つの
revisionへ結べない。パーサー由来の行は`parse_run_id`を必須にする。
取込みはソース出現を先にupsertし、その行が指す同じ`meeting_id`を再利用する。
`extraction_method=parser`なら`parse_run_id`を必須、`manual`ならnullとするCHECK制約を
会議根拠と登壇枠根拠へ設ける。manual根拠をverifiedとして扱う場合は
`source_version_id`、空でない`locator`、`verified_by`、`verified_at`をすべて
必須にする。

共通基盤0Aでは`ingestion_source_versions(id, ingestion_source_id)`、0Bでは
`council_meeting_source_occurrences(id, meeting_id, ingestion_source_id)`も一意にする。
会議根拠からこれら二組へ複合外部キーを張り、別会議の出現や別論理ソースの取得版を
誤って結べないようにする。

取得版と解析実行を両方持つ会議根拠、登壇枠根拠、会期カバレッジ根拠はすべて、
個別の外部キーに加えて`(parse_run_id, source_version_id)`から
共通`ingestion_parse_runs(id, source_version_id)`への複合外部キーを持つ。これにより、
別取得版の解析実行を結ぶ誤りをDBで拒否する。パーサー由来では両列を必須とし、
人手登録の根拠だけ`parse_run_id`をnull可とする。両列がnullableなcoverage根拠等には
`CHECK (parse_run_id is null or source_version_id is not null)`も設け、PostgreSQLの
`MATCH SIMPLE`で解析実行だけが指定された不正行を見逃さない。

`council_meetings`に単一の出典、正規化属性、公開状態、外部システムを持たせない。日付や
会議名だけで会議を自動統合せず、安定外部IDがない資料は候補をQAする。published revisionは
少なくとも一つのverified根拠を必須とする。本表、revision、二つの出典テーブルは委員会計画と
同じ論理モデルであり、テーマ別PRではなく共通基盤0Bで一度だけ追加する。
0B自身が`common:council_meeting_revision` consumer type、会議根拠と
active reference registryの同期trigger、registry完全一致を含む
`council_meeting_publication_guard`を所有する。一般質問・委員会のconsumer typeは
共通会議根拠を重ねて登録しない。

### 6.2 `general_question_appearances`

安定正本の1行を「1人の1登壇枠」とする。発言回数や項目数ではない。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | uuid | 主キー |
| `meeting_id` | uuid | `council_meetings.id` |
| `appearance_key` | text | 会議内で版をまたいで安定する決定的キー |
| `created_at` | timestamptz | 正本作成日時 |

登壇者の突合結果や表示属性は`general_question_appearance_revisions`へ追記する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `appearance_id` / `meeting_id` | uuid | revision、安定登壇枠、同一会議を保証するキー |
| `revision_number` | integer | 登壇枠内の追記番号。1以上 |
| `council_member_id` | uuid nullable | 確実に突合できた場合のみ |
| `speaker_display_name` | text | 複数資料を照合した表示名。原表記は根拠側へ置く |
| `seat_number` | integer nullable | 確認済みの場合のみ |
| `question_order` | integer nullable | 資料で確認できる場合のその日の質問順 |
| `question_kind` | enum | `representative` / `personal` / `other` / `unknown` |
| `delivery_method` | enum | `all_at_once` / `one_by_one` / `combined` / `other` / `unknown` |
| `qa_status` | enum | `pending` / `verified` / `rejected` |
| `publication_state` | enum | `draft` / `reviewed` / `published` / `superseded` |
| `reviewed_by` / `reviewed_at` | uuid / timestamptz nullable | revisionの内容を承認した人と時刻 |
| `published_at` | timestamptz nullable | 公開日時 |

正本の一意制約は`(meeting_id, appearance_key)`とし、`(id, meeting_id)`も一意にする。
revisionは`(appearance_id, revision_number)`と`(id, appearance_id, meeting_id)`を一意にし、
登壇枠ごとにpublished revisionを一つだけ許す。published revisionの`question_order`が非nullの
場合だけ`(meeting_id, question_order)`を一意にし、順番が資料にないときは番号を作らない。
ソース内の同じ登壇枠が再解析ごとに別の正本へ移らないよう、まず
`general_question_appearance_source_occurrences(id, appearance_id, meeting_id,
meeting_source_occurrence_id, ingestion_source_id, source_appearance_key, created_at)`を置く。
`(meeting_source_occurrence_id, source_appearance_key)`と
`(id, appearance_id)`、`(id, appearance_id, meeting_id, ingestion_source_id)`を一意にし、
正本登壇枠と会議ソース内出現の双方へ複合外部キーを張る。候補はstagingでQAし、
確定前にこの対応表へ入れない。

版・解析・revisionごとの根拠は`general_question_appearance_sources(id,
appearance_source_occurrence_id, appearance_revision_id, appearance_id,
meeting_id, ingestion_source_id, source_version_id, parse_run_id, source_locator, role, extraction_method,
observed_speaker_name, observed_seat_number, observed_question_order,
observed_question_kind, observed_delivery_method, evidence_revision, qa_status,
verified_by, verified_at)`へ追記する。
正本登壇枠、会議のソース内出現、取得版が同じ会議・論理ソースに属することを、
revisionを含むそれぞれの複合外部キーでDB保証する。解析実行ごとの根拠を失わないよう、
`general_question_appearance_sources`には
`(id, appearance_source_occurrence_id, appearance_id)`の複合一意制約も置く。
`(appearance_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision)`は`NULLS NOT DISTINCT`で一意にし、対象`appearance_id`は含めない。
parser根拠の`evidence_revision`は1に固定し、人手再確認では同じ物理キーのrevisionを増やす。
同じ一つの出典観測を二つの正本へ結べない一方、別会議では同じローカルキーを利用できる。
パーサー由来は`parse_run_id`必須、人手登録だけnullを許可する。published登壇revisionには
verifiedな根拠を一つ以上必須にする。訂正時は同じ正本の
新revisionと新しい根拠をdraftで追加し、旧publishedを上書きせずに版を切り替える。
登壇revisionには根拠行の確認者とは別に`reviewed_by / reviewed_at`を持たせる。
2列の片方だけを禁止し、`qa_status=verified`の場合と非draftへ進む場合は両方を
必須にする。非draftは`qa_status=verified`に限定し、公開後の確認者解除や
内容更新を拒否する。

`official_label_hash`は再取得時の変更検知用であり、原文の復元を目的としない。内部QAで
短期保持する抽出テキストの保存期間とアクセス権は、公開実装前に法務レビューで決める。
`topic_classification_runs`はrunning・`finished_at=null`で追加し、一度だけterminalへ進める。
`status=completed`だけを公開分類に利用し、taxonomy・method・model・prompt・開始日時と
terminal行を通常UPDATEできないようにする。
taxonomyは`qa_status=verified`の場合と非draftで`reviewed_by / reviewed_at`を両方必須にし、
reviewedへ進む時にtaxonomyと`policy_topics`の全列・順序付き行集合から
`content_hash`をDB計算して凍結する。publishedはverified・確認情報・hash再計算一致と
`published_at`を必須にし、一度だけ設定する。reviewed以降のtopic INSERT / UPDATE /
DELETE、確認取消、draft巻き戻し、`published_at`の巻き戻し・変更を拒否する。
名称・説明・有効状態を変える場合は新しいtaxonomy version、topic ID、分類runを追加し、
過去の分類結果の意味を遡及変更しない。
安定正本は`(appearance_id, item_key)`と`(appearance_id, answerer_key)`をそれぞれ一意にする。
項目・答弁者のrevisionは各正本内で`revision_number`を一意にし、正本ごとのpublished
revisionを一つだけ許す。項目の順序はpublished revisionだけを対象に
`item_order IS NOT NULL`を条件として`(appearance_id, parent_item_id, item_order)`を
`NULLS NOT DISTINCT`で一意にする。トップ階層の`parent_item_id=null`だけを同じ親として扱い、
順番不明の兄弟項目は複数公開できる。旧publishedと同じ順序の新draftも並行してQAできる。
親項目は同じ登壇枠に限定する複合外部キーを張り、
`parent_item_id IS NULL OR parent_item_id <> question_item_id`のCHECKで自己参照を拒否する。
公開切替トランザクションのコミット時に、その時点のpublished revisionだけで作る階層を
再帰的に検査し、循環がなく、非nullの親には同じ登壇枠のpublished revisionがあることを
DEFERRABLE INITIALLY DEFERREDなconstraint triggerで保証する。draftのプレビューも同じ
検証関数をserviceから呼び、親子の公開版を同一トランザクションで切り替えられるようにする。
階層の`level`は保存せず、repositoryが取得したrevision集合の親チェーンから
共有の純粋関数で導出する。
答弁者のpublished `display_order`も、非nullの場合だけ同じ登壇枠内で一意にする。
`role_group`はPhase 0で定義を固定する限定enumとし、少なくとも`mayor / deputy_mayor /
superintendent / department_head / division_head / administration_other / unknown`を持つ。
原表記と表示名は`role_display_name`と根拠側に残し、「市長」と「沼津市長」のような
同義表記は人手確認後に同じ`role_group`へ対応させる。`unknown`は役職別集計から
除外し、表示名の訂正で過去集計の分類軸を遱及変更しない。

項目・答弁者の正本にはそれぞれ`(id, appearance_id)`を、revisionにはそれぞれ
`(id, question_item_id, appearance_id)`と`(id, answerer_id, appearance_id)`を
複合一意制約として置く。根拠行からrevisionへこれらの複合外部キーを張り、同じ登壇枠の
組だけを許す。source occurrenceはそれぞれ
`(appearance_source_occurrence_id, source_item_key)`、
`(appearance_source_occurrence_id, source_answerer_key)`を対象IDなしで一意にする。
これにより、別parse runでも同じソース内項目・答弁者を複数の安定正本へ結べない。
さらに項目側は
`(id, question_item_id, appearance_id, appearance_source_occurrence_id)`、答弁者側は
`(id, answerer_id, appearance_id, appearance_source_occurrence_id)`を複合一意にする。
各source occurrenceから、対象正本の`(id, appearance_id)`と登壇枠source occurrenceの
`(id, appearance_id)`へ複合外部キーを張る。

版別根拠には`appearance_source_occurrence_id`を冗長保持し、項目側は
`(item_source_occurrence_id, question_item_id, appearance_id,
appearance_source_occurrence_id)`から、答弁者側は
`(answerer_source_occurrence_id, answerer_id, appearance_id,
appearance_source_occurrence_id)`から、それぞれのsource occurrenceへ複合外部キーを張る。
また両者とも
`(appearance_source_id, appearance_source_occurrence_id, appearance_id)`から
登壇枠の版別根拠へ複合外部キーを張る。これにより、項目・答弁者のソース内出現と版別根拠が
異なる登壇枠source occurrenceを参照する組み合わせをDBで拒否する。
版別根拠は`(item_source_occurrence_id, appearance_source_id, evidence_revision)`または
`(answerer_source_occurrence_id, appearance_source_id, evidence_revision)`を一意にし、
parser根拠はrevision 1、人手再解釈は番号を増やす。取得版と解析実行は
`appearance_source_id`から一意に導き、published revisionにはverified根拠を必須にする。
訂正時は同じ正本の新revisionと根拠をdraftで追加し、旧publishedを上書きせず
`superseded / published`を切り替える。
登壇・項目・答弁者の全revisionは根拠側とは別の`reviewed_by / reviewed_at`を持つ。
各表で「2列は両方nullか両方non-null」、「`qa_status=verified`なら両方non-null」、
「非draftなら`qa_status=verified`かつ両方non-null」をCHECKする。公開後の確認情報の
解除と内容更新を禁止し、訂正は確認情報付きの新revisionへ原子的に切り替える。

分類結果セットは`(question_item_revision_id, classification_run_id)`を一意にし、
`(question_item_revision_id, taxonomy_id) WHERE publication_state='published'`の部分一意制約を
設ける。taxonomyが違えばv1を現行公開したままv2の公開セットも準備できるが、
公開viewはconsumerのactive releaseが選んだセットだけを返す。同taxonomy内の再分類では
旧セット全体を`superseded`、新セットを`published`へ同一トランザクションで
切り替える。AI・ルール分類はセットの`qa_status=verified`まで公開しない。
`general_question_item_topics`は親セットが`draft`かつ参照runが`running`の間だけ
INSERT / UPDATE / DELETEを許し、runがterminal化した後はdraftセットでもtopic行集合と
全列を不変にする。classification setの新規INSERTと対象項目・run・taxonomyの変更も
参照runがrunningの間だけ許し、terminal後はQA・publication・reviewerの状態遷移だけを許す。
分類内容を訂正するときは既存セットを編集せず、新しいrun・セット・topic行を追加して公開版を
切り替える。

分類セットは`(id, taxonomy_id)`を一意にしたうえで、
`(classification_run_id, taxonomy_id)`から分類runへ、分類結果行は
`(classification_set_id, taxonomy_id)`と`(policy_topic_id, taxonomy_id)`からそれぞれ
セットと分野へ複合外部キーを張る。別taxonomy版の分野を同じ分類セットへ混在させる誤りを
DBで拒否する。

項目ごとのpublishedセットだけを直接公開すると、再分類中に項目Aはtaxonomy v1、項目Bはv2と
なり得る。そのため公開view / APIは分類セットを直接列挙せず、
`consumer_type=general_question_item`でpublishedの`topic_classification_releases`一行から
release itemを経由して読む。releaseは`UNIQUE (consumer_type, release_key)`と
`UNIQUE (consumer_type) WHERE publication_state='published'`を持ち、レスポンスへ
`classificationReleaseId`、`taxonomyId`、taxonomy `version`、snapshotの型付き範囲・
cutoff・DB計算件数を返す。

`topic_classification_population_snapshots`の範囲は`council_session / date_range /
fiscal_year`のどれかとし、CHECKで対応するIDまたは期間だけを必須にする。
`create_topic_classification_population_snapshot`は固定`search_path`の専用関数とし、
呼び出し側の任意cutoffを受け付けず`transaction_timestamp()`を`cutoff_at`に記録する。
`selection_rule_version`と型付き範囲により、そのトランザクションでpublished・verifiedかつ
親会議がpublished・verified・held・`held_on is not null`の一般質問項目を一括列挙する。
関数自身がmemberの`ordinal`、`subject_count`、順序付きID hashを計算し、
呼び出し側から件数・hash・memberを挿入させない。snapshotとmemberは生成完了後の
UPDATE / DELETE / TRUNCATEを不変性triggerと権限で拒否する。cutoff後の新規項目は旧snapshotに
追加せず、新しいsnapshotを作る。
予定中の登壇枠を示す場合は別のplanned consumer・releaseに分け、実績の政策構成や
共起集計と合算しない。scheduledからheldへ変わった対象は新snapshotで取り込む。

release itemは`(release_id, question_item_revision_id)`を一意にし、
`(population_snapshot_id, question_item_revision_id)`からsnapshot memberへ複合外部キーを張る。
`coverage_disposition=classified`なら同じtaxonomyのcompleted runから作られた
verified分類セット、`not_applicable / excluded`ならセットなしと空でない理由・
確認者・確認日時を要求する。draft / reviewed releaseのclassified itemは
`reviewed / published`セットを参照でき、releaseをpublishedにする時はすべてを
publishedに限定する。published guardはtaxonomyが公開済み、対象項目revisionと
その親appearance revisionがpublished・verified、全itemがclassifiedまたは確認済み除外で
あることに加え、snapshot memberとrelease itemの双方向`EXCEPT`がどちら0件であることを
遅延検査する。自由入力の定義や自己申告件数は公開ゲートに使わない。

releaseのconsumer・key・taxonomy・snapshotとitem集合は親releaseがdraftの間だけ編集を
許す。`draft -> reviewed -> published -> superseded`または
`reviewed -> superseded`だけを許し、reviewed以降の内容更新、draftへの巻き戻し、
物理DELETE / TRUNCATEを拒否する。訂正は新しいsnapshot・release・itemで行い、
旧active releaseのsuperseded化と新releaseのpublished化を同一トランザクションで行う。

一般質問と委員会は更新速度が異なるためactive releaseはconsumer別に持つ。テーマ横断画面は
両consumerのactive `taxonomy_id`が同じ場合だけ分類別に合算し、異なる場合はテーマ別に版を
明示して分離表示する。異なるtaxonomy版を同じ系列へ黙って合算しない。

### 6.4 0・null・該当なし

- `null`: 資料未公開、未取得、解析失敗、資料から判断不能。
- `0`: 対象資料を取得し、対象範囲を確認した結果、本当に0件。
- `not_applicable`: その会期に一般質問という区分が適用されない。
- `not_held`: 公式資料が一般質問を行わなかったと明示している。

会期に登壇行が一つもない場合も状態を保存できるよう、
対象の正本`general_question_session_coverage(id, council_session_id, source_kind)`と、
追記型の`general_question_session_coverage_observations`を分ける。正本は
`(council_session_id, source_kind)`と
`(id, council_session_id, source_kind)`を一意にする。観測行は`coverage_id`、`state`、
`council_session_id`、`source_kind`、`observation_key`、`record_presence`、
`session_disposition`、`expected_count`、`matched_count`、`checked_at`、`qa_status`、
`publication_state`、`reviewed_by`、`reviewed_at`を持つ。`session_disposition`は
`held / not_held / not_applicable / unknown`とする。

`(coverage_id, observation_key)`と
`(id, coverage_id, council_session_id, source_kind)`を一意にし、観測から正本へも
対象ID一式の複合外部キーを張る。同じcoverage対象で
`publication_state=published`の観測を一つだけ許す。再取得時は旧観測を
削除・上書きせず`superseded`へ切り替える。非draft観測は`qa_status=verified`かつ
`reviewed_by / reviewed_at`が両方非nullの場合だけ許すCHECKを設け、未公表・取得不能・
対象外の観測も匿名の承認で公開できないようにする。

`session_disposition`、`state`、`record_presence`、件数は独立に組み合わせず、次の許容行列を
一つのCHECK制約で固定する。件数には共通の非負・`matched_count <= expected_count`制約も
重ねる。

| `session_disposition` | 許可する`state` | `record_presence` | 件数条件 |
| :-- | :-- | :-- | :-- |
| `held` | `collected / partial` | `present` | `matched_count >= 1` |
| `not_held` | `collected` | `absent` | `expected_count = 0`かつ`matched_count = 0` |
| `not_applicable` | `not_applicable` | `unknown` | 両件数ともnull |
| `unknown` | `collected` | `absent` | `matched_count = 0` |
| `unknown` | `partial` | `unknown` | `matched_count`はnullまたは0 |
| `unknown` | `uncollected / source_not_published / source_unavailable / error` | `unknown` | 両件数ともnull |

これ以外はdraftでも保存しない。特に`present`は`held`だけに許し、資料内に行が無かった
`collected + absent + unknown`を`not_held`へ自動変換しない。`unknown`は「実施なし」の表示や
実施会期の分母へ使わず、確認状況だけを表示する。

別会期の資料をcoverage根拠へ流用できないよう、
`general_question_session_coverage_source_occurrences`に`id`、`coverage_id`、
`council_session_id`、`source_kind`、`ingestion_source_id`、
`source_coverage_key`を持たせる。`(ingestion_source_id, source_coverage_key)`を
coverage IDなしで一意にし、`(coverage_id, council_session_id, source_kind)`から正本へ
複合外部キーを張る。根拠から対象付きで参照できるよう、
`(id, coverage_id, council_session_id, source_kind, ingestion_source_id)`も一意にする。版別の
`general_question_session_coverage_observation_sources`は`observation_id`、
`coverage_id`、`council_session_id`、`source_kind`、`coverage_source_occurrence_id`、
`ingestion_source_id`、`source_version_id`、`parse_run_id`、`evidence_revision`、
`evidence_role`、`source_locator`、`extraction_method`、`qa_status`、
`verified_by`、`verified_at`を持つ。観測・occurrence・取得版・解析実行へ対象ID一式を
含む複合外部キーを張り、同じ物理根拠を二つのcoverage正本へ割り当てない。
parser/manual、追記型一意制約、不変性は他の版別根拠と同じ契約にする。集計の分母は
`state=collected`かつ`qa_status=verified`かつ公開中で、`session_disposition`が
`held`または`not_held`の観測だけに限定し、カバレッジを同時表示する。
`checked_at`は必須とし、publishedかつ`state in ('collected', 'partial')`では
同じ会期・source kindへ束縛されたverified primary根拠を一つ以上必須にする。根拠版のない
`record_presence=absent`や、別会期資料による「確認済み0件」を公開できないようにする。

### 6.5 公開整合、原本保持、安定ID

表をまたぐ公開条件はDBで保証する。共通0Bが所有する
`council_meeting_publication_guard`に加え、一般質問migrationで次のguard関数を作る。

- `general_question_appearance_publication_guard`: published登壇revisionに、同じ登壇枠・
  会議・source occurrenceへ結ばれたverified根拠を一つ以上要求する。親会議はpublished・
  verified、`kind=plenary`、`council_session_id`あり、`committee_id=null`で、状態を
  `scheduled / held`に限定する。scheduledの登壇枠は予定表示だけに使い、実績集計はheldに
  限る。親会議revisionの切替でも再検査する。
- `general_question_item_publication_guard`: published項目revisionにverified根拠を要求し、
  revision自身の確認者・確認日時、published親チェーンの存在・同一登壇枠・
  非循環に加え、親登壇枠にあるpublished・verified revisionを検査する。
- `general_question_answerer_publication_guard`: published答弁者revisionに、同じ登壇枠へ
  結ばれたverified根拠、revision自身の確認者・確認日時、親登壇枠の
  published・verified revisionを要求する。
- `general_question_classification_publication_guard`: published分類セット自身を
  `qa_status=verified`かつ`reviewed_by / reviewed_at`が両方非nullに限定し、
  `status=completed`の同一taxonomyのrun、`published_at`が非nullのtaxonomy、
  published項目を要求する。
- `general_question_classification_release_guard`: published releaseをconsumer内で一つに限定し、
  公開済みtaxonomy、DB生成snapshotとitemの双方向`EXCEPT`が0件、同じtaxonomyの
  completed・verified・published分類セットまたは確認済み除外を全itemに要求する。
  snapshot・member・release・item・set・対象項目・親appearanceの変更でもactive releaseを
  再検査する。
- `general_question_coverage_publication_guard`: publishedの`collected / partial`観測に
  対象付きsource occurrenceを介した同じ会期・source kindのverified primary根拠版を要求し、
  上記の`session_disposition × state × record_presence × 件数`行列を再検査して
  `present / absent`の意味を一致させる。`held / not_held`は、その判断を支える同じ会期の
  verified primary根拠なしでは公開できない。

各関数は対象の正本・revision・親revision・分類セット・分類topic子行・
classification population snapshot・member・release・item・coverage観測・根拠の
`INSERT / UPDATE / DELETE`後に発火する
`CONSTRAINT TRIGGER DEFERRABLE INITIALLY DEFERRED`から呼ぶ。最後のverified根拠の削除・
`rejected`化、別正本への付け替えもコミット時に拒否する。repositoryは同じ関数を
公開切替前の早期確認に使うが、DB保証の代替にはしない。manual根拠をverifiedとして数える
場合は取得版・根拠位置・確認者・確認日時を必須にする。

一般質問固有のconsumer typeを共通0Aの`source_artifact_consumer_types`へ登録する。
通常同期triggerは公開判定に数えるparser根拠を
`published_source_version_references`へ登録し、`superseded / rejected`化でreleaseする。
各publication guardは公開集合とregistryの完全一致も検査するため、共通の保持guardへ
一般質問テーブル名をハードコードしない。一般質問固有typeの対象には登壇枠、質問項目、
答弁者、会期coverageの根拠を含めるが、0Bが所有する会議revision根拠は含めない。

安定正本の親ID・stable keyと、全source occurrenceの正本ID一式・
`ingestion_source_id`・ローカルキーは`prevent_stable_identity_update`で通常UPDATEを
拒否する。revisionと版別根拠も対応先・取得版・解析実行・抽出内容の上書きを禁止し、
QA・公開・確認情報だけを状態遷移で変更する。誤突合候補はstagingで確認し、監査対象の
物理DELETEを行わない。訂正は新revisionと`superseded / rejected`で残す。

## 7. 取り込み・正規化・人手QA

### 7.1 PDF取り込み

1. 本会議報告の索引から期ページを探索し、一般質問PDF URLを収集する。
2. PDFを取得し、最新状態を`ingestion_sources`、取得した版を共通の
   `ingestion_source_versions`へ保存する。
3. 共通の`ingestion_parse_runs`にパーサー名・版・設定を記録し、
   `pdftotext -layout`相当で一時テキスト化してPDF本文の元号・会期・開催日を解析する。
4. 行の座標・段組みを考慮して、登壇枠、質問方式、階層項目、答弁者を抽出する。
5. 会期・開催日を`council_sessions`と突合し、stagingへ出力する。
6. 前回確定値との差分を生成し、新規・変更・消滅をQAキューへ送る。
7. QA承認後に公開テーブルへ反映する。ソースから消えた行は即削除せず非公開化候補にする。

元号はURLやファイル名から推測せず、PDF本文の会期見出しを正とする。質問方式の表記揺れは
原文ラベルと正規化enumを両方保持する。

### 7.2 会議記録・映像との照合

- PDFの登壇日・氏名・順番をAmiVoiceの会議記録と照合する。
- `AmivoiceClient.searchMinutes`の`hits.length`と公式画面のヒット総数を比較し、ページング
  欠落がある実行は失敗扱いにする。
- 会議記録本文は処理中だけ使用し、発言全文をDBへ保存しない。
- DiscussVisionは外部ID・発言区間URLの補助とし、PDF・会議記録との不一致を自動で
  上書きしない。
- 市議会議員名は空白、旧字体、異体字を正規化候補にするが、曖昧な突合は
  `council_member_id=null`のまま人手確認する。

### 7.3 政策分野分類

- 最初に20～30件を2人で独立分類し、分類定義と境界例を確定する。
- 1項目に複数分野を許す。主分野を強制して情報を落とさない。
- AIは分類候補と独自要約の下書きにのみ使い、公開は人手承認後とする。
- モデル名、プロンプト版、分類マスタ版、実行日時、confidenceを記録する。
- 分類定義を変更した場合は旧版を残し、同じ画面内で版の異なる集計を混ぜない。

### 7.4 QA基準

初期対象の現任期は全登壇枠を人がPDFと照合する。確認項目は次のとおり。

- 会期、質問種別、開催日、質問順
- 資料記載氏名、議席番号、市議会議員マスタとの突合
- 質問方式、最上位項目数、階層、答弁者役職
- 公式URL、PDFページ、取得日時
- `null`、`0`、`not_held`の区別
- 政策分野と公開要約が原文の趣旨を超えていないこと

過去分へ広げる条件は、1会期単位の公式掲載枠数とDB件数が一致し、fixture化した全形式の
パーサテストが通り、未突合・重複・日付逆転がQA画面で0件になることとする。

## 8. 画面・可視化

### 8.1 情報設計

候補ルートは次のとおり。実装時は`web/src/lib/routes.ts`へ必ず追加する。

- `/questions`: 一般質問の概要、会期・政策分野フィルター、カバレッジ
- `/questions/sessions/[sessionSlug]`: 会期別の登壇日・質問順・政策分野・公式リンク
- 個人別集計ページは作らない。氏名検索が必要な場合も結果は日付順の一次資料導線とし、
  件数順やスコア順にはしない。

### 8.2 初期版の可視化

1. **会期タイムライン**
   - 一般質問実施日、代表質問・個人質問、登壇枠を日付順に表示する。

2. **政策分野の構成**
   - 会期別・年度別の積み上げ棒またはドット表示。

3. **登壇枠単位の政策分野×答弁者役職の共起**

     共起であり、個別項目への答弁帰属ではないと明記する。

5. **データカバレッジ**

各カードには「出典」「対象期間」「取得日時」「集計単位」「未取得件数」を表示し、

- 市議会議員別の件数順位を生成する関数・UIが存在しないことの設計レビュー

### 11.2 DB・Integration

- 新規テーブルはRLSを有効化し、ポリシーを定義せず、Server側の
  `createAdminClient()`経由でのみ取得する。
- 一意制約、外部キー、QA済み公開条件、会期・会議のソートを実DBで検証する。
- 資料差し替え後も同じ会議・登壇枠を重複作成せず、新しい解析実行を追記できる。
- 会議・登壇枠の根拠へ別会議のソース内出現または別論理ソースの取得版を結べない。
- 会議revisionは`held`なら`held_on`必須、非heldなら実績日・開閉時刻なし、
  `scheduled / cancelled`なら`scheduled_on`必須となる。`closed_at`だけ、または
  `closed_at < opened_at`のINSERT / UPDATEを拒否し、published状態・日時を支えるverified根拠を
  削除・却下するとコミットできない。正しい予定→開催済み、中止、時刻あり開催への切替は通る。
- published会議revision自身の確認者・確認日時を必須にし、予定日・開始予定時刻は
  verified schedule根拠と一致させる。片欠け、根拠値不一致、最後の根拠却下、
  reviewed後のdraft巻き戻しを拒否する。
- `council_session_id`のあるpublished会議は、状態に応じた実開催日または予定日が
  会期の開始日・終了日の範囲内である。別会期・境界外・日付なしの関連付けを拒否し、
  `unknown`の会期ID・予定日・実績日も拒否する。両境界日と閉会中の
  `council_session_id=null`は受理する。公開後の会期期間縮小は
  関連会議と子を残す限り拒否し、同一トランザクションで会期・会議・子を正しく
  切り替える操作は成功する。
- 会議の`plenary / all_members / other`へ`committee_id`を設定する操作、committee / steeringで
  nullまたは委員会種別の不一致を拒否する。一般質問登壇枠をcommittee会議、会期なし本会議、
  cancelled / unknown会議へ公開できず、親会議だけを不適格なrevisionへ切り替える操作も
  拒否する。親子を同一トランザクションで正しく切り替える操作は成功する。
- 同じ会議ソース内の登壇枠・項目・答弁者キーを二つの正本へ結べず、別会議では同じ
  ローカルキーを利用できる。
- 会議・登壇枠・項目・答弁者のsource occurrenceについて、対象正本ID一式、
  `ingestion_source_id`、ローカルキーの直接UPDATEを拒否し、誤突合を別正本へ
  付け替えられない。
- 会議・登壇枠・項目・答弁者・分類の安定正本では親IDとstable key、revisionでは
  正規化内容、版別根拠では対応先・取得版・解析実行・抽出値の通常UPDATEを拒否する。
  QA・publication・確認情報だけの許可された状態遷移は成功し、対象表へのtrigger付与漏れを
  migrationテストで検出する。
- 別の取得版に属する解析実行を根拠・coverage根拠へ指定すると、複合外部キー違反で
  保存できず、解析実行だけ、または論理ソースなしで取得版だけを指定したcoverage根拠も
  CHECK制約で拒否される。
- 順番不明の登壇枠を保存でき、非nullの質問順だけが会議内で一意になる。
- 別の登壇枠に属する質問項目を親として設定できない。
- 登壇・項目・答弁者revisionは`reviewed_by / reviewed_at`の片方または両方を欠く
  verified化と非draft遷移を拒否する。根拠の確認者だけがあっても不十分とし、
  公開後のrevision確認者・日時のnull化を拒否する。両方とverified根拠がある正例と、
  新旧revisionを同一トランザクションで切り替える正例も確認する。
- 質問項目の自己参照、2項目以上の循環、published revisionのない項目を親にした子の
  published化を拒否する。親子を同じトランザクションで正しく公開切替する操作は通り、
  repositoryが導出する階層深さはpublished親チェーンと一致する。
- 親登壇revisionがdraft・superseded・未確認のまま項目・答弁者・分類releaseを
  公開できず、公開中の子を残した親だけのsuperseded化も拒否する。親子と
  releaseを新旧revision間で同一トランザクション切替する操作は成功する。
- 項目・答弁者の版別根拠に、異なる登壇枠source occurrence、または別の
  source occurrenceに属する`appearance_source_id`を結ぶと複合外部キー違反になる。
- 答弁者の`role_display_name`だけを訂正してもQA済み`role_group`が同じなら過去集計値が
  変わらず、`role_group=unknown`は役職別共起集計へ入らない。
- 行なし、確認済み0件、未公開、解析失敗をcoverage行で区別できる。
- coverageの再確認で旧観測が残り、公開中の観測は対象ごとに一つだけになる。
- coverage観測は`reviewed_by / reviewed_at`の片方でも欠くと、取得済み・未公表・取得不能・
  対象外のいずれも`reviewed / published / superseded`へ進めない。
- 別会期または別`source_kind`のcoverage source occurrence・取得版を結ぶと複合外部キーで
  拒否され、対象会期へ束縛されたverified primary根拠だけがpublished観測を支えられる。
- 共通契約で無効なstate・record presence、負の件数、matched超過をDB制約で拒否する。
- 許容行列の全行をINSERT / UPDATEできることを確認し、`not_held / not_applicable + present`、
  `held + not_applicable`、`not_held + matched_count > 0`、`unknown`から「実施なし」への
  自動変換を拒否する。publishedの`held / not_held`は同じ会期のverified primary根拠を
  外すとコミットできない。
- 共通会議guardと六つの一般質問publication guardについて、repositoryを迂回した直接SQLでも、
  根拠のないpublished行、最後のverified根拠のDELETE・`rejected`化、別正本の根拠への
  付け替えをコミット時に拒否する。新旧根拠を同一トランザクションで正しく切り替える操作は
  成功する。
- 共通会議のpublished parser根拠は0Bの
  `common:council_meeting_revision`としてregistryへ一度だけ登録され、一般質問固有typeへ
  重複しない。manual会議根拠は取得版、空でないlocator、確認者、確認日時のいずれかを
  欠くとverified根拠として数えない。
- published parser根拠の追加・`superseded / rejected`化で、一般質問固有consumer typeの
  active referenceが共通registryと完全に同期する。参照中取得版の
  `retained → expired / not_permitted / pending`変更またはobject key除去は単独UPDATEでは
  失敗し、同一トランザクションで別保持版またはmanual確認済み根拠へ切り替えた後は成功する。
- manual根拠は取得版・根拠位置・確認者・確認日時がなければverified根拠として数えず、
  同じsource occurrenceの別取得版へ追記しても旧版を失わない。
- 同じ質問項目・taxonomyで公開中の分類結果セットを二つ作れず、同じ項目の
  別taxonomyセットは併存できる。run切替後の公開viewはactive releaseの新セットだけを
  返す。
- 項目ごとのpublishedセットにtaxonomy v1・v2が混在していても、公開view / APIは
  `general_question_item`の単一active releaseに列挙された一つのtaxonomyだけを返す。
  同consumerのactive release二つ、未公開taxonomy、未完了run、未確認set、
  snapshot memberの欠落・余分・別snapshotのitem、理由未確認の除外を拒否する。
- snapshot作成関数が型付き範囲のpublished・verified revisionだけを列挙し、件数と順序付き
  ID hashをDBで生成する。呼び出し側の過去・未来cutoff指定を拒否し、同一トランザクションの
  一括生成で並行公開による半端なmember集合を作らない。欠落を自己申告件数でごまかす操作、
  余分item、別snapshot item、
  件数・hash・memberの直接変更を拒否する。snapshot後の新規項目は旧snapshotを変えず、
  新snapshotのみに入る。
- 実績snapshotは親会議がpublished・verified・held・実開催日ありの項目だけを含み、
  scheduled / cancelled / unknownを除外する。予定表示は別planned releaseからだけ読み、
  scheduledからheldへ変わった項目は新snapshotで採用し、plannedとactualを合算しない。
- draft releaseは内容を変更できるが、reviewed以降は識別・taxonomy・snapshot・item集合・
  確認内容を更新、削除、draftへ巻き戻しできない。reviewedセットで新版を準備し、
  セット・releaseの旧新を同一トランザクションでpublished / supersededへ切り替える操作は
  成功する。
- active releaseのitem追加・削除・set差し替えを拒否し、API契約テストで
  `classificationReleaseId / taxonomyId / taxonomyVersion / population`が固定される。
  一般質問と委員会のactive taxonomyが違う場合は横断集計せず、同じ場合だけ合算する。
- terminal化したrunの分類セット新規作成・identity変更と、同runを参照するtopicの
  追加・変更・削除を、親セットがdraftでも直接SQLで拒否する。running中にセットとtopicを
  作成してからcompletedへ進める操作は成功し、訂正は新しいrun・draftセットでだけ行える。
- 分類run・結果セットと異なるtaxonomy版の政策分野は複合外部キー違反で保存できない。
- `running / failed / rejected`の分類run、未確認の分類セット、または
  `reviewed_by / reviewed_at`の片方でも欠くセットは公開できず、`completed` runと
  `qa_status=verified`、確認者、確認日時が揃うセットだけが公開できる。
- `policy_taxonomies.published_at`がnullのtaxonomyを参照する分類セットは、runと確認情報が
  揃っていても公開できない。
- 分類runは`running + finished_at=null`でだけINSERTでき、一度の
  `running → completed / failed / rejected`だけが成功する。terminal状態での直接INSERT、
  taxonomy・method・model・prompt・開始日時のUPDATE、terminalからの再遷移をDBで拒否する。
- 公開済みtaxonomyのversion・label・published_atと配下topicのslug・label・description・
  `is_active`、行集合を直接変更できない。確認者・確認日時の欠落・片欠け、reviewed後の
  topic DML・承認取消・draft巻き戻し、content hash不一致を拒否する。確認情報とhashが揃う
  正例、新taxonomy versionと新topic IDの訂正は成功し、旧run・旧分類セットの表示内容は変わらない。
- DB functionを追加・変更するPRでは、functionごとに
  `tests/supabase/db-function/{kebab-case-function-name}.test.ts`を作成し、
  `tests/supabase/utils.ts`を利用してローカルSupabase実DBで検証する。戻り値、ソート、
  フィルター、集計、権限を対象とし、DBはmockしない。
- 公開viewは`security_invoker`、functionは原則`SECURITY INVOKER`とし、anon接続が
  基底表・view・functionから取得できないことを検証する。
- Open Data APIを追加する場合は未承認行、原文、内部confidenceを返さないことを検証する。
- 保存fixtureを通常CIで使い、公式サイトへのlive testは低頻度・手動実行に分離する。
- AmiVoice・DiscussVision・HTTPクライアントはインターフェース経由でDIし、
  通常CIの契約テストでは保存fixtureを返すFakeを使う。`vi.mock("server-only")`は使用せず、
  外部依存のない変換処理を純粋関数へ分離する。

## 12. 受入条件

- 現任期の公開対象について、会期・日付・質問順・氏名・方式・最上位項目数・答弁者が
  公式PDFと全件一致する。
- すべての表示値から、公式URL、資料名、source occurrence、取得版、解析実行、対象期間、
  取得日時、QA状態へ辿れ、保持中のparser原本から同じ設定で再解析できる。
- PDF未公開・未取得・解析失敗を0件として表示しない。
- 一般質問実施なしを、公式資料で確認した場合だけ`not_held`として表示する。
- 一般質問実施日数はpublished・verified・held・実開催日ありの会議だけから算出し、
  予定・中止・unknownや根拠のない日時を混ぜない。
- coverageの公開値が許容行列に一致し、`present`と`not_held / not_applicable`が同時成立せず、
  `session_disposition=unknown`を実施なしの表示・集計へ使わない。
- 公開中parser根拠と共通registryのactive referenceが一致し、根拠なし公開、最後のverified
  根拠の削除、参照中原本の保持終了を直接SQLでも拒否できる。
- 集計単位が「登壇枠」「最上位項目」「答弁者掲載枠」のいずれか明記される。
- 政策分野と答弁者役職の組合せを表示する場合は「登壇枠内の共起」と明示し、
  個別項目への答弁者・部局の帰属として表示しない。
- 一般質問数、登壇回数、発言量による市議会議員ランキングやスコアがない。
- 公開要約・分類は人手承認済みで、原文の長文転載がない。
- 登壇・項目・答弁者の公開revision自身に確認者・確認日時があり、適格な
  published・verified親revisionの連鎖をDBと公開viewの両方で保つ。
- 政策分野の公開view / APIは一般質問の単一active releaseへ束縛され、taxonomy versionと
  DB生成snapshotの範囲・cutoff・件数を返す。snapshot memberとrelease itemが完全一致し、
  新版切替の途中状態や委員会との異版を同じ系列へ混在させない。
- グラフと同値の表があり、色・ポインター操作・視覚だけに依存しない。
- WCAG 2.2 AA・JIS X 8341-3:2016の公開ゲートを満たし、キーボードと
  スクリーンリーダーで、会期・政策分野の絞り込み、結果確認、表閲覧、
  公式資料への移動という主要タスクを完了できる。
- 320 CSS px（1280 CSS px幅を400%拡大した相当条件を含む）で主要情報と操作を
  二次元スクロールなしに利用でき、200%・400%拡大でも再配置される。
- 絞り込み後の件数と適用条件が`aria-live="polite"`で簡潔に通知される。
- 「みらい議会＠沼津市」が沼津市・沼津市議会の公式サービスではない旨と、既存の
  フッター文言「これは政党チームみらいが運営しているものではありません」が維持される。

## 13. リスク・未決事項

| リスク・論点 | 対応・決めること |
| :-- | :-- |
| PDF表の形式変更 | 期・形式別fixture、失敗時は自動公開せずQAへ送る |
| 質問項目の粒度差 | 件数を個人比較に使わず、集計単位と限界を図ごとに表示する |
| 氏名・役職の変化 | 公式表記を残し、期間付きaliasを導入。曖昧な突合はnull |
| 政策分野分類の主観 | 定義・境界例・版を公開し、複数分類、人手確認、訂正履歴を持つ |
| 会議記録の著作権・個人情報 | 本文を永続化・再掲載せず、情報解析、事実、独自要約、公式リンクに限定する。公開前に専門家レビューを行う |
| 公開遅延 | 暫定情報と確定情報を状態で分け、更新日時を表示する |
| 外部基盤の仕様変更 | PDFを基幹とし、AmiVoice・DiscussVisionはadapterで分離する |
| 選挙期間中の見え方 | 個人比較は常時禁止。氏名表示を含む画面の運用方針を公開前に確認する |
| URL設計 | `/questions`か`/gikai/questions`かを情報設計レビューで確定する |
| オープンデータ | CSV/APIに公式資料の利用条件URL、出典、AI要約・人手確認済みであることを明示する。公式資料由来の情報へ本サービス独自のライセンスを付与しない。公開前に専門家レビューで最終確認する |
