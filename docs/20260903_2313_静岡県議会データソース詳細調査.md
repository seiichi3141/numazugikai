- 関連方針: [複数自治体ブランチ運用方針](./20260903_1906_複数自治体ブランチ運用方針.md)

現在の共通 trunk 方針を正とする。

## 1. 結論

### 直ちに進められること

- 審議結果 HTML と添付 PDF を根拠に、会期、議案等の件名、提出区分、議決日、
  議決結果、会派・議員単位の賛否を表現する後方互換な schema を設計する
- 静岡県固有 parser を、公式本文をコピーしない合成 fixture で実装・テストする
- 既存の沼津市取り込みを変更せず、共通の正規化済み入力契約を追加する
- 本会議・委員会会議録は、本文ではなく限定メタデータと公式リンクを扱う設計にする

### 実取得の前に確認が必要なこと

- 議案・審議結果ページの自動取得頻度、User-Agent、差分取得方法を県議会事務局へ
  連絡し、運用上問題がないことを確認する
- `www2.pref.shizuoka.jp` の会議録は全ページに
  `noindex,nofollow,noarchive` があるため、自動巡回、保存、全文検索、要約、
  外部 AI 送信、Domino 内部コマンド利用の可否を文書で確認する
- 公開サイトから公式ページへリンクを設定した後、県のリンク方針に従って
  リンク元・リンク先 URL を県広報窓口へ連絡する

### MVP で行わないこと

- 会議録本文、公式 HTML、PDF、写真、図表の転載・再配布
- 会派票を、その会派に所属する全議員の個人票へ展開すること
- 空欄、欠損列、結果文言から個別の賛否を推定すること
- 公式に公開・保証されていない Domino `ReadViewEntries` への本番依存
- 根拠となる原資料がない議案への AI 解説生成

この結論は安全側の運用方針であり、法的助言ではない。公開前に県への確認と、
必要に応じて専門家による確認を行う。

## 2. 調査方法と範囲

公式サイトに対して GET / HEAD の読み取り専用アクセスだけを行った。
審議結果は、現行索引に掲載された令和5〜8年度の全17会期について、HTML と
添付 PDF の計727結果行を照合した。加えて、請願の境界例として令和4年の公式資料、
会議録は最新会期、最古カテゴリ、ページング、カテゴリ展開、文書リンク、文字コード、
HTTP header、robots 指示を標本確認した。

調査値は基準日時点のスナップショットである。公式ページは更新・削除され得るため、
実装では取得日時、公式更新日、HTTP validator、content hash、元の値を保持する。

### 4.2 HTML と PDF の役割

| 項目 | HTML | 添付 PDF | 保存方針 |
| :-- | :-- | :-- | :-- |
| 会期名 | あり | あり | 正規化値と元表記を保存 |
| 提出区分・文書区分 | 見出しにあり | 表にあり | enum と元見出しを保存 |
| 議案番号 | あり。表記揺れあり | あり | 数値だけにせず、元表記も保存 |
| 件名 | あり | あり | 事実情報として保存し、source URL を併記 |
| 議決日 | 見出し単位 | 行単位 | PDF の行値で補完し、矛盾時は要確認 |
| 上程日 | なし | あり | PDF から取得できる場合のみ保存 |
| 結果 | `可決・全員一致` 等 | `可決` と一致区分が別列の場合あり | 構造化値と全 raw 値を保存 |
| 会派・個人票 | あり | あり | 双方を照合し、actor 単位で保存 |
| 備考 | 原則なし | あり得る | 任意 raw field として保存 |
| 公式更新日 | ページにあり | 文書内部では一定しない | HTML の更新日を source 単位で保存 |

HTML と PDF はどちらも公式であり、どちらかを常に正しいものとして上書きしない。
実際に[令和6年5月臨時会](https://www.pref.shizuoka.jp/kensei/kengikai/gikaiugoki/1003742/1063479/1063612.html)の
第89号で、HTML の「同意・全員一致」と
[公式 PDF](https://www.pref.shizuoka.jp/_res/projects/default_project/_page_/001/063/612/giketukekka0517.pdf)の
「承認」が一致しない例を確認した。件名も「専決処分事件の承認について」であるが、
取り込み側で PDF を正解と決め打ちしない。この場合は両方の raw 値を保存し、
`source_conflict` として公開前レビューに回す。

### 4.3 確認した文書区分

| 正規化候補 | 公式見出しの例 | 番号 | 提出者の扱い |
| :-- | :-- | :-- | :-- |
| `executive_bill` | 知事提出議案 | あり | `governor` |
| `member_bill` | 議員提出議案 | あり | `member` |
| `committee_bill` | 委員会提出議案 | あり | `committee` |
| `petition` | 請願 | あり | `citizen`。紹介議員とは分ける |
| `financial_statement` | 決算 | ない例がある | `governor`、または source 上の提出区分 |
| `opinion` | 意見書 | ない例がある | 議会文書として扱い、提出者を推定しない |
| `resolution` | 決議 | ない例がある | 議会文書として扱い、提出者を推定しない |

令和6年5月臨時会には「知事職務代理者提出議案」という見出しがある。canonical な
`governor` は執行機関提出の互換区分として用いる一方、`raw_submitter_label` と
`submitter_role_snapshot` に「知事職務代理者」を残し、表示上の役職を知事へ書き換えない。

陳情は、県公式説明上、請願と異なり採択・不採択などの議会決定を行わない。
審議結果と同じモデルへ無理に入れず、将来必要になった時点で別の要望文書として扱う。

### 4.4 議案番号は単独キーにならない

令和8年2月定例会には、知事提出、議員提出、委員会提出のそれぞれに「第1号」がある。
現行の `(council_session_id, bill_number)` 一意制約では格納できない。
また、意見書、決議、決算には番号がない行がある。

取り込み側で次の不透明な `source_record_key` を生成し、DB の一意性に用いる。

```text
shizuoka-pref:<session-slug>:<section-kind>:<submitter-kind>:<normalized-number-or-stable-id>
```

- `session-slug`: 西暦年月、定例会・臨時会、必要なら回次から作る会期の安定 key
- `section-kind`: 提出区分・文書区分。見出し raw 値も保存する
- `submitter-kind`: 知事、議員、委員会など。同じ第1号を区別する
- `normalized-number`: `第96号議案` / `第96号` を同じ番号へ正規化する
- `stable-id`: 番号がない場合、初回レビューで割り当てて以後変更しない不透明 ID

番号なし record の `stable-id` は、件名、議決日、行番号など訂正・並べ替えで変わる値から
再生成しない。初回 observation と stable-id の対応を alias として保存し、次回以降はその対応を
参照する。未知の fingerprint や複数候補は新規 record を自動作成せずレビューへ送り、訂正と
確認できたときだけ新しい alias を同じ stable-id に追加する。番号なしの
`source_record_key` 全体も初回確定値を永続化し、後から構成要素を再計算して変更しない。

ページ ID は URL から別途 provenance として保持するが、authoritative key に含めない。
事前案内ページが削除され、同じ会期の最終結果が別ページ ID で公開された例があるためである。
件名だけも識別子にしてはならない。誤字修正やページ差し替えがあっても同じ record と
判定できるよう、会期、区分、番号、枝番、既知 observation を併用し、曖昧な場合は
新規作成せずレビューで alias を確定する。

### 4.5 結果の表現

確認した主な結果は、単一文字列に押し込めず、少なくとも次に分解する。

```text
decision: passed | rejected | approved | consented | adopted | not_adopted | certified
          | continued | withdrawn | reported | other | unknown | null
agreement: unanimous | majority_for | minority_for | unknown | null
raw_result: 公式表記を無加工で保持
```

例:

| 公式表記 | `decision` | `agreement` |
| :-- | :-- | :-- |
| 可決・全員一致 | `passed` | `unanimous` |
| 可決・賛成多数 | `passed` | `majority_for` |
| 否決・賛成少数 | `rejected` | `minority_for` |
| 承認・全員一致 | `approved` | `unanimous` |
| 同意・全員一致 | `consented` | `unanimous` |
| 採択・全員一致 | `adopted` | `unanimous` |
| 不採択・賛成少数 | `not_adopted` | `minority_for` |
| 認定 / 全員一致 | `certified` | `unanimous` |
| 継続審査 | `continued` | `null` |
| 撤回 | `withdrawn` | `null` |
| 報告 | `reported` | `null` |
| 空欄（未決定） | `null` | `null` |

`continued`、`withdrawn`、`reported` と未決定の `null` は既存 Numazu 入力との後方互換の
ため共通契約に残す。raw 値はあるが対応不能なら `unknown`、既知のその他区分なら `other`
とし、勝手に既知値へ寄せない。`unknown` / `other` はそのまま公開用 `bill_status_enum` に
変換せず、レビューで既存 status への対応を確定するまで `preparing` の公開前状態に留める。
県の「全員一致」は投票参加者間の一致を示し得る。実際に個人列が `欠` でも
結果が「全員一致」の例があるため、全在籍議員の賛成という意味に展開しない。

### 4.6 賛否 actor と記号

通常表には会派列と無所属議員列が混在する。
[令和5年6月定例会](https://www.pref.shizuoka.jp/kensei/kengikai/gikaiugoki/1003742/1054197/1055138.html)の
知事不信任決議は、
通常表ではなく、議席番号付きの白票50名・青票18名による全議員の記名投票である。
議員数の3分の2以上が出席し、出席議員の4分の3以上が賛成するという特別要件も
明記されており、
可決条件を通常の過半数に固定してはならない。
したがって、会派専用 table だけでは表現できない。

```text
actor_type: faction | member
position: for | against | split | absent | excluded | abstained | unknown
voting_method: table | recorded_ballot | other
raw_mark: 〇 | ○ | ◯ | × | 欠 | ...
ballot_color: white | blue | null
seat_number_at_vote: integer | null
actor_name_at_vote: string
faction_name_at_vote: string | null
for_count: integer | null
against_count: integer | null
```

賛成記号は `〇`（U+3007）、`○`（U+25CB）、`◯`（U+25EF）の3種類を確認し、
同一ページ内で異なる字形が混在する例もある。3種類を `for` に正規化する一方、
`raw_mark` は失わない。`×` は `against`、`欠` は `absent` とする。
空欄、未知の記号、列不足は `unknown` とし、賛成へ既定化しない。既存 Numazu の
会派内賛否が分かれた `split` と `for_count` / `against_count` も損失なく共通契約へ渡す。

会派 actor の1レコードは「その会派の公式表示」を意味する。現在または採決当時の
所属名簿から、所属議員ごとの票を生成してはならない。個人 actor は公式表が個人名を
明示した場合だけ作る。

### 4.7 請願の境界例

現行索引の令和5〜8年度17会期には、請願 section を確認できなかった。
しかし、令和4年の公式資料には次の結果があり、将来の再出現に備える必要がある。

- [令和4年6月定例会の公式 PDF](https://www.pref.shizuoka.jp/_res/projects/default_project/_page_/001/030/981/0406giketsukekka.pdf):
  請願第1号が採択・全員一致
- [令和4年12月定例会の公式資料](https://www.pref.shizuoka.jp/_res/projects/default_project/_page_/001/077/648/202212pressrelease.pdf):
  第2号、第3号（その1〜その3）が不採択・賛成少数、第4号が採択・全員一致

`第3号（その1）` のような枝番を落としてはならない。`number=3` と
`sub_number=1` に分けつつ、raw number を保持する。請願が直近サンプルにないことを
理由に parser や schema から除外しない。

### 4.8 原案・説明資料

審議結果ページには、各議案の原案本文への統一リンクがない。

- 予算には別系統の予算書・説明書 PDF がある

## 5. 本会議・委員会会議録

### 5.1 公開範囲

| DB | 公式記載の収録開始 | 開催別 view の確認結果 |
| :-- | :-- | :-- |
| 本会議 `ggiji.nsf` | 平成11年5月臨時会。目次は平成19年2月定例会から | 最古カテゴリも平成11年5月、会期カテゴリ151件 |
| 委員会 `comgiji.nsf` | 平成19年5月臨時会 | 最古カテゴリも平成19年5月、最上位カテゴリ999件 |

県議会沿革には、本会議録の Web 公開開始を2000年2月、委員会会議録の Web 公開開始を
2006年9月とする別の記載がある。これはサービス開始時期であり、現在の DB に収録された
最古会期とは意味が違うため混同しない。

### 5.2 公開 view

本会議には、開催別、知事提案、議員別、代表質問、一般質問、全文検索の導線がある。
委員会には、開催別、委員会別、議員別、全文検索の導線がある。

開催別 HTML は Lotus Domino の階層 view で、既定30件である。

```text
WebView1?OpenView&Start=1&Count=30
WebView1?OpenView&Start=1&Count=30&Expand=1
```

- 次ページの `Start=30` は境界項目を重複して返すため、UNID で重複排除する
- 展開後は `Start=1.29` のような階層 position が現れる。position を永続 ID にしない
- `ExpandView` は全カテゴリを展開し負荷が大きいため使用しない
- 本会議は会期、親文書、答弁 response の3層を持ち、親文書に答弁がインラインで
  重複する場合がある。親・response を両方本文として数えない

### 5.3 文書 URL

文書リンクは次の形で、32桁の view ID と文書 UNID を含む。

```text
/all/<db>.nsf/<view-id>/<document-unid>?OpenDocument
```

例:

- [本会議の採決文書](https://www2.pref.shizuoka.jp/all/ggiji.nsf/ffb2b708c352ce3449256854002dd512/66c51c8b2e0ccb0549258e1800217fba?OpenDocument)
- [委員会文書](https://www2.pref.shizuoka.jp/all/comgiji.nsf/ffb2b708c352ce3449256854002dd512/86ca5edfeb608d0e49258df4000403b9?OpenDocument)

canonical URL や永続保証はない。画面に出た完全な href と UNID を保存し、view ID を
推測して URL を再構築しない。県の方針も URL の変更・削除可能性を明記しているため、
リンク切れを定期確認し、切れた場合も過去本文を無断転載して代替しない。

### 5.4 文字コード

- HTTP `Content-Type` は `text/html; charset=Shift_JIS`
- body の meta は誤って UTF-8 を示す
- 展開 view には厳密な Shift_JIS decoder が失敗する byte がある
- `CP932` / `Windows-31J` なら変換できる
- `ReadViewEntries` の XML だけは UTF-8

取得 client は HTTP header を優先しつつ CP932 互換 decoder を明示し、置換文字数と
decode error を記録する。JIS 外字などが公式画面上で `■` になっている場合も、
氏名を推測復元しない。

### 5.5 更新検知

HEAD は利用できるが、調査時点では `If-Modified-Since` / `If-None-Match` に同じ値を
送っても 304 ではなく 200 を返した。`Last-Modified` と `ETag` は複数文書で DB 単位に
同じ値となり、文書個別の更新日時とは扱えない。

実装する場合は、HEAD の validator が前回値と同じなら取得を止め、変化時だけ小さい
`Count` で先頭から既知 UNID まで辿る。validator が欠損・異常な場合は content hash と
上限付き取得へ切り替える。

### 5.6 検索と非公開仕様

`WebSearch?CreateDocument` は公開 UI 用の POST だが、Domino 文書作成と多数の legacy
option に依存する。上限には「無制限=5000」もあり、自動収集には使わない。

`WebView1?ReadViewEntries&Start=1&Count=5&Expand=1` は匿名 XML を返すことを確認した。
しかし県が API としてリンク・文書化した interface ではなく、schema、廃止、負荷の
保証もない。初期実装では不採用とし、将来、議事課が利用を明示承認した場合だけ、
小さい `Count`、HTML fallback、fixture 監視を備えた opt-in 機能として再検討する。

### 5.7 議案との対応

会議録文書に内部 bill ID はない。`第１号`、`第一号`、ASCII 数字、一括採決が混在する。

```text
会期 + 提出区分 + 正規化番号 -> bill_minutes_links <- 会議録文書
```

- 一つの文書が複数議案を扱うため、多対多とする
- 単なる言及と、提案説明、質疑、討論、採決を `relation_kind` で分ける
- 会議録本文中の結果より、審議結果ページを結果の正本として優先する
- confidence が閾値未満、提出区分が不明、番号が複数候補なら自動確定しない

許諾前は自動突合のために本文を収集せず、会議録 view から得られる限定メタデータか
人手確認でリンクする。

## 9. コンフリクトを減らす実装境界

共有 `develop` に自治体固有処理を直接混ぜず、次の境界にする。

```text
静岡県公式 source
  -> packages/shizuoka-ingest の source 固有 parser
  -> packages/council-ingest-core の正規化済み IngestRecord contract
  -> 共通 repository / schema
  -> profile capability に応じた Web / Admin 表示
```

### 原則

- `packages/numazu-ingest` の parser と source client は変更しない
- 静岡県の URL、selector、CP932、表記正規化は `packages/shizuoka-ingest` に閉じ込める
- Numazu repository を一度に移動せず、呼び出し単位で `council-ingest-core` へ寄せる
- enum と table は既存値を rename / delete せず、additive に拡張する
- 既存 Numazu データを新 key へ backfill してから旧 unique constraint を切り替える
- read model は既存 `faction_votes` を当面読める compatibility layer を持つ
- `SITE_ID` 未指定時の Numazu 既定動作を維持し、未知 ID は fail closed にする
- 公開 runtime readiness と、隔離 staging への ingest capability を別の flag にする
- `shizuoka-pref` は必要 schema と seed readiness が揃うまで fail-closed のままにする
- 自治体ごとの DB と実データは分離するが、migration 履歴と生成型は共有する

### 推奨する provenance

source 単位:

```text
site_key, source_kind, source_url, source_page_id,
source_updated_at, fetched_at, http_etag, http_last_modified,
content_hash, parser_version, decode_warning_count
```

record 単位:

```text
source_record_key, raw_section_label, raw_number, raw_title,
raw_result, source_row_index, source_document_url,
source_conflict, review_status
```

個人・会派名は現在の master 参照だけにせず、採決時点の表示名を snapshot として保存する。

### 推奨する additive schema

名前は実装 PR で既存命名規則に合わせて確定するが、責務は次のように分ける。

| 保存先 | 役割 | 主な項目 |
| :-- | :-- | :-- |
| `bills` 拡張 | 正規化済みの公開候補 | `source_record_key`, `result_agreement`, `review_status` |
| `ingestion_sources` 拡張 | URL単位の取得状態 | `site_key`, `source_updated_at`, `parser_version`, `charset`, decode warning |
| `bill_source_observations` | HTML / PDF ごとの根拠と差分 | source FK、row key、raw number/title/result、parsed fields、取得時刻 |
| `bill_source_aliases` | source 上の識別候補と永続 key の対応 | bill FK、source record key、fingerprint、locator、確認方法、確認時刻 |
| `bill_vote_positions` | 会派・個人を共通化した票 | actor type/FK、snapshot 名、position、raw mark、方式、票色、議席番号、source URL |
| `bill_source_documents` | 原案・概要・付託表などのリンク | bill FK、document kind、URL、公開範囲、利用可否 |
| `bill_minutes_links` | 許諾範囲の会議録リンク | bill FK、UNID、完全 href、relation kind、confidence、review state |

`bill_source_observations` に保存する raw は、照合に必要な番号、件名、日付、結果、
票記号などの限定した field である。取得 HTML / PDF 全体を DB や Git に保存する設計には
しない。

`source_record_key` は nullable column と通常の `UNIQUE` 制約で追加する。partial unique
index は Supabase/PostgREST の `ON CONFLICT` 推論に安定して使えない。PostgreSQL の通常
`UNIQUE` でも null 同士は重複扱いにならないため、既存・手入力 record を壊さず、
取り込み record だけ `.upsert(..., { onConflict: "source_record_key" })` へ移行できる。

### source key の二段階移行

1. nullable `source_record_key` と通常の UNIQUE 制約を追加する。旧 unique constraint は残す
2. Numazu writer が `numazu-city:` で始まる key を書くようにし、既存取り込み行を backfill する
3. 生成型、Admin、Web、open-data API、AI explainer を更新し、旧経路の回帰テストを通す
4. backfill 対象の Numazu 自動取り込み行では null、重複、二重作成がないことを DB で監査する
5. 全 import upsert を source key へ切り替えてから
   `bills_session_bill_number_key` を別 migration で drop する
6. その後に Shizuoka の同会期・同番号・別区分 fixture を投入する

同じ migration で key 追加、backfill、writer 切替、旧制約削除を完結させない。段階間で
Numazu staging の読み書きと rollback 手順を確認し、運用中サイトへの影響範囲を限定する。

## 10. 取り込み algorithm

1. 許可された入口だけを低頻度・逐次で取得する
2. host ごとに同時実行1、保守的な初期値として2秒以上/req、30req/min以下にする
3. 429、503、WAF 応答時は指数 backoff し、その run を fail closed で停止する
4. body size、Content-Type、文字コード、必須見出し、table 数に上限と契約を置く
5. HTML と PDF をそれぞれ parse し、raw record を source 別に保持する
6. page ID、section、番号、保存済み alias などを evidence として照合する
7. 値が一致すれば canonical record を upsert する
8. 不一致、未知の記号、重複 key、行数の急変は公開せず review queue へ送る
9. 公式 source から行が消えても即 delete せず、`missing_since` を記録して確認する
10. 同一入力を2回処理して DB 状態が変わらないことを検証する
11. Admin の既存公開経路で差分確認と承認を行った後にのみ `publish_status` を
    `published` にする。`published_at` は提出日と同期する legacy field であり、公開制御に使わない

県が公表した取得上限は確認できていない。上記頻度は許諾を意味せず、確認前の
保守的な提案である。県から指定を受けた場合はその値を優先する。

## 11. テストと受入条件

### parser fixture

- `第96号議案` と `第96号` を同じ normalized number にする
- 知事・議員・委員会提出の同じ `第1号` を別 record にする
- 番号なしの意見書、決議、決算を安定 key で再取り込みできる
- `第3号（その1〜3）` を枝番ごとに分ける
- `〇`、`○`、`◯` を賛成として正規化し raw mark を保存する
- `×`、`欠`、空欄、未知文字を区別する
- 個人列と会派列を正しく判別する
- 全議員の白票・青票を議席番号付き actor records にする
- 結果列が2列ある決算を `decision` と `agreement` に分ける
- `decision` / `agreement` の全対応表と `other` / `unknown` / `null` を表駆動で検証する
- HTML / PDF 不一致を上書きせず conflict にする
- 番号なし文書の件名・議決日訂正でも永続 key を維持し、新旧 fingerprint を alias にする
- 番号なし文書の未知 fingerprint、複数候補、alias collision は自動 insert せずレビューへ送る
- 見出し内改行、全角・半角空白、NBSP、表の分割に耐える
- 必須列欠損や未知 section では silent success せず fail closed にする

fixture は公式 HTML / PDF の複製ではなく、確認した DOM と値の種類だけを再現した
最小の合成データにする。実 source に対する smoke test は明示実行・低頻度とし、CI から
毎回アクセスしない。

正規化と照合は副作用のない関数に分離し、リポジトリ規約どおり `utils/` の対象 file と
同階層の `*.test.ts` で表駆動テストを行う。network client、時計、待機処理は DI し、
429 / 503 / WAF、指数 backoff、body 上限、Content-Type、CP932 decode、必須構造の変化、
行消失、承認前の公開拒否を外部 site へ接続しないテストで検証する。

### schema / repository

次は local Supabase を実際に起動・reset する統合テストで確認する。repository test も
mock client ではなく local DB に接続する。

- 既存 Numazu fixture と seed が変更前と同じ件数・値になる
- 既存 `bill_submitter=mayor` と `faction_votes` を読み書きできる
- backfill 対象の Numazu 自動取り込み行では source key に null と重複がない
- Shizuoka の同会期・同番号・別提出区分を同時に保存できる
- actor が faction / member のどちらでも保存でき、snapshot 名が残る
- 同じ normalized records の2回投入が完全に冪等である
- source conflict と unknown vote は公開状態にならない
- source key の一意制約、段階的 backfill、冪等 upsert、alias collision を実 DB で検証する
- 新しい source observation / alias / vote table は RLS を有効化し、policy は定義しない。
  anon / authenticated はデフォルト全拒否とし、server 側の `createAdminClient()` だけが扱う

### 全体 gate

- `pnpm lint`
- `pnpm typecheck`
- `pnpm build`
- `pnpm test`
- DB reset と Supabase 生成型の差分確認
- deploy / Vercel / production workflow 設定に意図しない差分がないことを diff で確認する
- Numazu fixture と local DB 統合テストで既存件数・値・読み書きの回帰がないこと
- Numazu staging で主要画面と既存 ingest の smoke test を行うこと
- production promotion 前に migration、環境変数、対象 branch、rollback 手順を再確認すること
- `SITE_ID` 未指定では従来どおり Numazu、未知 ID では起動失敗すること
- Numazu では「市長／市民」、静岡県では「知事／県民」と表示すること
- 静岡県 profile は準備完了条件を満たすまで runtime で拒否されること

## 12. 推奨 PR 分割

1. **調査文書**: 本文書のみ。実取得・schema 変更なし
2. **共通入力契約**: provenance、source record、result、vote actor の型と合成 fixture
3. **後方互換 migration**: `governor`、source key、新 vote model、生成型、Numazu backfill
4. **repository / read model**: 新旧 vote model の compatibility と idempotent upsert
5. **静岡県 parser**: 17会期の構造を覆う合成 fixture。network client は無効
6. **連絡結果の記録**: 県の回答、許容範囲、頻度、User-Agent、見直し期限
7. **限定 network ingest**: 合意範囲だけを opt-in で有効化、Admin 差分確認まで
8. **会議録リンク**: 許諾内容に応じて限定メタデータと公式 URL を追加
9. **公開準備**: 実データ検証後に seed readiness と profile guard を解除

各 PR は `develop` から分岐して `develop` へ戻す。`sites/shizuoka-pref/develop` へは、
共通 CI と沼津市後方互換確認後に promotion する。site branch へ parser や migration を
直接追加しない。

## 13. 再現コマンド

次は調査時に利用した読み取り専用の例である。実運用 crawler の許可を意味しない。

```bash
# 議案結果の header
curl -fsSI 'https://www.pref.shizuoka.jp/kensei/kengikai/gikaiugoki/1003742/1082496/1083206.html'

# 本会議の先頭カテゴリだけを展開し、CP932 として読む
curl -fsSL --compressed \
  'https://www2.pref.shizuoka.jp/all/ggiji.nsf/WebView1?OpenView&Start=1&Count=30&Expand=1' \
  | iconv -f CP932 -t UTF-8

# 会議録 DB の validator
curl -fsSI 'https://www2.pref.shizuoka.jp/all/comgiji.nsf/WebView1?OpenView'

# 同 origin の robots.txt が404であることを確認
curl -sS -o /dev/null -w '%{http_code}\n' \
  'https://www2.pref.shizuoka.jp/robots.txt'

# 県オープンデータの公式 dataset 一覧
curl -fsSL 'https://opendata.pref.shizuoka.jp/api/package_list'
```

県への確認結果が記録されるまで作成・有効化しない。
