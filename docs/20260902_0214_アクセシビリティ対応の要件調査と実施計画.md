## 0. この文書の位置づけ

「WCAG の最新版への適合」と「VoiceOver による操作の最適化」に向けた、要件の調査・現状分析・実施計画をまとめる。実装はこの文書の合意後に着手する。

**重要な前置き**: 本書の「適合/不適合」は、記載した対象・範囲・証拠に基づく**自己評価**である。第三者認証でも、組織としての正式な適合表明でもない。正式な表明には人間のレビュワーによる全項目の検証が別途必要（→ 6章）。

## 1. 適合すべき基準の整理

### 1.1 WCAG の「最新版」とは何か

| 版 | 位置づけ | 本プロジェクトでの扱い |
| :-- | :-- | :-- |
| WCAG 2.0 | 2008年勧告。JIS X 8341-3:2016 の技術的内容と一致 | 下限。JIS 経由で公共分野の実質的な要求水準 |
| WCAG 2.1 | 2018年勧告。モバイル・ロービジョン・認知の17項目を追加 | 2.2 に包含される |
| **WCAG 2.2** | **2023年10月勧告。現行の最新勧告** | **本計画の目標。レベルAA** |
| WCAG 3.0 | 草案（Working Draft）。勧告化の時期未定 | 対象外。安定していないため適合対象にしない |

**結論: 目標は WCAG 2.2 レベル AA。**

WCAG 2.2 は 2.1 に9項目を追加し、1項目（4.1.1 構文解析）を廃止した。2.1 からの追加分のうち AA は以下6項目で、いずれも本サービスに関係する:

- 2.4.11 Focus Not Obscured (Minimum) — 固定ヘッダーがフォーカス中の要素を隠さない
- 2.5.7 Dragging Movements — ドラッグ以外の手段を用意する
- 2.5.8 Target Size (Minimum) — タップ領域 24×24 CSS px 以上
- 3.2.6 Consistent Help — ヘルプの導線を一貫した位置に置く
- 3.3.7 Redundant Entry — 同じ情報を再入力させない
- 3.3.8 Accessible Authentication (Minimum) — 認知機能テストに頼らない認証

（2.4.12 Focus Not Obscured (Enhanced)、2.4.13 Focus Appearance、3.3.9 は AAA のため対象外。ただし 2.4.13 は実用上重要なので参考として扱う。）

### 1.2 日本の公共分野で追加的に求められる水準

本サービスは沼津市議会の情報を市民に届けるもので、公共性が高い。以下を併せて満たす前提で設計する。

- **JIS X 8341-3:2016**（高齢者・障害者等配慮設計指針—情報通信における機器,ソフトウェア及びサービス—第3部:ウェブコンテンツ）
  技術的内容は WCAG 2.0 と一致。**WCAG 2.2 AA を満たせば自動的に満たす**。
- **総務省「みんなの公共サイト運用ガイドライン」**
  公的機関に JIS X 8341-3:2016 の**レベル AA 準拠**を求める。準拠の表明には試験結果の公開が必要。
- **障害者差別解消法**
  民間事業者にも合理的配慮の提供が義務。運営主体が民間でも配慮義務は生じる。

**運営主体が未確定**（`docs/20260901_2220_沼津市向けブランディング対応状況.md` 参照）のため、「準拠」を公式表明するかは公開時に判断する。技術水準は表明の有無にかかわらず AA を目指す。

### 1.3 本サービス固有の考慮

議会情報を「あらゆる沼津市民が理解できる」ことが目的なので、達成基準を満たすこと自体より、以下の利用者が実際に使えるかを軸に据える。

- スクリーンリーダー利用者（VoiceOver / NVDA / TalkBack）
- ロービジョン・色覚特性のある利用者（拡大、コントラスト）
- 高齢の利用者（タップ領域、文字サイズ、専門用語）
- 認知・学習に困難のある利用者（既存の「ふつう/くわしい」難易度切替はこの層への配慮として既に有効）

## 2. VoiceOver 検証環境の調査結果

### 2.1 結論: iOS Simulator で VoiceOver の操作テストはできる

当初「Simulator では VoiceOver は動かない」と判断したが、**誤りだった**。設定値を書くだけでは起動しないが、サービスを明示的に起動すれば動く。実地に確認した手順を残す。

```bash
D=<UDID>

# 1. 設定値を立てる（これだけでは起動しない）
xcrun simctl spawn $D defaults write com.apple.Accessibility VoiceOverTouchEnabled -int 1

# 2. VoiceOver 本体を起動する。ここが要点
xcrun simctl spawn $D launchctl kickstart -p system/com.apple.VoiceOverTouch

# 3. 起動を確認（PID が付いていれば動いている）
xcrun simctl spawn $D launchctl list | grep -i voiceover
  → 68179  0  com.apple.VoiceOverTouch
```

起動すると「VoiceOverジェスチャ」の案内ダイアログが出て、以降は**画面上に VoiceOver カーソル（黒い枠）が表示され、要素を送るたびに移動する**ことをスクリーンショットで確認した。

当初 `launchctl list` で PID が `-` だったのを「起動できない」と読み違えた。これは on-demand のサービスが待機している状態であって、起動できないことを意味しない。

### 2.2 Simulator を CLI から直接操作する

GUI 自動化（osascript の `click at`）は macOS の「アクセシビリティ」権限が要るうえ、スクリーンショットを挟む操作は遅い。**`idb`（iOS Development Bridge）を使うとコマンドラインから直接操作でき、権限も不要**。

```bash
brew tap facebook/fb && brew trust facebook/fb && brew install idb-companion
python3 -m venv idbenv && ./idbenv/bin/pip install fb-idb
```

VoiceOver のキーボード操作は Control+Option（VOキー）＋キーで行う。HID キーコードで送る。

```bash
IDB=./idbenv/bin/idb

# 次の要素へ（VO + →）。HID: → = 79
$IDB ui key 79 --control --option --udid $D

# 前の要素へ（VO + ←）。HID: ← = 80
$IDB ui key 80 --control --option --udid $D

# 実行（VO + Space）。HID: Space = 44
$IDB ui key 44 --control --option --udid $D

# タップ・ダブルタップ・スワイプ・テキスト入力
$IDB ui tap X Y --udid $D
$IDB ui multi-tap X Y --udid $D
$IDB ui text "予算" --udid $D
```

`idb ui describe-all` でアクセシビリティツリーも取れるが、**Safari のクロム（アドレス欄・ツールバー）までで、WebView 内のコンテンツは辿れない**（実測: 要素6件のみ）。Web の要素については DOM 側から算出した方が確実（→ 2.3）。

### 2.2.1 読み上げ文字列をどう確かめるか

VoiceOver の音声そのものは取得できない。次のいずれかで代替する。

- **DOM から算出**（推奨・自動化可）: Web コンテンツの読み上げ名はブラウザが DOM から仕様どおりに算出する。`aria-label` → 内包テキスト、の順で決まるので、DOM を見れば読み上げ内容が分かる。実際にこの方法で 3.6 の所見を得た
- **キャプションパネル**: VoiceOver の設定でキャプションパネルを有効にすると読み上げ文字列が画面に出る。ただし `defaults write` では反映されず、シミュレータの設定アプリから操作する必要がある（未実施）

### 2.3 したがって検証は4層に分ける

| 層 | 手段 | 何を検証するか | 自動化 |
| :-- | :-- | :-- | :-- |
| **L1 静的** | axe-core（Playwright / vitest） | 機械判定できる違反（コントラスト、ラベル欠落、見出し順、ARIA誤用） | CI で自動 |
| **L2 ツリー** | DOM から読み上げ名を算出 / Accessibility Inspector | 要素の名前・役割・値。読み上げ内容の元データ | CI で自動 |
| **L3 実操作** | **Simulator + VoiceOver（idb 経由）** | 読み上げ順、要素のまとまり、操作が効くか | idb でスクリプト化可 |
| **L4 実機** | 実機 iPhone + VoiceOver | 実際の音声、ジェスチャ、ローター、使い勝手 | 手動 |

L3 まで Simulator で自動化できる。**L4（実際の音声とジェスチャ操作）だけは実機が要る**。macOS Safari + VoiceOver も同じ WebKit 系なので L4 の一次近似になる。

### 2.4 環境整備で発生した問題（記録）

Simulator が起動しなかった。原因と対処を残す。

- **症状**: `xcrun simctl create` が `Device was allocated but was stuck in creation state` で失敗
- **原因**: `~/Library/Developer` が外付けSSD（`/Volumes/ExSSD`）へのシンボリックリンクで、`CoreSimulatorService` が当該ボリュームに書き込めない（`NSCocoaErrorDomain Code=513 "You don't have permission"`）。macOS の TCC によるリムーバブルボリューム保護と見られる
- **効かなかった対処**: Xcode / Simulator.app へのフルディスクアクセス付与。**実際に書き込むのは `CoreSimulatorService` という XPC デーモンで、これらの許可を継承しない**
- **有効だった対処**: デバイス保存先だけを内蔵ディスクへ退避
  ```bash
  BASE=/Volumes/ExSSD/MigratedData/Library/Developer/CoreSimulator
  mv "$BASE/Devices" "$BASE/Devices.old"      # 既存15GBは削除せず残す
  mkdir -p ~/Library/CoreSimulatorDevices
  ln -s ~/Library/CoreSimulatorDevices "$BASE/Devices"
  ```
  DerivedData(16GB) と Xcode(20GB) は外付けのまま。戻す場合はリンクを削除して `Devices.old` を `Devices` に戻す。

### 3.6 VoiceOver で実際に操作して分かったこと

Simulator の VoiceOver で `/bills` を要素送りし、あわせて読み上げ名を DOM から算出して突き合わせた。

| # | 事象 | 根拠 |
| :-- | :-- | :-- |
| **V-1** | **絞り込みチップの件数が数字だけで読まれる。** 「審議中0」「可決78」と読み上げられ、数字が件数だと伝わらない。目で見れば数字は小さく別色で件数と分かるが、その手がかりは音声に残らない。「否決0」は「否決された議案は0件」なのか「否決」という項目なのか判別できない | DOM のテキスト連結を確認。`<a>` 内が「審議中」＋「0」で、区切りも単位も無い |
| **V-2** | **選択中のチップに `aria-current="true"` を使っている。** VoiceOver は「現在の項目」と読む。`aria-current` は本来「現在のページ／手順」を示すもので、絞り込みの選択状態には `aria-pressed`（トグルボタン）が適切 | 同上 |
| **V-3** | **`role="checkbox"` のリンクは Space で切り替わらない。** 実体が `<a href>` でキーハンドラを持たないため、Space はブラウザ既定のスクロールに落ちる。VoiceOver 利用者はチェックボックスと案内されたうえで Space が効かず、代わりに画面が飛ぶ | コード上 `next/link` にキー処理なし。実操作でも Space 押下でページがスクロールした |
| **V-4** | ページ送りは適切に読まれる。`aria-label="ページ送り"`、各リンクが「1ページ目」「次のページ」 | DOM 確認 |
| **V-5** | 検索欄は `aria-label="議案を検索"` だが可視ラベルが無く、プレースホルダは「議案名やキーワードで探す」。音声上のラベルと見た目のラベルが一致しない（2.5.3 の論点） | DOM 確認 |

V-1 は監査の指摘に含まれていなかったもので、**一覧の絞り込みという中心機能に関わるため優先度は高い**。

## 4. 実施計画

### フェーズ1: 機械判定できる不適合の是正（優先）

小さく確実に効く。既存コンポーネントの修正のみで、設計変更を伴わない。

| 項目 | 対応 | 影響範囲 |
| :-- | :-- | :-- |
| A-1 / A-2 | `--color-mirai-text-muted` を 4.5:1 を満たす色（#6b6b70 前後）へ。`--color-mirai-text-placeholder` も同様。あるいは用途を大きい文字専用に分離 | globals.css のトークン変更。使用箇所が広いので目視確認が要る |
| A-3 / A-4 | トップページに `h1` を追加（視覚的に控えめでも可）。会期カードに見出しを付与 | 2ファイル |
| A-5 | `#featured` に `scroll-mt-*` を付与。可能ならグローバルに `scroll-padding-top` | 1〜2ファイル |
| A-6 / A-7 / V-3 | 「受付中のみ表示」を本物の `input[type=checkbox]` + ラベルにする（`role` の付け替えより確実で、Space キー・タップ領域・読み上げが同時に解決する） | 1ファイル。Client Component 化が必要 |
| A-8 | 件数表示を含むコンテナに `aria-live="polite"` を常時付与 | 1ファイル |
| B-1 | `Button` の `outline-none` を外すか、リングを 3:1 以上にする | 全ページに影響。要目視確認 |
| 3.5 | パンくずに `aria-label="パンくずリスト"`、`ol/li` 化、最終項目に `aria-current="page"` | 1ファイル |
| V-1 | チップに件数の単位を伝える読み上げ名を与える（例: `aria-label="審議中 0件"`）。数字だけの読み上げをやめる | 2ファイル |
| V-2 | 絞り込みチップの選択状態を `aria-current` から `aria-pressed` へ | 2ファイル |
| 2.4.1 | スキップリンクを追加（`main` へ） | レイアウト1ファイル |

#### フェーズ1で持ち込んだ副作用（要判断）

「AIインタビュー受付中のみ表示」を `input[type=checkbox]` にしたことで、切り替えに
JavaScript が要るようになった。以前はリンクだったので JS 無しでも絞り込めた。
ステータスとカテゴリのチップはリンクのままなので、この1つだけ挙動が異なる。

JS 無しでの絞り込みを保つなら、GET フォームで囲み、他の絞り込みを hidden で
持たせて `onChange` で送信する形にできる（同じページの検索フォームが既にこの
作りになっている）。対応するかは、JS 無しの利用をどこまで支えるかの判断次第。

### フェーズ2: 検証の自動化（回帰させない仕組み）

フェーズ1の是正が壊れないようにする。**先に入れておくとフェーズ1の検証にも使える**ので、実際は1と並行で着手したい。

- `axe-core` を導入し、主要画面（`/`, `/bills`, `/bills/{id}`, インタビューLP、レポート）に対する自動チェックを CI に追加
- コントラストは**トークン単位のユニットテスト**にする。globals.css の値を読んで比を計算し、閾値を割ったら落とす。色を変えたときに気づける（今回の配色変更のような場面で効く）
- ページ単位の axe 実行は Playwright を新規導入するか、既存の vitest + jsdom で完結させるかを比較して決める（jsdom は CSS を評価しないためコントラスト検査に向かない点に注意）

### フェーズ3: スクリーンリーダーでの実地検証

自動チェックでは「読み上げて意味が通るか」は判定できない。ここは人が確認する。

1. **L2（Simulator + Accessibility Inspector）**: 主要画面のツリーを検査し、名前・役割・値が意図どおりか確認。自動監査機能も併用
2. **L3（実機 iPhone + VoiceOver）**: 以下のシナリオを通しで操作
   - トップから議案を探して詳細を読む
   - 一覧の絞り込み（ステータス・カテゴリ・受付中のみ）とページ送り
   - AIインタビューの開始から回答、公開同意まで
   - AIチャットでの質問
3. **macOS Safari + VoiceOver**: 実機が用意できるまでの一次近似として使う

検証項目は「読み上げ順が視覚順と一致するか」「操作後に何が起きたか伝わるか」「議案番号・和暦・専門用語が正しく読まれるか」を重視する。**議会用語の読み上げ**（例:「議第63号」「専決処分」「認第31号」）は本サービス固有の論点で、必要なら `aria-label` で読みを補う。

### フェーズ4: 継続的な体制

- 是正内容と検証結果を記録し、公開時に「アクセシビリティ方針」ページとして出せる形にする（みんなの公共サイト運用ガイドラインが求める試験結果の公開に対応）
- 新規 UI 追加時のチェックリストを `AGENTS.md` に追加
