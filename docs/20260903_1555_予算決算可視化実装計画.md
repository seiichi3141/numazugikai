## 1. 結論

最初に実装するべきなのは、網羅的な「財政ダッシュボード」ではなく、
**予算案が提出され、可決された金額が年度中にどう変わり、決算としていくら執行され、
市議会がどう認定したか**を同一画面で追える機能である。

優先順位は次のとおりとする。

1. **一般会計の予算・決算ライフサイクル**
   - 当初予算、補正予算、基準日付きの現計予算または予算現額、決算額を混同せず表示する。
   - 各段階を該当する予算議案・決算認定議案へ結ぶ。
2. **議会費の内訳と推移**
   - 市議会そのものに使われる金額を、一般会計全体との比率、前年度比、予算対決算で示す。
3. **主要施策・主要建設事業の予算対決算**
   - 市民が関心を持ちやすい事業を、担当部局、財源、執行率、関連議案・審査と結ぶ。
4. **普通会計の財政指標と類似団体比較**
   - 財政状況資料集の Excel を使い、経常収支比率、実質公債費比率、基金、
     住民1人当たり費用等を比較する。ただし一般会計とは別画面・別スコープにする。
5. **地方公会計・固定資産**
   - ストック、減価償却、施設を扱う独立したテーマとして後続実装する。

沼津市公式サイトには、予算・決算の概要、主要施策報告、財政状況資料集、
地方公会計財務書類、固定資産一覧、議案審議結果がある。十分に可視化へ使える一方、
主な資料は PDF、Excel、旧形式の `.xls` であり、共通の事業 ID はない。
したがって、**出典の版を固定し、会計範囲と金額段階を正規化し、検算後に公開する**
取り込み基盤が先に必要になる。

## 2. 目的

### 2.1 利用者に提供する価値

- 市民が「市のお金はいくらで、何に使われたか」を単位や会計用語で迷わず読める。
- 市民、記者、議員、議会事務局が、数字から関連する予算案、補正予算案、決算認定、
  委員会審査へ移動できる。
- 予算と決算、一般会計と普通会計、計画値と実績値を取り違えず比較できる。
- すべての数字について、出典、対象年度、会計範囲、基準日、取得日を確認できる。
- PDF の表を読み解けない利用者にも、要約、表、グラフ、ダウンロードデータを
  同等の内容で提供する。

### 2.2 本サービスで扱う意味

本機能は沼津市や沼津市議会の公式見解を示すものではない。
公式資料にある事実を独自のデータモデルへ再構成し、
議案情報と結び付けて理解を助ける非公式サービスである。
金額の評価や政策効果を自動的に断定せず、出典へ戻れることを最優先にする。

## 3. 利用者の問い

初期画面とデータ API は、少なくとも次の問いに答えられるようにする。

### 3.1 市全体

- この年度の一般会計当初予算はいくらか。前年度からいくら増減したか。
- 一般会計、特別会計、公営企業会計はそれぞれ何を指し、単純合算できる数字か。
- 歳出は目的別に何へ配分され、構成比はどうなっているか。
- 年度中の補正で、どの会計・分野がいくら増減したか。
- 期末の予算現額に対して、決算の支出済額はいくらで、執行率は何パーセントか。
- 数年で増減した分野はどこか。分類変更の影響はないか。

### 3.2 市議会との関係

- その当初予算・補正予算・決算は、何年度の何号議案か。
- 提出日、付託委員会、議決日、議決結果、決算の認定状況はどうなっているか。
- 委員会の委員発言ブロック数はいくつで、本会議で討論があったか。
- 議会が原案どおり可決したのか、修正・否決・継続審査等だったのか。
- 決算額が公表されていても、まだ議会の認定前ではないか。

### 3.3 議会費

- 議会費はいくらで、一般会計歳出の何パーセントか。
- 人件費、物件費、政務活動費等の内訳はいくらか。
- 当初予算、最終的な予算現額、決算額の差はどの程度か。
- 過去数年で議会費と住民1人当たり議会費はどう変わったか。

### 3.4 比較・評価

- 沼津市の財政指標は、類似団体平均、県内自治体、自市の過去と比べてどうか。
- 住民1人当たり額の分母は、どの時点のどの人口か。
- 主要施策は予算どおり執行されたか。成果指標との関係はどうか。

最後の問いは、支出額だけでは政策効果を判断できない。
成果指標、行政評価、統計・調査を接続するまでは、
「執行率が高いから成果が高い」といった因果的な表現をしない。

## 4. 対象範囲

### 4.1 初期リリースの対象

- 令和6年度（2024年度）の一般会計について、当初予算、年度末の予算現額、決算を表示する。
- 令和8年度（2026年度）の一般会計当初予算を表示し、議第39号へ結ぶ。
- 上記年度の議会費について、公式資料で確認できる内訳、予算、決算を表示する。
- 一般会計の目的別歳出を、公式資料と同じ階層・名称で表示する。
- すべての金額に、年度、会計、段階、単位、基準日、出典を付ける。
- 予算・決算イベントを既存の `bills` と結び、議案詳細側にも財政パネルを表示する。
- CSV または JSON で、画面と同じ構造化済み事実データを取得できるようにする。

間の年度が揃うまでは2点を連続した時系列グラフで結ばない。

### 4.2 後続フェーズの対象

- 特別会計、公営企業会計の予算・決算。ただし収益的収支と資本的収支を分ける。
- 主要施策、主要建設事業、財源内訳、担当部局。
- 財政状況資料集の普通会計指標、類似団体比較、5年推移。
- 地方公会計の貸借対照表、行政コスト計算書、純資産変動計算書、資金収支計算書。
- 固定資産一覧の施設単位への集約と地理可視化。
- 監査委員の決算審査意見との接続。
- 人口統計を使った住民1人当たり額、物価調整済みの長期比較。

### 4.3 対象外

- 公開されていない予算書・決算書の款項目節すべてを推測して復元すること。
- 支払先、個別伝票、契約相手など、公式資料にない取引明細。
- 予算額だけから政策の良否、無駄、議員・会派の評価を自動判定すること。
- 議会だより、予算概要、決算報告、財務書類 PDF の丸ごとの再配布。
- 共通 ID のない事業を名称だけで自動確定し、誤った議案・施策へ結ぶこと。
- 起債残高時計の補間値を実績値として保存すること。
- 長期財政推計を将来の確定額として表示すること。

### 5.3 著作権・利用条件

[沼津市ホームページの著作権表示](https://www.city.numazu.shizuoka.jp/about/copyright.htm)
は、私的使用・引用の範囲を超える利用や転載等を制限する旨を掲げている。
財政ページには調査時点で CC BY 等の明示的なオープンライセンスを確認できなかった。

一般に、単なる予算額、決算額、議案番号、日付等の事実は著作物性が
認められにくい一方、個別資料の選択・構成、解説文、図版、紙面全体は
保護対象となり得る。本計画だけで個別資料の法的な利用可否を断定せず、実装では次を守る。

- 原 PDF・Excel の紙面や図を公開サイトから再配布しない。公式 URL へリンクする。
- 数値と事実を自前のスキーマ、表、グラフへ再構成し、出典を必ず表示する。
- 原文を引用する場合は必要最小限とし、引用部分、主従関係、出所を明確にする。
- parser由来の値を公開根拠にする原本スナップショットは、非公開ストレージへ不変
  オブジェクトとして保持し、最小権限、保存期間、削除監査を定める。保持できない資料は
  parser根拠のまま公開せず、公式URLを用いたmanual確認等の別根拠へ切り替える。原本は
  公開配布しない。
- `.xls`、`.xlsx`、PDF の継続利用について、市の担当課へ用途を並行して共有し、
  オープンデータ化または明示的な二次利用条件を提案する。回答の有無だけを構造化した
  事実データの公開条件にはせず、条件が不明な原本・紙面は再配布しない。
- 法的整理は既存文書を参照しつつ、公開前に専門家または権利者へ確認する。

## 6. 会計・金額段階の定義

### 6.1 年度

- DB の `fiscal_year` は**年度が始まる西暦年**を整数で持つ。
  令和8年度は `2026`、対象期間は2026-04-01から2027-03-31までである。
- 資料 URL の年、資料の公表年、会計年度、取得年を同じフィールドに入れない。
- `published_at`（公式公表日時）、`as_of_date`（数字の基準日）、
  `fetched_at`（本サービス取得日時）を別々に持つ。

### 6.2 会計範囲

| 区分 | この計画での厳密な扱い | 比較・合算ルール |
| :-- | :-- | :-- |
| **一般会計** | 市の基本的な行政サービスを経理する法定の会計。`account_type=general` | 同一年度・同一段階の一般会計同士だけを直接比較する |
| **特別会計** | 特定事業・特定収入について一般会計と分けて経理する会計。会計ごとに `account_code` を持つ | 一般会計からの繰入等を含むため、単純合算時は内部取引の重複を注記する |
| **公営企業会計** | 地方公営企業法等に基づく発生主義・複式簿記の会計 | 収益的収入・支出と資本的収入・支出を別系列にする。一般会計の歳入歳出と同じ棒に積まない |
| **普通会計** | 地方公共団体間比較のため総務省の基準で組み替える**統計上の会計範囲**。法定の一つの会計ではない | `account_type` にせず `reporting_scope=ordinary` とする。一般会計との差を誤差扱いせず、議案へ直接結ばない |
| **一般会計等** | 地方公会計の財務書類で使う範囲 | 予算・決算の「一般会計」と同一と仮定しない。資料の連結範囲を表示する |
| **全体・連結** | 地方公会計で特別会計、企業会計、関係団体等を段階的に含めた範囲 | 内部取引消去後の公会計値であり、各会計予算の単純合計と比較しない |

画面では会計範囲を常時表示し、普通会計には
「自治体比較用に組み替えた統計上の区分で、一般会計とは一致しません」と説明を付ける。

### 6.3 当初・補正・現計・予算現額・決算・認定

金額の段階と市議会の意思決定状態を直交する二軸として保存する。

| 用語 | 金額としての定義 | 市議会との関係 | 実装上の表現 |
| :-- | :-- | :-- | :-- |
| **当初予算案** | 年度開始前を基本として市長が最初に提出する予算案の額 | 未議決なら提案値であり確定予算ではない | `event_kind=initial_budget`、`decision_stage=proposed` |
| **当初予算** | 当初予算案が可決された時点の額 | 原案可決、修正可決等の結果と議決日を保持 | 同じイベントに `decision_stage=passed` を追加する。修正時も提案額と可決後額を別の金額セットで持つ |
| **補正予算案** | 可決済み予算へ年度途中に加える増額または減額の変更案 | 補正ごとに別議案。未可決は現計へ算入しない | `event_kind=supplementary_budget`、`decision_stage=proposed`、`supplement_sequence` 必須。減額は負の整数 |
| **補正予算** | 可決された補正の増減額 | 議決後だけ可決済み系列へ算入 | 同じイベントに `decision_stage=passed` を追加する。補正後総額が資料にある場合は増減額と別 `measure` にする |
| **現計予算額** | ある基準日時点の当初予算と可決済み補正予算を反映した現在額 | 審議中の補正案は含めない | `event_kind=current_snapshot`、`decision_stage=not_applicable`、`as_of_date` 必須。出典の定義どおりに保存する |
| **予算現額** | 決算・執行管理で使う執行可能額。資料によって当初・補正に加え、繰越額、流用・予備費充用等を含み得る | 個々の構成要素がすべて議案になるとは限らない | `event_kind=available_budget_snapshot`、`decision_stage=not_applicable` として現計と分離。原資料の表題と構成項目を保持する |
| **決算額** | 年度終了後の収入済額・支出済額等の実績値 | 市長が監査委員の審査を経て議会へ提出する。認定前でも会計実績そのものは存在する | `event_kind=settlement`、`decision_stage=not_applicable`。歳入・歳出、収益・費用等の `measure` を必ず付ける |
| **認定** | 決算について市議会が行う議決結果であり、別の金額段階ではない | `認定`、`不認定`、`継続審査`等を表す。提出前は「議会認定前」、提出後の審査中は「認定審査中」と表示 | 既存 `bills.status` とイベントへの関連付けで表現し、決算額を複製・上書きしない |

「現計予算額」と「予算現額」は自治体資料によって表記・範囲が揺れる。
パーサーが名称から推定して統合せず、資料ごとの定義を source profile として設定する。
構成が判別できない場合は `source_label` をそのまま保存し、公開前レビュー対象にする。

### 6.4 金額、単位、丸め、`null` と `0`

- 正規化金額は PostgreSQL `bigint` の**円単位整数** `amount_yen` とし、
  JavaScript では `number` に変換せず `bigint` または10進文字列として扱う。
- 原資料の `source_value_text`、`source_value_numeric`、`source_unit`
  （`yen`、`thousand_yen`、`million_yen`、`percent` 等）を必ず残す。
- 千円単位の `469887` は `469_887_000` 円へ正確に変換できる。
  百万円単位の小数等も10進数として変換し、二進浮動小数点を介さない。
- DB の正規値は丸めない。億円・万円等への丸めは表示層だけで行う。
- 公式資料の公表済み構成比・執行率は `published_metric_value` として保持し、
  円単位から再計算した値と並べて検算する。表示桁は公式資料に合わせる。
- `0` は、資料が明示的にゼロと示した値であり `amount_yen=0` とする。
- `null` は、未公表、該当なし、判読不能、空欄、抑制等で値を確定できない状態である。
  `null_reason` を必須にし、ゼロへ変換しない。
- `-`、空欄、`…` は資料ごとに意味が異なる。source profile で意味を確認できない限り
  `null` とし、`source_value_text` を残す。
- 補正減額、赤字、資金流出等の負値は有効な値であり、欠損扱いしない。
- 「全会計合計」は、公式資料が示す同一側の合計を採用する。
  歳入と歳出、収益的収支と資本的収支を二重に足した独自の総額を作らない。

## 7. 議案との結合

### 7.1 既存実装

現行 DB は、市議会への移行マイグレーションにより次を保持している。

- `council_sessions`: 会期、回次、期間、公式 URL。
- `bills`: 議案番号、議案番号種別、分類、提出者、付託委員会、提出日、議決日、結果。
- `bills.category`: `budget` と `settlement` を識別できる。
- `bills.status`: 現行の予算`passed`・決算`certified`・否決・継続等に加え、議案計画の
  先行migrationで本会議の不認定を表す`not_certified`を追加する。
- `bill_debates`と委員会審査の旧互換列は、討論と委員発言ブロック数相当値を保持する。
  旧互換列は移行一致テスト以外の読み取りに使わない。
- 議案には既存の`(council_session_id, bill_number)`一意制約があるが、両列はnullableである。
  議案計画の移行後は非null・一意な`canonical_bill_key`を正本識別子とする。

既存の `bill_number_kind_enum` の `nin` は「認第」の接頭辞を表し、
人事案件だけでなく決算認定にも使われる。結合時は接頭辞だけで用途を決めず、
`bills.category=settlement` と議案名も確認する。

### 7.2 推奨結合キー

既存の次の組は、自動突合の候補生成にだけ使う。

```text
(council_session_id, bill_number)
```

両列のnull、表記揺れ、既存重複候補をQAし、議案計画の
`numazu:{verified_session_slug}:{normalized_bill_number}`形式の
`canonical_bill_key`が確定した行だけを結合する。`fiscal_event_bill_link_revisions`の
published版に最終的な`bills.id`を保存し、表示時のjoinを文字列キーへ依存させない。
議案名だけでは自動確定しない。

財政イベントの自然キーは次とする。

```text
(fiscal_year, reporting_scope_id, account_id, event_kind,
 supplement_sequence, as_of_date)
```

- 当初予算、決算は `supplement_sequence=null`。
- 補正予算は議案名の「補正予算（第4回）」等を正規化し、回次を必須にする。
- スナップショット型の現計・予算現額は `as_of_date` を必須にする。
- この自然キーには PostgreSQL の `UNIQUE NULLS NOT DISTINCT` を使い、
  `account_id`、`supplement_sequence`、`as_of_date` が null の場合も重複を防ぐ。
- `fiscal_events` は年度・集計範囲・会計・イベント種別・回次・基準日という
  安定した意味だけを表す。提案・可決、訂正、出典はイベントの同一性に含めない。

財政イベントと議案は `fiscal_event_bill_links` で結ぶ。
`bill_id` を財政金額テーブルへ直接埋め込まない。これにより、一つの資料が複数議案を
説明する場合、修正案・付帯決議がある場合、決算認定と関連決議を併記する場合に対応する。

### 7.3 自動突合と人手確認

候補生成は次の順で行う。

1. 議案の `category` が予算なら `budget`、決算なら `settlement` であること。
2. 議案名から年度、正式な会計名、当初・補正・決算、補正回次を抽出する。
3. 財政イベントの `fiscal_year`、`account_id`、`event_kind`、回次と完全一致させる。
4. 会期の日付が当該イベントの提出・議決時期として矛盾しないことを確認する。
5. `bill_number`、議案名、出典 URL を管理画面で人が確認して `verified` にする。

正規化した事業名や部局名による曖昧一致は、候補提示にだけ使う。
**名称類似度だけで公開済みリンクを確定しない。**
結合レコードには `match_method`、`confidence`、`evidence_text`、
`verified_by`、`verified_at` を持たせる。

### 7.4 修正・採決の扱い

- 原案可決は提案額と可決後額が同じであることを示すが、同一レコードにせず、
  一つの `fiscal_event` に `decision_stage=proposed` と `passed` の
  `fiscal_amount_sets` を併存させる。
- 修正可決の場合、修正案の議案・動議が既存 `bills` に存在するかを確認し、
  提案額と可決後額を`proposed`と`passed`の別金額セットとして保持する。修正差額は
  `passed`セット内のdelta measureとして提案額との差を明示し、第3の議決段階を作らない。
- 否決された補正予算案は履歴として表示できるが、現計予算へは算入しない。
- 決算は `decision_stage=not_applicable` の実績金額セットを一つだけ持ち、
  認定議案の提出・審査・認定・不認定に伴って同じ金額を複製しない。
- 決算が不認定でも、確定した会計実績をゼロや未確定へ戻さない。
- 付帯決議・関連決議は `relationship=related_resolution` として金額イベントへ結ぶ。

## 8. データモデル案

### 8.1 基本方針

- 財政の法的会計、比較用スコープ、金額段階、意思決定状態を別の列・テーブルにする。
- 原資料の行と、年度間比較のための正規化分類を分ける。
- 一つの「現在値」だけでなく、取得原本、解析結果、公開版を追記型で保持する。
- `source_version_id` と `parse_run_id` の監査証跡 FK は原則
  `ON DELETE RESTRICT` とし、派生データだけが残る削除を許さない。
- 両列を持つ全テーブルは、共通基盤0Aの`ingestion_parse_runs`で定義する
  `UNIQUE (id, source_version_id)`を参照する
  `(parse_run_id, source_version_id)`の複合外部キーも持つ。解析実行と別取得版の
  誤った組合せをDBで拒否し、パーサー由来では両列を必須にする。両列がnullableな
  テーブルには`CHECK (parse_run_id is null or source_version_id is not null)`も設ける。
- 全テーブルで RLS を有効化し、ポリシーを定義せず、既存方針どおり
  `createAdminClient()` を用いたサーバー側 repository からアクセスする。
- 公開 API は公開用 view または DB function / repository で必要列だけ返す。
- 公開用 view を作る場合は `WITH (security_invoker = true)` とし、基礎テーブルと view を
  `anon` / `authenticated` へ直接 grant しない。公開値はサーバー側 repository から返す。
- DB function は原則 `SECURITY INVOKER` とする。集計上 `SECURITY DEFINER` が必要な場合は、
  固定した `search_path`、完全修飾名、`PUBLIC` / `anon` / `authenticated` からの
  `EXECUTE` revoke、`service_role` だけへの grant を migration と統合テストで確認する。

### 8.2 テーブル

#### `fiscal_accounts`

法定の会計を年度をまたいで識別する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `code` | `text` | 内部安定キー。例 `general`, `national_health_insurance` |
| `name` | `text` | 公式名称 |
| `account_type` | enum | `general` / `special` / `public_enterprise` |
| `valid_from_fiscal_year` | `smallint` | 名称・会計の有効開始年度 |
| `valid_to_fiscal_year` | `smallint null` | 廃止・改称前の最終年度 |
| `predecessor_id` | `uuid null` | 組替え・改称元。自動で同一系列とはみなさない |

`valid_to_fiscal_year is null or valid_to_fiscal_year >= valid_from_fiscal_year`をCHECKし、
`unique(code, valid_from_fiscal_year)`を設ける。さらにこのmigrationが`extensions` schemaと
`btree_gist`を作成する。`int4range(valid_from_fiscal_year,
valid_to_fiscal_year + 1, '[)')`（終了nullは上限なし）と`code`にEXCLUDE制約を設定し、
資料上の開始・終了年度を両端包含として扱う。同じcodeのopen-ended期間を含む重複を
DBで拒否し、年度から会計IDを必ず一意に
解決できるようにする。年度途中の統廃合は別途注記する。
`account_id`と`fiscal_year`を持つmembership、coverage、財政event、金額セット等の
全stable targetには共通`fiscal_account_year_guard`を適用し、
`valid_from_fiscal_year <= fiscal_year <= coalesce(valid_to_fiscal_year, infinity)`を
INSERT時とidentity変更時にDB検査する。会計期間列は子から参照された後の通常UPDATEを
不変性triggerで拒否し、期間訂正は新しい会計IDと明示的な承継関係で行う。これにより
FY2026の値をFY2020だけの会計へ結ぶ誤りを、membership経由を含め公開前に拒否する。

#### `fiscal_reporting_scopes`

`general_account`、`ordinary_account`、`public_accounting_general`、`overall`、
`consolidated` 等の集計範囲と、含まれる会計・内部取引消去の説明を持つ。
普通会計を `fiscal_accounts` に入れないためのテーブルである。

#### `fiscal_reporting_scope_memberships`

集計範囲の構成は年度と資料によって変わり得るため、スコープ本体へ固定せず、
根拠版付きの年度別 membership として保持する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `reporting_scope_id` | `uuid` | 対象の集計範囲 |
| `fiscal_year` | `smallint` | membership が有効な年度 |
| `account_id` | `uuid null` | 対応する法定会計。関係団体等は null 可 |
| `account_identity_key` | `text generated` | `coalesce(account_id::text, 'scope-only')`を`STORED`で保持する非null参照キー |
| `member_key` | `text` | 表記変更に依存しない構成主体の安定キー |

自然キーは `(reporting_scope_id, fiscal_year, member_key)` とし、空の`member_key`を拒否する。
`account_id`がある場合は
`CHECK (account_id is null or member_key = 'account:' || account_id::text)`で決定的な値を
DB保証し、さらに
`UNIQUE (reporting_scope_id, fiscal_year, account_id) WHERE account_id is not null`を設ける。
nullの関係団体等は
公式の主体同一性を人が確認してから安定キーを付ける。資料上の表記は正本キーに使わず、
観測側に残す。`included / eliminated / reference_only`の役割も資料訂正で変わり得るため
正本キーに含めず、観測側の`membership_role`へ置く。同じ年度・scope・構成主体を
役割違い・表記違いで二重作成できない。
年度が異なる membership は
別の正本行とし、`(id, reporting_scope_id, fiscal_year,
account_identity_key)`も一意にする。`account_id`を含む複合外部キーは使わず、
後述の非nullキーで参照する。これによりPostgreSQLの`MATCH SIMPLE`がnull列を含む
複合外部キー全体を検査対象外にすることを防ぐ。同じ年度・同じ構成に
対する別の根拠版や再解析結果は観測テーブルへ追記する。
これにより、一般会計等・全体・連結の範囲変更と内部取引消去を再現できるようにする。

資料内の構成主体との安定した対応は
`fiscal_reporting_scope_membership_source_occurrences`へ置く。`id`、`membership_id`、
`reporting_scope_id`、`fiscal_year`、`account_id`、`account_identity_key`、
`edition_source_occurrence_id`、
`edition_id`、`ingestion_source_id`、`source_membership_key`を持たせ、
`account_identity_key`はこの行自身の`account_id`から正本と同じ式で作る`STORED`生成列とし、
アプリケーションから別値を指定させない。
`(edition_source_occurrence_id, source_membership_key)`を対象membershipなしで一意にする。
同じ論理ソース内の同じ構成主体を、取得版や再解析のたびに別の正本へ割り当てない。

版別根拠と公開版選択は追記型の`fiscal_reporting_scope_membership_observations`へ置く。
`id`、`membership_id`、`reporting_scope_id`、`fiscal_year`、`account_id`、
`account_identity_key`、
`membership_source_occurrence_id`、`ingestion_source_id`、`source_version_id`、
`edition_observation_id`、`edition_id`、`parse_run_id`、`extraction_method`、
`membership_role`、`source_member_name`、
`display_name`、`evidence_revision`、
`source_locator`、`qa_status`、`publication_state`、`verified_by`、`verified_at`を持つ。
`account_identity_key`は正本と同じ生成式の`STORED`列とし、
`(membership_id, reporting_scope_id, fiscal_year, account_identity_key)`から
正本へ複合外部キーを張り、
別年度・別scope・別会計の根拠を誤接続できないようにする。観測側にも同じID一式の
複合一意制約を置き、金額セットrevisionから固定参照できるようにする。occurrence、
published書誌観測、
取得版、解析実行にもeditionと論理ソースを含む複合外部キーを張る。出典側の一意制約は
対象の`membership_id`を含めず、
`(membership_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。同じソース内出現を二つのmembershipへ
割り当てられない一方、差し替え取得版と再解析は別根拠として追記できる。

パーサー由来は`source_version_id`と`parse_run_id`を必須、人手根拠は取得版を必須にして
`parse_run_id=null`とし、共通の複合外部キーで取得版と解析実行の一致を保証する。
parser根拠の`evidence_revision`は1に固定し、人手で同じ取得版の解釈を訂正する場合は
同じoccurrenceの番号を増やす。
共通のQA・公開状態CHECKを適用し、membershipごとに`publication_state=published`の観測を
一つだけ許す。公開viewはpublished観測がある正本だけを返し、訂正時は旧観測を
`superseded`にしてから新観測を`published`へ切り替える。役割訂正でも正本を増やさず、
旧published観測と新draft観測を併存させてから切り替える。

#### `fiscal_source_documents`

財政資料の論理的な系列だけを表す。年度ごとに URL が変わる場合も同じ系列として扱い、
URL の同一性は既存の `ingestion_sources`、取得バイナリの版は全テーマ共通の
`ingestion_source_versions` を正本にする。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `source_kind` | enum | `budget_overview`、`execution_report`、`settlement_report`、`major_measures`、`fiscal_comparison`、`public_accounting` 等 |
| `series_code` | `text` | 年度や改訂で変わらない内部安定キー |

`title`、`fiscal_year`、公表日時等の版ごとに変わる属性は置かない。
`series_code` を一意にする。

#### `fiscal_source_document_editions`

論理資料系列の中の「令和8年度当初予算概要」等、資料として安定した版枠を表す。
同じ URL の内容差し替えは同じeditionの版別観測とし、年度違い等は別editionにする。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `fiscal_source_document_id` | `uuid` | 論理資料 |
| `edition_key` | `text` | 年度・資料種別等から人が確認した系列内安定キー |
| `created_at` | `timestamptz` | 登録日時 |

`(fiscal_source_document_id, edition_key)`と`(id, fiscal_source_document_id)`を一意にする。
取得版や解析から得た書誌値をこの行へ上書きしない。

論理ソース内の資料出現は`fiscal_source_document_edition_source_occurrences`へ置く。
`id`、`edition_id`、`fiscal_source_document_id`、`ingestion_source_id`、
`source_edition_key`を持たせ、`(ingestion_source_id, source_edition_key)`をeditionなしで
一意にする。同じ URL が差し替えられてhashが変わっても同じoccurrenceを使い、別URLの
同一editionは別occurrenceとして同じeditionへ結ぶ。候補はstagingで照合してから確定する。

書誌値と公開版選択は追記型の`fiscal_source_document_edition_observations`に置く。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `edition_id` / `fiscal_source_document_id` | `uuid` | 同じ論理資料に属するeditionを複合外部キーで保証 |
| `edition_source_occurrence_id` / `ingestion_source_id` | `uuid` | 安定した資料出現と論理ソース |
| `source_version_id` | `uuid` | この書誌値を確認した取得版 |
| `parse_run_id` | `uuid null` | 書誌情報を抽出した解析実行。人手登録ではnull |
| `observation_revision` | `integer` | 同じedition内の追記番号。1から開始 |
| `evidence_revision` | `integer` | 同じ取得版・物理根拠の人手再解釈番号。parserでは1 |
| `extraction_method` | enum | `parser` / `manual` |
| `source_locator` | `text null` | 書誌値を確認したページ、表、セル等の位置 |
| `title` | `text` | この観測で確認した公式資料名 |
| `fiscal_year` | `smallint null` | 単年度資料の対象年度。索引等は null 可 |
| `publisher` | `text` | 原則「沼津市」または「沼津市議会」 |
| `published_at` | `timestamptz null` | 公式の公表日時。取得日時とは分ける |
| `as_of_date` | `date null` | 資料内の数値の基準日 |
| `license_note` | `text null` | その版について確認した利用条件。推測しない |
| `redistribution_allowed` | `boolean null` | 明示条件がない間は null |
| `qa_status` / `publication_state` | enum | 共通のQA状態と公開版選択 |
| `verified_by` / `verified_at` | `uuid null` / `timestamptz null` | 人手確認の監査情報 |

`(edition_id, observation_revision)`を一意にし、版別根拠には対象IDを含めない
`(edition_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`を設ける。同じソース内資料出現を
別editionへ割り当てられず、同じURLの差し替え版も旧版を残して追記できる。parser/manualの
組合せ、occurrence・取得版・解析実行、共通のQA・公開状態を複合外部キーとCHECKで保証し、
editionごとのpublished観測は一つだけ許す。金額出典から安全に複合参照できるよう
`(id, edition_id, ingestion_source_id, source_version_id)`も一意にする。
書誌の訂正は旧観測を保持したまま
新観測をdraftで確認し、承認時に
同一トランザクションで公開版を切り替える。

#### 共通の `ingestion_source_versions`

財政専用の版テーブルは作らない。調査レポート9.1で定義した共通の
`ingestion_source_versions`には、取得バイナリの SHA-256、取得日時、HTTP 情報、
MIME、サイズ、取得時に観測した資料名・公表日時・基準日、任意の非公開原本キーを持たせる。
対象年度、公表者、利用条件と、人が確認した財政資料としての表題・基準日は
`fiscal_source_document_edition_observations`、パーサー名・版・設定と解析結果は
`ingestion_parse_runs` の責務とする。共通の取得時メタデータ、QA済みの財政書誌情報、
解析実行を別の記録として追跡する。

editionのsource occurrenceと版別観測を介して財政資料へ結び、同じ URL で
hash が変われば同じeditionの新しい観測、年度が変われば原則として同じ資料系列の
別editionとする。年度が同じままURLだけ変わった場合は、根拠を確認して同じeditionへ結ぶ。
旧版と過去の書誌観測は更新・削除せず、現行値はpublished観測を選ぶviewで導く。これにより、議案・一般質問・委員会と
同じ版管理、訂正監査、保持方針を利用できる。

#### 共通の `ingestion_parse_runs`

一つの `source_version_id` に対し、パーサーの変更や再解析ごとに行を追加する。
`ingestion_run_id`、`source_version_id`、`parser_name`、`parser_version`、
`configuration_hash`、`started_at`、`finished_at`、`status`、`parse_stats` を持つ。
取得バイナリが同じでもパーサー版または設定が変われば別の parse run とし、
同一の取得版・パーサー版・設定で完了済みの場合だけ再解析を省略する。

#### 財政固有のsource occurrence共通契約

membership、document edition、coverage、classification、classification mapping、
amount set、amount、indicator、bill linkの各根拠は、
安定正本と版別根拠の間に、それぞれ前述の`*_source_occurrences`を置く。occurrenceは
少なくとも対象正本ID一式、`ingestion_source_id`、資料内ローカルキーを持ち、
document edition配下では`edition_source_occurrence_id`、金額配下では親amount set
occurrenceを最小範囲として、ローカルキーとの組を**対象正本IDなし**で一意にする。
同じURLを複数年度editionで使っても相互に衝突させない。版別根拠は
`source_occurrence_id`、`ingestion_source_id`、`source_version_id`、`parse_run_id`、
`evidence_revision`を持つ。document edition観測は、これに加えて安定edition内の公開履歴を
並べる`observation_revision`を持つ。次を共通制約とする。

- `(source_occurrence_id, source_version_id, parse_run_id, evidence_revision)
  UNIQUE NULLS NOT DISTINCT`とし、manual根拠でも別取得版を追記できるようにする。
- parser根拠は`parse_run_id`必須かつ`evidence_revision=1`、manual根拠は
  `parse_run_id=null`かつ取得版・空でない根拠位置・確認者・確認日時を必須にする。
- occurrence、取得版、解析実行へ`ingestion_source_id`を含む複合外部キーを張り、
  別論理ソース・別取得版の解析結果を誤接続できないようにする。
- occurrenceの対象正本ID一式、親source occurrence、`ingestion_source_id`、ローカルキーは
  `prevent_stable_identity_update`で通常UPDATEを拒否する。版別根拠も対応先、取得版、
  解析実行、抽出内容の上書きを禁止し、QA・公開・確認情報だけを状態遷移で変更する。
- 誤突合候補はoccurrenceへ入れる前にstagingで確認し、監査対象の物理DELETEを行わない。
  例外的な対応訂正は旧新IDと公開影響を記録する専用migrationだけで扱う。

公開判定に使うparser根拠は、共通0Aの`source_artifact_consumer_types`へ財政固有の
consumer typeを登録し、`published_source_version_references`と同期する。これにより
後続の財政テーブル名を0Aの保持guardへ静的に追加せず、保持中の原本だけを公開根拠に数える。
分類revisionと年度間mapping revisionのparser根拠もこの集合に含め、差し替え時は旧参照を
releaseして新しい取得版へ同期する。

#### `fiscal_data_coverage` と `fiscal_data_coverage_observations`

金額の`null_reason`とは別に、「そもそも資料が未公表」「取得不能」「一部だけ解析済み」等を
表示・監査する。正本の`fiscal_data_coverage`は、`id`、`fiscal_year`、
`reporting_scope_id`、`account_id`（null可）、`source_kind`、`data_kind`、`as_of_date`
（null可）を持つ。`data_kind`は`document_edition / scope_membership / amount_set /
classification / classification_mapping / indicator / bill_link`等、何の充足状況かを表す。
`account_identity_key`と
`as_of_identity_key`はそれぞれnullを衝突不能な文字列へ変換する生成列とする。自然キーには
`UNIQUE NULLS NOT DISTINCT`を設定し、複合参照用に
`(id, fiscal_year, reporting_scope_id, account_identity_key, source_kind, data_kind,
as_of_identity_key)`も一意にする。

各確認時点はappend-onlyの`fiscal_data_coverage_observations`へ記録する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `coverage_id` | `uuid` | 観測の主キーと対象正本 |
| `fiscal_year` / `reporting_scope_id` | 年度 / UUID | 対象正本を固定する冗長キー |
| `account_id` / `account_identity_key` | UUID nullable / 生成text | nullを含む会計条件も複合FKで検査する |
| `source_kind` / `data_kind` | enum | 対象資料種別と充足対象。classificationとmappingも区別する |
| `as_of_date` / `as_of_identity_key` | date nullable / 生成text | 基準日条件をnullでも固定する |
| `observation_key` | `text` | 取込実行または手動監査内で決定的な冪等キー |
| `state` / `record_presence` | enum | 共通のカバレッジ状態と`present / absent / unknown` |
| `expected_count` / `matched_count` | `integer null` | 期待件数と確認件数。推測値は入れない |
| `reason_code` / `details` | `text null` | 失敗・未公開・部分取得の説明 |
| `qa_status` / `publication_state` | enum | 共通のQA状態と公開版選択 |
| `observed_at` / `reviewed_by` / `reviewed_at` | 日時・UUID | 観測と承認の監査情報 |

`(coverage_id, observation_key)`と、観測根拠から参照する
`(id, coverage_id, fiscal_year, reporting_scope_id, account_identity_key, source_kind,
data_kind, as_of_identity_key)`を一意にし、観測からcoverage正本へも同じ対象tupleの
複合外部キーを張る。非draft観測は`qa_status=verified`かつ
`reviewed_by / reviewed_at`が両方非nullの場合だけ許すCHECKを設け、未公表・取得不能・
対象外の観測も匿名の承認で公開できないようにする。

資料内で対象coverageを指す安定対応は
`fiscal_data_coverage_source_occurrences`へ置く。`id`、coverageの全対象tuple、
`edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
`source_coverage_key`を持たせる。`(edition_source_occurrence_id, source_coverage_key)`を
coverage IDなしで一意にし、一つの資料内対象を複数のscope・account・data kind・基準日へ
割り当てない。この表の`account_identity_key`と`as_of_identity_key`も、行自身の
`account_id`と`as_of_date`から正本と同じ式で作る`STORED`生成列にする。正本への対象tuple FKと、観測根拠用の
`(id, coverage_id, fiscal_year, reporting_scope_id, account_identity_key, source_kind,
data_kind, as_of_identity_key, edition_id, ingestion_source_id)`一意制約を設ける。

版別の`fiscal_data_coverage_observation_sources`は、`observation_id`、
`coverage_id`、coverageの全対象tuple、`coverage_source_occurrence_id`、
`edition_observation_id`、`edition_id`、`ingestion_source_id`、
`source_version_id`、`parse_run_id`、`evidence_revision`、`evidence_role`
（`primary / corroborating`）、`observed_presence`、`source_locator`、
`extraction_method`、`qa_status`、`verified_by`、`verified_at`を持つ。
この表でも`account_identity_key`と`as_of_identity_key`を行自身のnullable元列から作る
`STORED`生成列とし、観測やoccurrenceからキー文字列をコピー入力しない。
`(coverage_source_occurrence_id, source_version_id, parse_run_id, evidence_revision)
UNIQUE NULLS NOT DISTINCT`とし、観測・occurrence・資料出現・書誌観測・取得版・解析実行へ
対象tupleとedition・論理ソースを含む複合外部キーを張る。parser根拠は解析実行必須、
manual根拠は解析実行nullかつ取得版・空でないlocator・確認者・確認日時を必須にする。

[「沼津市議会データ可視化調査レポート」](./20260903_1555_沼津市議会データ可視化調査レポート.md)の
9.2「共通状態語彙と履歴契約」で定義した`state × record_presence`行列、
件数の非負・大小関係、QA・公開状態のCHECKをそのまま適用する。
対象ごとのpublished観測は一つだけ許す。未公表・未取得・取得不能・部分取得・解析失敗と、取得済み
資料内の金額欠損を別々に保持し、失敗観測で既存の公開金額や過去観測を削除しない。
publishedかつ`collected / partial`では`observed_at`と、対象tupleへ束縛されたverified
primary根拠を必須にし、根拠版のない「取得済み」「確認済み0件」を拒否する。根拠の
`observed_presence`は観測の`record_presence`と一致させる。参照する書誌観測は
publishedかつverifiedで、その`fiscal_year`がcoverage年度と一致し、editionから辿る
論理資料の`source_kind`もcoverageと一致することを公開guardで検査する。採用根拠では
`extraction_method`を必須にし、parserなら同じ取得版のcompleted parse run、manualなら
取得版・空でないlocator・確認者・確認日時が揃わない限りverified primaryに数えない。
公開画面とAPIは金額とともに現在のpublished coverage観測を返し、coverageが未確定なら
0円・0件へ丸めず「確認中」等と表示する。

#### `fiscal_events`

予算・決算の意味上安定したイベントを表す。議決段階、訂正、公開状態、出典は
ここへ入れず、同じ当初予算について提案版と可決版を一つのイベントへ結び付ける。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `fiscal_year` | `smallint` | 年度開始年 |
| `account_id` | `uuid null` | 法定会計。普通会計等は null |
| `account_identity_key` | `text generated` | membershipと同じ生成式でaccountのnullを非null参照値へ変換 |
| `reporting_scope_id` | `uuid` | 集計範囲 |
| `scope_membership_id` | `uuid null` | `account_id`がある場合の年度別scope構成枠 |
| `event_kind` | enum | `initial_budget` / `supplementary_budget` / `current_snapshot` / `available_budget_snapshot` / `settlement` |
| `supplement_sequence` | `smallint null` | 補正回次 |
| `as_of_date` | `date null` | スナップショット基準日 |
| `created_at` | `timestamptz` | 登録日時 |

制約例:

- `event_kind=supplementary_budget`なら`supplement_sequence >= 1`。
- 補正予算以外は `supplement_sequence is null`。
- `current_snapshot / available_budget_snapshot`なら`as_of_date is not null`、
  それ以外なら`as_of_date is null`。当初予算等の提出・可決日は金額セット側へ置く。
- `account_id is not null`なら`scope_membership_id`を必須、nullなら禁止する。
  membership正本に`(id, reporting_scope_id, fiscal_year,
  account_identity_key)`を一意にし、eventの同じ非null参照列を含む四列から
  複合外部キーを張る。
- `(fiscal_year, reporting_scope_id, account_id, event_kind,
  supplement_sequence, as_of_date)` に `UNIQUE NULLS NOT DISTINCT` を設定する。
- 金額セットからイベント種別を複合参照で検証できるよう、
  `(id, event_kind)`も一意にする。
- 金額セットrevisionから年度・scope・accountも同時に検証できるよう、
  `(id, event_kind, fiscal_year, reporting_scope_id, account_identity_key)`も一意にする。

`account_id`付きeventの金額セットrevisionをpublishedへ進めるときは、revisionが固定参照する
membership観測が`publication_state=published`、`membership_role=included`かつverifiedであることを
遅延constraint triggerで検証する。repositoryは同じ検証関数を事前確認に使うが、
DB保証の代替にはしない。特別会計を一般会計scopeへ結ぶ等、
年度・scope・accountの不正な組を公開できないようにする。

#### `fiscal_amount_sets`

一つの財政イベント・議決段階に対する安定した金額セット枠を表す。提案と可決は別の
安定枠とし、資料訂正や再解析でこの正本を増やさない。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `fiscal_event_id` | `uuid` | 安定した財政イベント |
| `event_kind` | enum | 親イベントと同じ種別。議決段階とのDB制約用に冗長保持する |
| `decision_stage` | enum | `proposed` / `passed` / `not_applicable` |
| `created_at` | `timestamptz` | 登録日時 |

`(fiscal_event_id, event_kind)`から`fiscal_events(id, event_kind)`へ複合外部キーを張り、
別イベント種別を金額セットへ設定できないようにする。さらにCHECK制約で、
`initial_budget / supplementary_budget`は`decision_stage in ('proposed', 'passed')`だけ、
`current_snapshot / available_budget_snapshot / settlement`は
`decision_stage='not_applicable'`だけを許す。不明な組合せは正本へ入れずstagingでQAする。

`(fiscal_event_id, decision_stage)`を一意にする。提案額と可決後額が同額でも
`proposed`と`passed`を別の安定枠にする。否決・撤回は関連する`bills.status`で示し、
`passed`の金額セットを作らない。

#### `fiscal_source_kind_event_rules`

金額セットの一次根拠に使える資料種別をコードへ散在させず、
`event_kind`、`decision_stage`、`source_kind`、`may_be_primary`、`rationale`、
`reviewed_by`、`reviewed_at`を持つ管理表で定義する。三つの種別列を主キーにし、
`may_be_primary=true`ではレビュー情報を必須にする。初期値はデータ辞書で確認し、
当初・補正予算、現計・予算現額、決算のそれぞれに適切な公式資料種別だけを許可する。
対応表はmigration管理のappend-onlyデータとし、通常UPDATE・DELETEを拒否する。許可取消が
必要な場合は影響するpublished金額セットを先に再検証・差し替えする専用migrationで扱う。

#### `fiscal_amount_set_revisions`

金額セットの資料訂正と公開版選択を追記する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `amount_set_id` | `uuid` | revisionと安定金額セット |
| `fiscal_event_id` / `event_kind` | `uuid` / enum | 親イベントとの複合整合用 |
| `revision_number` | `integer` | 同じ議決段階内の訂正版。1以上 |
| `effective_on` | `date null` | 提案日、可決日または資料上の適用日 |
| `scope_membership_id` / `membership_observation_id` | `uuid null` | この公開版が前提にした年度別scope構成と観測版 |
| `reporting_scope_id` / `fiscal_year` / `account_id` | `uuid` / `smallint` / `uuid null` | membership観測とイベントの同一性を保証する冗長キー |
| `account_identity_key` | `text generated` | accountのnullを含めてもevent・membershipとの複合FKを必ず検査する非null参照列 |
| `qa_status` | enum | `pending` / `verified` / `rejected` |
| `publication_state` | enum | `draft` / `reviewed` / `published` / `superseded` |
| `reviewed_by` / `reviewed_at` | `uuid null` / `timestamptz null` | 公開前確認 |

`(amount_set_id, revision_number)`と、根拠から参照するID一式を一意にし、金額セットごとに
published revisionを一つだけ許す。金額セット・財政イベント・membership観測へ
同じ`fiscal_event_id`、`event_kind`、年度、scope、`account_identity_key`を含む
複合外部キーを張る。
event参照はaccountがnullでも必ず検査し、membership参照は`scope_membership_id`が
非nullの場合だけ適用する。`account_id`付きでは
membershipと観測を必須、scope全体等の`account_id=null`では両方をnullにする。
published revisionが参照するmembership観測は`qa_status=verified`、
`publication_state=published`、`membership_role=included`でなければならない。
membership観測を切り替える場合は、同じトランザクションで金額セットも新しいeligibleな
revisionへ切り替えるか、対象金額セットrevisionを公開集合から外す。旧revisionがどの
旧観測を前提にしたかは保持する。

共通の状態CHECKにより`draft`は`pending / rejected`だけ、`reviewed / published /
superseded`は`verified`だけを許可する。draft以外へ進める場合は`reviewed_by`と
`reviewed_at`も必須にする。公開時は少なくとも一つの検証済み`primary`出典と、公開revisionの
値に一致する金額根拠があることを同じトランザクション内で検証する。

資料訂正では同じ安定金額セットへrevisionを追加し、過去版を`superseded`として残す。
政策上の修正可決は`proposed / passed`の別安定枠とdelta measureで表し、資料訂正と混ぜない。

決算実績は `decision_stage=not_applicable` の金額セットとして一度だけ保存する。
議会への提出・認定審査・認定・不認定はpublished
`fiscal_event_bill_link_revisions`と`bills.status`から導き、
認定状態ごとに決算額を複製しない。本会議の不認定は、議案審議過程計画が先行migrationで
追加する`bills.status='not_certified'`を用い、`certified`や否決へ丸めない。

#### `fiscal_amount_set_sources`

金額セットと根拠版は多対多にする。一つの資料で一次根拠を示す場合も、別の公式資料で
同じ額を照合する場合も、イベントや金額を複製せず出典を追加する。

まず`fiscal_amount_set_source_occurrences`に、`id`、`amount_set_id`、
`edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
`source_amount_set_key`を置く。
`(edition_source_occurrence_id, source_amount_set_key)`を対象金額セットなしで一意にし、
同じ資料edition内の同じ表・金額セットを、差し替え取得版や再解析のたびに別正本へ
付け替えない。同じURLが異なる年度editionに再利用され、ローカルキーも同じ場合は、
edition source occurrenceが異なるため衝突しない。
版ごとの読取りと確認は`fiscal_amount_set_sources`へ追記する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `amount_set_id` | `uuid` | 対象の金額セット |
| `amount_set_revision_id` | `uuid` | この版の値を持つ金額セットrevision |
| `amount_set_source_occurrence_id` | `uuid` | 安定したソース内金額セットとの対応 |
| `edition_observation_id` / `edition_id` | `uuid` | 採用した財政書誌観測とedition |
| `ingestion_source_id` | `uuid` | occurrence・取得版との整合確認用 |
| `source_version_id` | `uuid` | 根拠となる取得版 |
| `parse_run_id` | `uuid null` | parser根拠を解析した実行。同じ`source_version_id`に属すること |
| `extraction_method` | enum | `parser` / `manual` |
| `evidence_revision` | `integer` | 同じ物理根拠の人手再解釈番号。1以上 |
| `evidence_role` | enum | `primary` / `corroborating` / `calculation_input` |
| `source_locator` | `text null` | ページ、表、セル等の根拠位置 |
| `qa_status` | enum | 根拠対応の人手確認状態 |
| `verified_by` / `verified_at` | `uuid null` / `timestamptz null` | 根拠確認の監査情報 |

出典側の一意制約は対象IDを含めず、`(amount_set_source_occurrence_id,
source_version_id, parse_run_id, evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。
同じソース内出現を複数の正本金額セットへ割り当てられず、別取得版と再解析は
履歴として併存できる。parser根拠のrevisionは1に固定し、
人手で対応を訂正するときだけ番号を増やす。少なくとも一つの `primary` 出典を公開要件とし、
同じ金額セットに複数の公式版を関連付けられるようにする。後続の金額根拠から
同じ金額セットrevisionに属することを複合外部キーで検証できるよう、
`(id, amount_set_revision_id, amount_set_id)`も一意にする。
`extraction_method=parser`なら`parse_run_id`を必須、`manual`ならnullとする
CHECK制約を設ける。どちらも`source_version_id`は必須で、人手確認も読んだ取得版を失わない。
occurrenceから安定金額セット・edition source occurrence・論理ソースへ、版別根拠から
金額セットrevision・occurrence・書誌観測・取得版・解析実行へ、同じID一式を含む
複合外部キーを張る。
`(edition_observation_id, edition_id, ingestion_source_id, source_version_id)`から
書誌観測へ参照し、別取得版または別論理ソースのeditionを誤接続できないようにする。

#### 財政分類の正本、revision、出典

目的別、性質別、事業、財源、公会計科目等の分類は、年度ごとに名称、コード、階層、
担当部局が変わり得る。原資料の値を正本へ直書きせず、安定正本、公開revision、
ソース内出現、版別根拠を分ける。

- `fiscal_classifications`: `id`、`scheme`（`purpose / nature / program /
  funding_source / public_accounting`等）、人が確定した`canonical_key`、`created_at`を持つ
  出典非依存の安定正本。`(scheme, canonical_key)`と`(id, scheme)`を一意にする。
  年度間で同じ項目と確認できない候補にcanonical keyを推測付与せず、stagingで保留する。
- `fiscal_classification_revisions`: `id`、`classification_id`、`scheme`、
  `revision_number`、`display_label`、`parent_classification_id`、
  `valid_from_fiscal_year / valid_to_fiscal_year`、`qa_status`、`publication_state`、
  `reviewed_by / reviewed_at`を持つ追記型の表示・階層判断。同じ分類のpublished有効期間を
  重複させず、参照年度ごとに採用可能なpublished revisionを一つ以下にする。
  `(classification_id, revision_number)`と`(id, classification_id, scheme)`を一意にする。
- `fiscal_classification_source_occurrences`: `id`、`classification_id`、`scheme`、
  `edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
  `source_classification_key`を持つ安定対応。
  `(edition_source_occurrence_id, scheme, source_classification_key)`を対象分類IDなしで一意にし、
  同じedition内の同じ原表行を別の正本へ割り当てない。
- `fiscal_classification_sources`: `id`、`classification_revision_id`、
  `classification_id`、`scheme`、`classification_source_occurrence_id`、
  `edition_observation_id / edition_id`、`ingestion_source_id`、`source_version_id`、
  `parse_run_id`、`evidence_revision`、`source_code`、`source_label`、
  `source_department_name`、`observed_fiscal_year`、`source_locator`、
  `extraction_method`、`qa_status`、`verified_by / verified_at`を持つ版別根拠。

revision・正本・scheme、occurrence・正本・edition source occurrence、根拠・revision・
occurrence・書誌観測・取得版・解析実行を、それぞれ対象ID一式を含む複合外部キーで結ぶ。
出典側は`(classification_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`とし、原コード・原名称・担当部局・観測年度を
上書きせず版ごとに残す。parser根拠は`parse_run_id`必須かつevidence revision 1、manual根拠は
`parse_run_id=null`かつ取得版、空でないlocator、確認者、確認日時を必須にする。

`parent_classification_id`は同じschemeの正本だけを許す。published revisionについて、
自分自身を親にする場合だけでなく複数段の循環も遅延再帰guardで拒否する。子の有効年度には
同じschemeで有効なpublished親revisionが必要であり、親の無い最上位項目はnullで明示する。

#### 年度間の改称・分割・統合

単なるラベル訂正は同じ分類正本の新revisionとする。制度上別項目になった改称、分割、統合、
比較上の同等関係は、暗黙に同じIDへ寄せず次へ記録する。

- `fiscal_classification_mappings`: `id`、`scheme`、`mapping_key`、`created_at`を持つ安定枠。
  `(scheme, mapping_key)`と`(id, scheme)`を一意にする。
- `fiscal_classification_mapping_revisions`: `id`、`mapping_id`、`scheme`、
  `revision_number`、`relation_kind`（`rename / split / merge / equivalent`）、
  `effective_fiscal_year`、`note`、`qa_status`、`publication_state`、
  `reviewed_by / reviewed_at`を持つ追記型判断。
  `(mapping_id, revision_number)`と`(id, mapping_id, scheme)`を一意にし、
  `UNIQUE (mapping_id) WHERE publication_state='published'`の部分一意インデックスで、
  同じ安定枠の公開revisionを一つだけにする。
- `fiscal_classification_mapping_members`: `mapping_revision_id`、`mapping_id`、`scheme`、
  `classification_id`、`direction`（`from / to`）、`member_order`を持つ。分割は1対多、
  統合は多対1、改称・同等は1対1という要件をpublication guardで検査する。
  `(mapping_revision_id, classification_id, direction)`と
  `(mapping_revision_id, direction, member_order)`を一意にする。
- `fiscal_classification_mapping_source_occurrences`: `id`、`mapping_id`、`scheme`、
  `edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
  `source_mapping_key`を持つ安定対応。edition内のローカルキーを対象mapping IDなしで
  一意にする。
- `fiscal_classification_mapping_sources`: `id`、`mapping_revision_id`、`mapping_id`、
  `scheme`、`mapping_source_occurrence_id`、`edition_observation_id / edition_id`、
  `ingestion_source_id`、`source_version_id`、`parse_run_id`、`evidence_revision`、
  `source_locator`、`observed_mapping_text`、`extraction_method`、`qa_status`、
  `verified_by / verified_at`を持つ版別根拠。

mapping側も分類と同じ複合外部キー、一意性、parser/manual、追記型契約を適用する。
memberは`(mapping_revision_id, mapping_id, scheme)`からmapping revisionへ、
`(classification_id, scheme)`から分類正本へ複合外部キーを張る。mapping source occurrenceと
版別根拠も対象mapping・scheme・edition・論理ソースの全IDを複合外部キーで固定し、
`(mapping_source_occurrence_id, source_version_id, parse_run_id, evidence_revision)
UNIQUE NULLS NOT DISTINCT`にする。
memberのINSERT / UPDATE / DELETEは、triggerが親mapping revisionをロックして
`publication_state=draft`である間だけ許可する。親が`reviewed / published / superseded`へ
進んだ後は行集合と全列を凍結し、draftへ戻して編集する経路も許可しない。対応関係を訂正する
場合は、新しいmapping revisionとmember一式を追記し、旧revisionのrelation kind・cardinalityを
再現できるようにする。publication guardも親をロックしてmember数を検査し、member変更と
公開遷移の競合で未検証の組合せが公開されないようにする。
`effective_fiscal_year`は新分類が適用される最初の年度と定義する。すべてのrelation kindで、
`from` memberには`effective_fiscal_year - 1`を有効期間に含むverified・published分類revision、
`to` memberには`effective_fiscal_year`を含むverified・published分類revisionを要求する。
`equivalent`もこの隣接年度間の対応として扱い、離れた年度は検証済みmappingを年度ごとに
連鎖させる。分類revisionの公開切替時にも、それを参照するpublished mappingを遅延guardで
再検査し、有効なrevisionが片側から消える変更を拒否する。
published mapping revisionには確認者・確認日時とverified根拠を必須にし、根拠なしの年度間対応を
比較表示へ使わない。mappingが無い年度間は同じ名称でも「比較可能」と推測せず、画面とCSVで
比較不能または未確認と明示する。

#### `fiscal_amounts`

金額セットと分類に対する、版をまたいで安定した一つの金額項目を表す。値そのものは
訂正され得るため正本へ置かない。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `amount_set_id` | `uuid` | 提案・可決・決算実績の安定金額セット |
| `created_for_amount_set_revision_id` | `uuid` | この正本を初めて追加したdraft金額セットrevision |
| `classification_id` | `uuid null` | 総額なら null、内訳なら安定した`fiscal_classifications.id` |
| `measure` | enum | `revenue_budget` / `expenditure_budget` / `revenue_budget_delta` / `expenditure_budget_delta` / `revenue_budget_after` / `expenditure_budget_after` / `revenue_actual` / `expenditure_actual` / `income` / `expense` / `asset` / `liability` 等 |
| `created_at` | `timestamptz` | 登録日時 |

`(amount_set_id, classification_id, measure)` に
`UNIQUE NULLS NOT DISTINCT` を設定し、総額を表す `classification_id=null` でも
同じ measure の重複を防ぐ。根拠との複合外部キー用に`(id, amount_set_id)`も一意にする。
`(created_for_amount_set_revision_id, amount_set_id)`から金額セットrevisionへ複合外部キーを
張り、正本INSERT時のtriggerがその親行をロックして`publication_state=draft`を要求する。
正本の親、分類、measureは作成後不変にし、後続の金額セットrevisionでは同じ正本を再利用する。
分類付き金額は、親イベント年度に有効なpublished分類revisionが一つあり、そのrevisionに
verifiedな版別根拠がある場合だけ公開できる。正本IDだけを参照して未確認の年度へ
表示ラベルや階層を遡及適用しない。

#### `fiscal_amount_revisions`

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `amount_id` / `amount_set_id` | `uuid` | 値revision、安定金額項目、安定金額セット |
| `amount_set_revision_id` | `uuid` | この値を採用する金額セットrevision |
| `revision_number` | `integer` | 金額項目内の追記番号。1以上 |
| `amount_yen` | `bigint null` | 円単位の正規値 |
| `null_reason` | enum null | `not_published` / `not_applicable` / `unreadable` / `suppressed` / `unknown_dash` |
| `qa_status` | enum | 値の確認状態 |
| `verified_by` / `verified_at` | `uuid null` / `timestamptz null` | 値確認の監査情報 |

`(amount_id, revision_number)`と`(amount_id, amount_set_revision_id)`を一意にし、
`(amount_id, amount_set_id)`から安定項目へ、`(amount_set_revision_id, amount_set_id)`から
金額セットrevisionへ複合外部キーを張る。`amount_yen`がnullなら`null_reason`を必須、
非nullなら`null_reason`を禁止する。ゼロは非nullの値である。公開金額セットrevisionでは、
その版に属する金額revisionだけを読み、値を旧新版から混ぜない。公式訂正では同じ
`fiscal_amounts.id`に新しい値revisionを追加する。

金額revisionのINSERTと許可されたUPDATEはtriggerが親金額セットrevisionをロックして
`publication_state=draft`であることを要求し、物理DELETEは全状態で拒否する。親が
`reviewed / published / superseded`へ進んだ後は、そのrevisionに属する金額行集合と
値・null理由・QA情報を凍結する。訂正時は
新しいdraft金額セットrevisionを作り、公開スナップショットに含める全金額正本について
新しい金額revisionを明示的に作る。旧revisionの値へ暗黙にフォールバックしない。

#### `fiscal_amount_evidence`

一つの正規金額に複数の一次・照合資料を結び、資料ごとの原表記と位置を追跡する。
原表記を`fiscal_amounts`へ直接置くと複数資料の値が上書きされるため、根拠行へ分離する。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | `uuid` | 主キー |
| `amount_id` | `uuid` | `fiscal_amounts.id`。監査履歴を連鎖削除しない`ON DELETE RESTRICT` |
| `amount_set_id` | `uuid` | 金額と金額セット出典が同じセットに属することをDBで保証するためのキー |
| `amount_revision_id` / `amount_set_revision_id` | `uuid` | この版の値と親金額セットrevision |
| `amount_source_occurrence_id` | `uuid` | 安定したソース内金額との対応 |
| `amount_set_source_occurrence_id` / `ingestion_source_id` | `uuid` | 親のソース内金額セットと論理ソース |
| `amount_set_source_id` | `uuid` | `fiscal_amount_set_sources.id`。この版・解析の親根拠 |
| `source_version_id` / `parse_run_id` | `uuid` / `uuid null` | 金額を読んだ取得版と解析実行 |
| `evidence_revision` | `integer` | 同じセル等の人手再解釈番号。1以上 |
| `source_value_text` | `text null` | セルまたはPDFの原表記。資料に値自体が無い場合はnull |
| `source_value_numeric` | `numeric null` | 原単位での10進値 |
| `source_unit` | `enum null` | `yen` / `thousand_yen` / `million_yen` 等。値が無い場合はnull可 |
| `normalized_amount_yen` | `bigint null` | この根拠から変換した円単位値 |
| `normalized_null_reason` | enum null | この根拠で値を得られない理由 |
| `source_page` / `source_table` / `source_cell` | `text null` | 当該資料内の根拠位置 |
| `confidence` | `numeric null` | 自動抽出の信頼度。公開可否の代わりには使わない |
| `qa_status` | enum | この根拠と値revisionの対応を確認した状態 |
| `verified_by` / `verified_at` | `uuid null` / `timestamptz null` | 値確認の監査情報 |

ソース内の一つの金額は、先に
`fiscal_amount_source_occurrences(id, amount_id, amount_set_id,
amount_set_source_occurrence_id, ingestion_source_id, source_amount_key)`へ対応付ける。
`(amount_set_source_occurrence_id, source_amount_key)`を対象金額なしで一意にし、版ごとの
根拠を`fiscal_amount_evidence`へ追記する。出典側の一意制約は対象の`amount_id`を含めず、
`(amount_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`に設定する。同じソース内出現を二つの正本金額へ
割り当てられず、差し替え版と再解析を区別できる。parser由来はrevision 1、人手訂正は番号を
増やす。`fiscal_amounts`、`fiscal_amount_revisions`、`fiscal_amount_set_sources`には
根拠行から参照するID一式の複合一意制約を置く。根拠行の
`(amount_revision_id, amount_id, amount_set_revision_id, amount_set_id)`と
`(amount_set_source_id, amount_set_revision_id, amount_set_id)`から複合外部キーを張る。
加えてoccurrence同士と版別根拠に`amount_set_source_occurrence_id`、
`ingestion_source_id`、`source_version_id`を冗長保持した複合外部キーを張る。これにより、
別の金額セット・別のソース内表・別取得版に属する金額と出典を誤って結べない。

根拠内でも`normalized_amount_yen`と`normalized_null_reason`を排他的にする。
`source_value_numeric`がある場合は`source_unit`を必須とするが、`not_published`や
`not_applicable`で資料上に値が無い場合は原表記・原数値・単位をnullにできる。
parser/manualの区別は親`fiscal_amount_set_sources.extraction_method`から、HTML・PDF・XLSXの
形式はその取得版のMIMEとlocator列から導き、子へ同名の別enumを重複させない。
公開する`fiscal_amount_revisions`には少なくとも一つの`primary`な金額セット出典に属する根拠を
必須とし、その出典・金額根拠・書誌観測がすべて`qa_status=verified`、書誌観測が
`publication_state=published`で、`normalized_amount_yen`またはnull理由が値revisionと一致することを
遅延constraint triggerで検証する。repositoryは同じ検証関数を公開切替前に呼ぶが、
DB保証の代替にはしない。
金額セット出典、金額根拠、revisionに結ぶ検算結果・検算根拠のINSERTと許可されたUPDATEも、
同じ親ロックでdraft中だけ許可し、物理DELETEは全状態で拒否する。親がreviewed以降は
根拠の追加も含めてスナップショットを凍結し、追加の照合資料や根拠訂正は新しい
金額セットrevisionへ追記する。
複数の公式資料で差があれば、片方を上書きせず`fiscal_validation_results`へ送り、
人手確認後に公開版を決める。

#### `fiscal_indicators`

財政状況資料集の率、住民1人当たり額、類似団体値、公会計の比率も正本・revision・根拠を
分け、金額表へ百分率を押し込まない。

- `fiscal_indicators`: `id`、`indicator_code`、`reporting_scope_id`、`fiscal_year`、
  `comparison_group`、`comparison_entity_key`を持つ安定正本。nullを含む自然キーには
  `UNIQUE NULLS NOT DISTINCT`を使う。
- `fiscal_indicator_revisions`: `id`、`fiscal_indicator_id`、`revision_number`、
  `value_numeric`、`null_reason`、`unit`、`denominator_value`、`denominator_definition`、
  `qa_status`、`publication_state`、`verified_by`、`verified_at`を持つ。値とnull理由は排他的にし、
  指標ごとのpublished revisionを一つだけ許す。
- `fiscal_indicator_source_occurrences`: `id`、`fiscal_indicator_id`、
  `edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
  `source_indicator_key`を持つ安定対応。
  `(edition_source_occurrence_id, source_indicator_key)`を対象指標なしで一意にする。
- `fiscal_indicator_sources`: `id`、`indicator_revision_id`、`fiscal_indicator_id`、
  `indicator_source_occurrence_id`、`edition_observation_id`、`edition_id`、
  `ingestion_source_id`、`source_version_id`、`parse_run_id`、`evidence_revision`、
  `evidence_role`（`value / denominator / corroborating`）、原表記、原単位、locator、
  `extraction_method`、`qa_status`、確認者・確認日時を持つ。

revisionと正本、occurrenceと正本、根拠とrevision・occurrence、解析実行と取得版に
edition source occurrenceと書誌観測を含む複合外部キーを張り、書誌観測のpublished状態は
guardで保証する。出典側一意制約は対象IDを含めず、
`(indicator_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。parser根拠のevidence revisionは1、
人手再確認は番号を増やす。published revisionには、同じ対象年度のpublished・verified書誌観測と
verifiedな`value`根拠を一つ以上必須にし、
分母を公開する場合はverifiedな`denominator`根拠も必須にする。訂正・再解析時は旧publishedを
維持したまま新revisionをdraftでQAする。coverageの`data_kind=indicator`も同時に公開する。

#### `fiscal_event_bill_links`

議案候補の誤突合・訂正を残すため、リンク枠、正規化revision、出典を分ける。

- `fiscal_event_bill_links`: `id`、`fiscal_event_id`、`link_key`を持つ安定枠。
  `(fiscal_event_id, link_key)`を一意にする。
- `fiscal_event_bill_link_revisions`: `id`、`link_id`、`fiscal_event_id`、
  `revision_number`、`bill_id`、`relationship`（`proposes / passes / amends / recognizes /
  related_resolution`）、`match_method`（`exact_fields / manual / imported / candidate`）、
  `confidence`、`evidence_summary`、`qa_status`、`publication_state`、`verified_by`、
  `verified_at`を持つ。リンク枠ごとのpublished revisionを一つだけ許す。
- `fiscal_event_bill_link_source_occurrences`: `id`、`link_id`、`fiscal_event_id`、
  `edition_source_occurrence_id`、`edition_id`、`ingestion_source_id`、
  `source_relation_key`を持つ安定対応。
  `(edition_source_occurrence_id, source_relation_key)`を対象リンクなしで一意にする。
- `fiscal_event_bill_link_sources`: `id`、`link_revision_id`、`link_id`、
  `fiscal_event_id`、`link_source_occurrence_id`、`edition_observation_id`、`edition_id`、
  `ingestion_source_id`、
  `source_version_id`、`parse_run_id`、
  `evidence_revision`、`raw_bill_number`、`raw_relationship`、`source_locator`、
  `extraction_method`、`qa_status`、確認者・確認日時を持つ。

revision・安定枠・財政イベント、occurrence・安定枠・edition source occurrence、
根拠・revision・occurrence・published書誌観測の組を、対象年度と論理ソース込みの
複合外部キーとpublication guardで保証する。出典側は
`(link_source_occurrence_id, source_version_id, parse_run_id, evidence_revision)
UNIQUE NULLS NOT DISTINCT`とし、対象linkや`bill_id`を含めない。parser根拠の
evidence revisionは1、人手再確認は番号を増やす。`candidate`はdraft/pendingに限り、公開には
年度・会計・段階・補正回次を確認したverified根拠、確認者、確認日時を必須にする。
訂正時は旧publishedを残して新revisionをdraftでQAし、同一トランザクションで切り替える。
`passes` は沼津市議会で予算案が「可決」された関係を表す。

#### `fiscal_validation_results`

`validation_scope`（`source_parse / amount_set / cross_source`）、`parse_run_id`、
`source_version_id`、`amount_set_id`、`amount_set_revision_id`
（いずれもscopeに応じてnull可）、`rule_code`、`severity`、`status`、
`expected_value`、`actual_value`、`difference`、`tolerance`、`details`、
`reviewed_by`、`reviewed_at`を持つ。`source_parse`では取得版と解析実行を両方必須にし、
`amount_set / cross_source`では`amount_set_id`と`amount_set_revision_id`を必須、
単一の取得版・解析実行はnullにして、
対象根拠を次の中間表で列挙する。これにより複数出典の検算へ恣意的な「代表source」を
置かない。`parse_run_id`がある場合は、その`source_version_id`との一致を共通の複合外部キーで
DB保証する。警告をログだけに流さず公開判断の記録にする。

`fiscal_validation_results`と`fiscal_amount_evidence`には、複合外部キー用の
`(id, amount_set_revision_id, amount_set_id)`一意制約を設ける。

複数の金額根拠を比較する検算は、
`fiscal_validation_result_evidence(validation_result_id, amount_set_revision_id,
amount_set_id, amount_evidence_id, comparison_role)`で対象行を明示する。中間表の二つの
親IDはnot nullとし、`(validation_result_id, amount_set_revision_id, amount_set_id)`と
`(amount_evidence_id, amount_set_revision_id, amount_set_id)`の双方から複合外部キーを張る。
別の金額セットまたは別訂正版の根拠を混在させない。
`comparison_role`は`baseline / compared /
calculation_input / output`とし、主キーを
`(validation_result_id, amount_evidence_id, comparison_role)`にする。これにより、同じ金額セットに
複数金額・複数出典があっても、どの`fiscal_amount_evidence`同士の差を警告したかを
外部キー付きで再現できる。`cross_source`では少なくとも`baseline`と`compared`を一つずつ持ち、
両者の`amount_set_source_id`が異なることを遅延constraint triggerで保証する。
repositoryは同じ検証関数を事前確認に使うが、DB保証の代替にはしない。

### 8.3 公開整合、原本保持、監査履歴

財政テーマmigrationで次のguard関数を作り、対象の正本・revision・観測・根拠・
registry参照の`INSERT / UPDATE / DELETE`後に同じ関数を呼ぶ
`CONSTRAINT TRIGGER DEFERRABLE INITIALLY DEFERRED`を設定する。

- `fiscal_document_edition_publication_guard`: published書誌観測をverifiedに限定し、同じ
  edition occurrence・論理ソース・取得版・解析実行の組と、parser/manual要件を検査する。
  manualのverified観測は空でない`source_locator`、確認者、確認日時を必須にする。
- `fiscal_membership_publication_guard`: published membership観測をverifiedに限定し、同じ年度の
  published・verified書誌観測を要求する。
  `account_id`付きpublished金額セットrevisionが固定参照する観測は
  `membership_role=included`に限る。membership切替時は既存published金額セットrevisionも
  再検査する。
- `fiscal_account_year_guard`: `account_id`がnon-nullの全stable targetで年度を会計の
  有効範囲へ束縛する。membership・coverage・event・金額セットの親子切替でも再検査し、
  無効年度のmembershipを経由した金額公開を拒否する。
- `fiscal_data_coverage_publication_guard`: publishedの`collected / partial`観測に同じ対象の
  根拠版、edition source occurrence、published・verified書誌観測を要求する。書誌年度と
  coverage年度、論理資料の`source_kind`とcoverageの`source_kind`、
  `present / absent`と根拠の意味をそれぞれ一致させる。採用するverified primary根拠に
  extraction methodを必須とし、parser/manualの取得版・parse run・locator・確認監査契約も
  検査する。
- `fiscal_classification_publication_guard`: published分類revisionと年度間mapping revisionを
  verifiedかつ確認者・確認日時ありに限定し、同じedition・取得版に属するverified根拠を
  要求する。根拠の観測年度をrevisionの有効年度またはmappingの発効年度と一致させる。
  分類のpublished有効期間重複、別schemeの親、親の有効期間欠落、階層循環、
  mapping種別とfrom/to件数の不一致を拒否する。published mappingの各`from` memberには
  発効前年、各`to` memberには発効年に有効なverified・published分類revisionを要求し、
  memberまたは参照分類revisionの変更でも再検査する。分類付きpublished金額については
  親イベント年度に有効な分類revisionを一つ要求する。
- `fiscal_amount_set_publication_guard`: published金額セットrevisionにverifiedなprimary出典と、
  同じrevisionだけに属するverified金額revision・一致する金額根拠、同じ取得版の
  published・verified書誌観測を要求する。primary出典の書誌年度を親イベント年度と一致させ、
  `fiscal_source_kind_event_rules(event_kind, decision_stage, source_kind,
  may_be_primary)`のレビュー済み対応表で`may_be_primary=true`の資料種別だけを一次根拠に
  許可する。対応表は共通0Aの列挙ではなく財政migrationが所有し、たとえば決算イベントへ
  予算概要を一次根拠として結ぶ誤りを拒否する。金額正本、金額revision、金額セット出典、
  金額根拠、検算結果・根拠の変更でも親をロックして、非draft親の子集合が変わらないことを
  検査する。
- `fiscal_indicator_publication_guard`: published指標revisionにverifiedなvalue根拠を、
  分母を公開する場合はdenominator根拠も要求し、書誌観測の年度を指標年度と一致させる。
- `fiscal_bill_link_publication_guard`: published議案リンクrevisionに、候補ではないverified根拠と
  確認者・確認日時を要求し、書誌観測の年度を財政イベント年度と一致させる。
- `fiscal_validation_publication_guard`: 公開に用いる`cross_source`検算に別出典の
  `baseline / compared`を一つ以上ずつ要求する。

各guardは公開行だけでなく、最後のverified根拠の削除・`rejected`化、書誌観測やmembershipの
切替、source occurrence・取得版・解析実行の変更でも発火する。直接SQLでも根拠なし公開や
別正本への付け替えをコミット時に拒否し、repositoryは同じ関数による早期確認だけを担う。
通常同期triggerは公開判定に数えるparser根拠を共通registryへactive referenceとして登録し、
`superseded / rejected`化でreleaseする。テーマ固有guardは公開集合とregistryの完全一致も
検査する。

共通0Aの`ingestion_source_version_retention_guard`はactive referenceが残る取得版について、
`retained`から`expired / not_permitted / pending`への変更と非公開object keyの除去を拒否する。
同じトランザクションで別の保持版またはmanual確認済み根拠へ公開を切り替えた後だけ、旧版の
保持終了を許す。正本・occurrence・revision・根拠・coverage観測は`ON DELETE RESTRICT`と
`prevent_audit_delete`で物理DELETEを拒否し、訂正は新revisionと
`superseded / rejected`で残す。

## 9. 取り込み、検算、版管理

### 9.1 現行基盤との関係

`@mirai-gikai/numazu-ingest` には既に次がある。

- 1秒以上のアクセス間隔と連絡先付き User-Agent を持つ `NumazuSiteClient`。
- PDF を `pdftotext -layout` で変換する処理。
- `ingestion_runs` に実行状態と件数・エラーを残す処理。
- `ingestion_sources` に URL、最新 hash、ETag、Last-Modified、取得日時を残す処理。
- 議案 PDF の hash が同じなら再解析しない冪等取り込み。

財政取り込みも同じ package の server/service/repository/shared 構成へ追加する。
ただし `ingestion_sources` だけでは過去 hash が消えるため、
`ingestion_source_versions` を監査証跡の正とする。既存テーブルは最新状態の高速判定と
実行一覧に使い、財政版テーブルを置き換えない。

`ingestion_source_versions` は取得バイナリの版だけを表し、解析の成功・失敗や
パーサー版を表さない。解析は常に `ingestion_parse_runs` を開始し、同じ取得版を
パーサー更新後に再解析できるようにする。書誌情報は
`fiscal_source_document_edition_observations`、構造化された金額は
`fiscal_amount_sets`以下へ保存し、
どちらも生成元の parse run まで追跡できるようにする。

### 9.2 パイプライン

```text
索引発見
  -> レート制限付き取得
  -> バイナリ hash・HTTP 情報の版登録
  -> 非公開原本保存・保持状態登録（parser根拠として公開する資料）
  -> parse run 登録
  -> 形式別 staging 解析
  -> 正本候補をQAし、source occurrenceへ安定対応
  -> 資料 edition の書誌観測をdraftで追記
  -> coverage観測を追記
  -> 単位・年度・会計・段階の正規化
  -> 自動検算
  -> 管理画面で差分・警告・議案候補を確認
  -> reviewed
  -> 公開版へ昇格し、共通原本registryと同期
  -> キャッシュ再検証
```

原本取得と公開を一つのトランザクションにしない。解析途中の値を公開テーブルから返さない。

### 9.3 形式別方針

- **HTML**: 索引、タイトル、更新日、リンクを DOM で抽出し、リンク切れと年度追加を検知する。
- **PDF**: バイナリ hash を先に確定し、テキストレイヤーがあれば
  `pdftotext -layout` を使う。表の列境界、ページ見出し、単位を source profile で固定する。
  画像 PDF の OCR は自動公開せず要レビューとする。
- **XLSX**: シート名、セル座標、数式、表示値、結合セルを読む。
  14シートすべてを一度に汎用化せず、使うシートごとに schema を定義する。
- **旧 XLS**: 対応ライブラリまたは LibreOffice による読み取りを分離し、
  変換後ファイルではなく元バイナリの hash を版 ID に使う。

### 9.4 同一 URL の上書き対策

`予算執行状況` と `固定資産一覧` は同じ URL の内容が更新される可能性がある。

- URL を版 ID にしない。
- 取得バイナリの SHA-256 と取得日時を source version の必須情報にし、
  資料内の基準日は対応するpublished
  `fiscal_source_document_edition_observations`から導く。
- hash が変わったら、同じ表題でも新しい `ingestion_source_versions` を追加する。
- 新しい取得版の値が同じなら、同じ金額セットへ版別根拠を追記する。値またはnull理由が
  公式訂正で変わった場合だけ、同じ議決段階の
  `fiscal_amount_set_revisions`と`fiscal_amount_revisions`を追加して旧版を
  `superseded`にし、訂正履歴を表示できるようにする。source occurrenceと安定金額項目は
  再利用する。提案版と可決版は訂正関係にせず、別の安定金額セットとして併存させる。
- 基準日を PDF 内から抽出できない版は自動公開しない。
- ETag / Last-Modified は補助情報であり、hash の代わりにしない。
- ジョブ障害や公開元の一時的な 404 で、既存公開データを削除しない。
  失敗は新しいcoverage観測として残す。

### 9.5 自動検算

| 検算 | 判定 |
| :-- | :-- |
| 年度・会計・資料表題 | URL から推測した値ではなく本文と一致すること。元号変換も確認する |
| 単位 | ページまたは表の単位を全行へ適用し、行内の例外を検出する |
| 子項目合計 | 款・項・内訳の合計と公表小計を原単位で比較する。差を勝手に按分しない |
| 当初 + 補正 | source profile が「現計」をこの式で定義する場合だけ比較する。繰越等を含む予算現額には強制しない |
| 執行率 | `支出済額 / 予算現額` 等、資料の分母定義を固定し、公表された丸め桁の範囲で一致すること |
| 会計間 | 全会計合計と構成会計を、同じ収支側・同じ段階で比較する。内部取引の有無を注記する |
| 資料間 | 同年度・同会計・同段階・同基準日のみ比較する。普通会計と一般会計の差はエラーにしない |
| 議案 | 年度、会計名、当初/補正/決算、補正回次、category が一致すること |
| null / 0 | 空欄をゼロ化していないこと、明示ゼロが欠損化していないこと |

source profile ごとに `exact`、許容差、警告のみの規則を宣言する。
公表値が千円単位で独立に丸められている場合、差が生じ得るため、
許容差と根拠を検算レコードに保存する。閾値内でも元データを補正しない。

### 9.6 人手レビュー

管理画面には次を出す。

- 新旧版の hash、取得日時、ページ数・シート名、行数の差。
- 原表記、円換算値、単位、分類、根拠ページ・セル。
- 小計差、執行率差、年度間の分類変更、未解決 `null`。
- 議案結合候補と一致した年度・会計・補正回次。
- 公開中の版への影響件数。

`hard_error` が1件でもあれば公開不可とする。`warning` は理由を記録してレビュー完了しない限り
公開不可とする。誰がどの版を承認したかを監査ログに残す。

### 9.7 更新頻度

- 財政情報索引: 通常は週次、2月・3月、6月、9月、11月の会期中は日次。
- 予算執行状況: 半期公表を想定し、月次で hash を確認する。毎日の取得は行わない。
- 当初・補正予算: 会期中は議案取り込み後に日次確認し、議決後に可決状態を反映する。
- 決算・主要施策報告・監査意見: 9月定例会前後に週次確認する。
- 財政状況資料集・地方公会計: 年次。

相手サイトへのアクセスは既存どおり最低1秒間隔とし、条件付き GET を使える場合も
過剰取得しない。失敗時は指数バックオフし、無限再試行しない。

### 10.2 `/finance` 財政トップ

- 最新の公開済み年度と「データは何月何日現在」を最初に表示する。
- 一般会計当初予算、全会計合計、一般会計歳出決算、議会費を要点カードで示す。
- 年度選択と会計範囲選択を設ける。初期状態は一般会計とし、普通会計を混ぜない。
- 「予算」「決算」「自治体比較」「資産」を明確に分け、未実装領域は数値を代用しない。
- 数字ごとに出典、単位、会計範囲、段階を短く表示し、詳細から原資料へ移動できる。

### 10.3 年度詳細

#### 予算から決算までの流れ

横方向の複雑な Sankey 図ではなく、最初は次の縦型タイムラインと差額表を採用する。

```text
当初予算案提出 -> 当初予算可決 -> 補正第1回 ... -> 年度末の予算現額
                                           -> 決算提出 -> 認定
```

各ノードに日付、金額、前段からの増減、議案番号、議決結果を付ける。
審議中、可決、否決、認定を色だけでなくテキストとアイコンで示す。

#### 目的別構成

- 横棒グラフを主とし、款別の金額と構成比を大きい順または公式順に切り替えられるようにする。
- 同じ内容の表を必ず併置し、款・項へ段階的に開く。
- 円グラフは項目が多いと比較しづらいため採用しない。
- ツリーマップを追加する場合も補助表示とし、表と横棒を主要手段に保つ。

#### 予算対決算

- 当初予算、年度末の予算現額、決算を同じ目的分類ごとのグループ棒またはドットプロットで示す。
- 「未執行額」を価値判断語で呼ばず、`予算現額 - 支出済額` と定義を表示する。
- 執行率の分母が当初予算ではなく予算現額であることを明記する。
- 分類変更がある年度間は線で直接つながず「比較不能」または組替え注記を出す。

### 10.4 議案との往来

- 財政イベントから既存 `routes.billDetail(bill.id)` へリンクする。
- 議案詳細には「この議案に関連する予算・決算」パネルを追加し、
  年度、会計、補正回次、提案額または増減額、議決状態を表示する。
- published `committee_review_observations.member_utterance_block_count`と
  published `bill_debate_revisions`がある場合は、表示名「委員発言ブロック数」と
  本会議討論の有無を数字の変更と並べる。委員発言ブロック数を質問件数とは呼ばない。
- 審査で発言された金額を自動で財政イベントの確定値とみなさない。
- 公式の議案、会議記録、財政資料の3種類の出典を区別して表示する。

### 10.5 議会費

- 当初予算、年度末の予算現額、決算を比較する。
- 一般会計歳出に占める比率を、分子・分母と計算式付きで示す。
- 人件費、物件費、委託料、負担金・補助金等の内訳を公式資料の粒度で表示する。
- 政務活動費等の名称は原資料に合わせ、支給額と実支出額を同一視しない。
- 普通会計の議会費推移を表示する場合は、一般会計決算とは別のタブと説明に分ける。

### 10.6 比較画面

- 5年推移は名目円を既定とし、物価調整済みなら指数、基準年、計算式を示す。
- 住民1人当たり額は人口の基準日、人口区分、出典を表示する。
- 類似団体比較は財政状況資料集の分類年度・団体群を表示し、現在の分類と決め付けない。
- 指標値の良し悪しを単色の信号表示だけで断定せず、定義、全国・類似団体分布、
  過去推移を併記する。

### 10.7 出典表示とダウンロード

すべての画面に「この数字について」詳細を用意し、次を表示する。

- 公式資料名と公式 URL。
- 対象年度、会計、集計範囲、金額段階、基準日。
- 原資料の単位、ページ・表・セル、取得日時、SHA-256 の短縮表示。
- 本サービスによる計算式と丸め規則。
- 訂正・版変更履歴。

CSV/JSON には少なくとも `fiscalYear`、`accountCode`、`reportingScope`、
`eventKind`、`asOfDate`、`measure`、`amountYen`（文字列）、`nullReason`、
`sourceUrl`、`sourceHash`、`publishedAt` を含める。
現在確認した金額はJavaScriptの安全整数内だが、将来の連結値や他テーマとの共通契約でも
精度を失わないよう、JSONの金額は10進文字列にする。

## 11. アクセシビリティ

WCAG 2.2 AA と JIS X 8341-3:2016 を実装水準とし、
グラフが読めなくても同じ問いに答えられることを受入条件にする。

- 各グラフに見出し、短い要約、単位、会計範囲、基準日を付ける。
- グラフと同じ全データを、`caption`、列見出し、行見出しを持つ HTML table で提供する。
- 表示上だけ省略した「億円」ではなく、読み上げ名に「956億5,000万円、一般会計当初予算」
  のように値・単位・意味を含める。
- 色だけで年度、増減、審議状態を区別しない。線種、形、ラベル、凡例テキストを併用する。
- 通常テキストは4.5:1、グラフの必要な線・領域・フォーカス表示は3:1以上の
  コントラストを確保する。色は `globals.css` のテーマトークンを使う。
- tooltip の情報はフォーカスでも開け、Esc で閉じられ、hover だけに依存しない。
- フィルター変更後の年度、会計、件数を `aria-live="polite"` で通知する。
- キーボードでデータ点を一つずつ巡回させることを唯一の読み方にしない。
  要約と表を先に使えるようにする。
- 320 CSS px（1280 CSS px 幅を400%拡大した相当条件を含む）、200%・400%拡大、
  文字間隔変更で横スクロールを本文全体に発生させない。
  幅広表は表コンテナ内だけをスクロール可能にし、その旨を伝える。
- アニメーションは情報理解に必須とせず、`prefers-reduced-motion` に従う。
- 欠損は空白にせず「未公表」「該当なし」「判読できず」等を表示する。
  ゼロは「0円」と読む。
- 「前年比 +10.0%」には比較元年度と金額差も併記する。
- VoiceOver 実機または Simulator で、年度変更、会計変更、表の移動、議案への遷移を確認する。

自動テストだけで適合を宣言せず、既存アクセシビリティ計画の L1〜L4 の検証へ
財政トップ、年度詳細、議案財政パネルを追加する。

- 令和8年度予算概要の一般会計総額 `95_650_000_000` 円と議会費
  `469_887_000` 円を抽出できる。

### 13.3 DB 統合テスト

ローカル Supabase を実際に使い、次を確認する。

- RLS 有効・ポリシーなしで anon から読めず、server repository から必要列だけ読める。
- 公開用 view は `security_invoker=true` で、基礎テーブルと view に
  `anon` / `authenticated` の直接権限がない。DB function は既定の
  `SECURITY INVOKER`、または固定 `search_path`・権限 revoke 済みの
  `SECURITY DEFINER` で、想定外ロールから実行できない。
- 同一 source URL・同一 hash の再取得は版を重複作成しない。
- 同一 URL・異なる hash は新しい版を作り、旧版を残す。
- parser由来のpublished根拠は、参照する取得版が`retained`でなければ公開できない。
  公開根拠に参照された版を`expired / not_permitted / pending`へ変える操作または非公開
  object keyを除去する操作は、単独の直接UPDATEではコミット時に拒否される。同一
  トランザクションで別の保持版またはmanual確認済み根拠へ切り替えた後は成功する。
- 同じ URL・同じ年度・異なる hash のV1とV2は同じdocument editionとsource occurrenceに
  属し、V1 publishedとV2 draftを併存させてからV1 superseded・V2 publishedへ切り替えられる。
  年度ごとに URL が異なる資料は同じ`fiscal_source_documents`の別editionとして保存される。
- 同じURLをFY2025・FY2026の別editionで使い、同じローカルキーが現れても、下流occurrenceは
  edition source occurrenceごとに一意になる。FY2026のmembership・amount set・indicator・
  bill link・coverage・classification・classification mappingへFY2025の書誌観測または
  取得版を結ぶINSERTと公開を拒否する。
  coverageと異なる`source_kind`、またはevent kind・decision stageに対して一次根拠に
  許可されていない`source_kind`のamount setも公開できない。
- reporting scope の membership は年度・根拠版ごとに再現でき、同じ
  source occurrenceを複数の正本へ割り当てられず、普通会計等の範囲変更が別年度へ
  波及しない。`membership_role`を`reference_only`から`included`へ訂正しても安定正本は
  増えず、旧published観測と新published観測の履歴を復元できる。
- 書誌観測とmembership観測は同じ対象の旧publishedと新draftを併存でき、publishedを
  二つにできず、切替後も旧`superseded`観測を復元できる。
- membership、edition、coverage、classification、classification mapping、amount set、amount、
  indicator、bill linkのsource occurrenceについて、
  対象正本ID、親source occurrence、`ingestion_source_id`、ローカルキーの直接UPDATEを
  拒否する。候補をstagingで確定する前後と、誤突合を通常UPDATEで別正本へ
  付け替えられないことを確認する。
- 安定正本の親ID・stable key、revisionの正規値、版別根拠の対応先・取得版・解析実行・
  抽出値は通常UPDATEを拒否する一方、QA・publication・確認情報の許可された状態遷移は
  成功する。対象表一覧とtrigger付与漏れをmigrationテストで固定する。
- 各版別根拠はV1 manualとV2 manualを同じoccurrenceへ追記できる一方、同じoccurrence・
  取得版・parse run・evidence revisionの二重INSERTを拒否する。
- failed run が公開中データを変更しない。
- 同じ source version を異なるパーサー版または設定で解析すると別 parse run になり、
  検算結果がそれぞれの source version と parse run の組まで追跡できる。
- 別の source version に属する parse run を根拠行へ指定すると、複合外部キー違反で
  保存できない。解析実行だけを指定したnullable行もCHECK制約で拒否され、
  人手根拠の`parse_run_id=null`は保存できる。
- coverage正本では`account_id`や`as_of_date`がnullでも自然キーが重複せず、観測では
  共通の`state × record_presence`行列、非負件数、`matched_count <= expected_count`を
  DBが保証する。未公表、未取得、取得不能、部分取得、解析失敗を金額のnull理由と分け、
  同じ対象の再観測を履歴として残しつつpublished観測は一つだけにできる。
- coverage観測は`reviewed_by / reviewed_at`の片方でも欠くと、取得済み・未公表・取得不能・
  対象外のいずれも`reviewed / published / superseded`へ進めない。
- 九つの財政publication guardについて、通常repositoryを迂回した直接SQLでも、根拠のない
  published行、最後のverified根拠のDELETE・`rejected`化、別正本または別取得版の根拠への
  付け替えをコミット時に拒否する。新旧根拠を同一トランザクションで正しく切り替える操作は
  成功する。
- published parser根拠の追加・`superseded / rejected`化で、財政固有consumer typeのactive
  referenceが共通registryと完全に同期する。未登録consumer typeとregistryへの直接DMLを
  拒否し、保持guardが後続テーブル名を知らなくても参照中の取得版を保護する。
- `account_id`、`supplement_sequence`、`as_of_date` が null の自然キーを再投入しても、
  `fiscal_events` が重複しない。`reporting_scope_id` が異なる場合は別イベントになる。
- `fiscal_accounts`は終了年度が開始年度より前の期間を拒否する。同じcodeの
  `2024–open-ended`と`2025–open-ended`は重複として拒否し、`2024–2024`と
  `2025–open-ended`は隣接期間として保存できる。異なるcodeの同期間は競合しない。
- `account_id`付きmembership・coverage・event・金額セットは会計の開始年度、終了年度の
  両境界とopen-ended期間内なら保存でき、範囲前後なら拒否される。`account_id=null`は
  適用外として保存できる。参照後の会計期間縮小を拒否し、無効年度membershipを経由した
  金額公開も失敗する。
- `account_id=null`のmembership正本・source occurrence・観測に別年度または別scopeの
  冗長キーを組み合わせると、非nullの`account_identity_key`を含む複合外部キー違反で
  拒否される。`account_id`を直接含む`MATCH SIMPLE`の複合FKへ退行していないことも
  migration定義の検査で固定する。membership・coverageの正本、観測、source occurrence、
  版別根拠でidentity keyへ任意値をINSERT / UPDATEできず、各行自身の`account_id`・
  `as_of_date`から同じ生成式で決まることも検証する。
- 非nullの同じ`account_id`を同じscope・年度へ異なる`member_key`で追加するとCHECKで拒否し、
  正しい決定的キーを使っても部分一意制約で二重登録できない。`account_id=null`では同じ
  人手確認済み`member_key`の重複を自然一意制約で拒否し、異なる主体キーは併存できる。
- 同じ当初予算イベントに `proposed` と `passed` の金額セットが併存し、
  原案可決で金額が同じでも一方が他方を上書きしない。
- `initial_budget / supplementary_budget`に`not_applicable`、または
  `current_snapshot / available_budget_snapshot / settlement`に`proposed / passed`を
  設定するとCHECK制約で拒否される。正しい当初・補正の
  `proposed / passed`と、スナップショット・決算の`not_applicable`は保存できる。
- 親`fiscal_events.event_kind`と異なる`fiscal_amount_sets.event_kind`を指定すると、
  `(fiscal_event_id, event_kind)`の複合外部キー違反で拒否される。
- 同じ議決段階の訂正版は同じ安定`fiscal_amount_sets.id`・`fiscal_amounts.id`を再利用して
  set/amount revisionだけが増える。V1 publishedとV2 draftを併存させてから切り替え、
  公開viewはV2だけを返し、V1の値・根拠・書誌観測も復元できる。
- draft金額セットrevisionでは、同revisionを`created_for`にした新しい金額正本、金額revision、
  金額セット出典、金額根拠、検算結果・根拠のINSERTと許可されたUPDATEが成功する。
  親をreviewedへ進めた後は同じ操作をINSERT / UPDATEで行えず、全状態の物理DELETEも拒否する。
  値訂正または追加根拠は新しいdraft金額セットrevisionへ必要な金額revision一式とともに
  追加し、旧published revisionの子行数・値・根拠集合が変わらない。
- `fiscal_amount_set_revisions`は`qa_status=verified`かつ確認者・確認日時がある場合だけ
  `reviewed / published / superseded`へ進め、同一対象を二つ同時にpublishedへできない。
- `account_id`付きpublished金額セットrevisionは、公開時に固定した
  `membership_observation_id`を保持する。membershipを`included`から`reference_only`へ
  切り替えるだけのトランザクションは拒否する。対象金額セットrevisionも公開集合から外す、
  または別のincluded観測を参照する新revisionへ切り替えれば成功し、旧revisionから
  旧membership観測を復元できる。
- 一つの金額セットへ一次根拠と照合用根拠の複数出典を結んでも、イベントと金額を
  重複作成しない。同じamount set occurrenceまたはamount occurrenceを二つの正本へ
  割り当てる操作は一意制約または不変性triggerで失敗する。
- 同じ金額に二つの公式資料を結ぶと、資料ごとの原表記、単位、ページ・表・セル、
  円換算値を別々の`fiscal_amount_evidence`から追跡できる。不一致は正本を上書きせず
  検算結果へ送られる。
- 金額と別の金額セットに属する出典を`fiscal_amount_evidence`で結ぶと、複合外部キー
  違反で保存できない。資料に値が掲載されていない根拠は、空文字や架空単位を強制せず
  null理由とlocatorで保存できる。
- parser根拠は`parse_run_id`なしで保存できず、manual根拠はnullで保存できる。manualの
  財政書誌観測は空でない`source_locator`、確認者、確認日時のいずれかを欠けば
  verifiedまたはpublishedへ進めない。二つ以上の金額根拠を比較した検算は、各
  `fiscal_amount_evidence.id`と比較上の役割を再現できる。
- `fiscal_amount_revisions`で`amount_yen=null`と`null_reason`の制約、明示ゼロ、負の補正が
  保存できる。
- `classification_id=null` の総額を同じ `amount_set_id`・`measure` で重複登録できず、
  分類付きの内訳は別に登録できる。
- 同じedition内の分類ローカルキーを二つの安定分類へ割り当てられず、差し替え版の原コード・
  原名称・担当部局は同じsource occurrenceの新しい版別根拠として復元できる。manual分類根拠は
  取得版・空でないlocator・確認者・確認日時のいずれかを欠くとverifiedにならない。
- published分類revisionの有効年度は同じ正本内で重複できず、別schemeの親、自分自身または
  複数段の親循環、子年度に有効なpublished親がない階層を拒否する。分類付き金額は親イベント
  年度に有効なverified・published分類revisionがない限り公開できない。
- 改称・同等は1対1、分割は1対多、統合は多対1のmemberだけをpublished mappingへ許し、
  verified根拠のないmappingや年度・schemeの異なる根拠を拒否する。mappingの無い年度間を
  比較可能へ丸めず、訂正時も旧mapping revisionと版別根拠を復元できる。
- 同じmapping rootではV1 publishedとV2 draftを併存できるが、二つのpublishedを拒否する。
  V1をsuperseded、V2をpublishedへ同一トランザクションで切り替えると成功し、旧版も残る。
- `rename / split / merge / equivalent`の各mappingについて、`from`側に発効前年、`to`側に
  発効年のverified・published分類revisionがある場合だけ公開できる。片側の有効期間外、
  pending / draft分類、verified根拠欠落を拒否し、参照分類の切替で有効revisionを失う操作も
  mapping側を同時に差し替えない限りコミットできない。
- draft mapping revisionのmember追加・並べ替え・削除は許可し、reviewed以降のmemberの
  INSERT / UPDATE / DELETEと親revisionのdraftへの巻き戻しは拒否する。訂正は新revisionと
  新しいmember一式で行い、旧revisionのrelation kindとmember集合が不変で復元できる。
- Phase 5で政策分野を接続する時は、fiscal-year scopeからDB生成したsnapshot memberと
  release itemの双方向差分が0件でなければ公開できない。同じ対象・taxonomyの公開セット一意、
  reviewed releaseの凍結、active taxonomy不一致時の非合算を共通release契約テストへ追加する。
- 否決された補正には `passed` の金額セットが作られず、可決後現計 view に含まれない。
- 決算の認定状態を`certified / not_certified`間で変えても金額セットと決算額の行数・値が
  変わらず、本会議の不認定を否決へ丸めない。
- 移行期間中の旧`bills.committee_qa_count`は、同一議案に結ぶQA済みpublished観測の
  `member_utterance_block_count`との一致確認にだけ使用する。不一致を検出した場合は
  移行を失敗させ、公開viewや画面の入力には使わない。
- 既存`(council_session_id, bill_number)`から生成した候補が、QA後に
  `canonical_bill_key`確定済みの`bills.id`へ結び、nullable・曖昧な候補は公開されない。
- DB functionを追加・変更するPRでは、functionごとに
  `tests/supabase/db-function/{kebab-case-function-name}.test.ts`を作成し、
  `tests/supabase/utils.ts`を利用してローカルSupabase実DBで検証する。戻り値、ソート、
  フィルター、集計、権限を対象とし、DBはmockしない。

## 14. 受入条件

### 14.1 データ

- 令和6年度一般会計と議会費、令和8年度一般会計当初予算と議会費が、
  4.1 の円単位基準値と一致する。

- 普通会計議会費 448,976千円が一般会計決算 449,516,456円を上書きせず、
  別 scope で保存・表示される。
- reporting scope の年度別 membership と根拠版を表示・監査できる。
- `account_id`付きの全対象は財政年度が会計の有効期間内にあり、期間外のmembership・
  coverage・event・金額は公開できない。
- 年度間分類mappingは安定枠ごとにpublished revisionが一つだけで、発効前年の`from`と
  発効年の`to`に有効なverified・published分類revisionがある関係だけを比較へ利用する。
  訂正前のmapping revisionとmember集合も復元できる。
- すべての公開数値からsource occurrence、source version、parse run、公式 URL、原単位、
  根拠位置へたどれ、保持中のparser原本から同じ設定で再解析できる。
- 提案・可決は同じ財政イベントの別の安定金額セットとして併存し、訂正前のset/amount
  revisionと複数出典も失わず参照できる。
- `null` と `0`、負の補正を区別でき、欠損理由が表示される。
- 同一 URL の内容差し替えを2版以上のテストで再現し、保持中の旧版を復元できる。
  保持終了後も旧版のハッシュ・取得日時・抽出事実・差分・削除監査は残り、再解析不能で
  あることが明示される。
- 公開中parser根拠と共通registryのactive referenceが一致し、根拠のないpublished正本、
  最後のverified根拠の削除、参照中原本の保持終了を直接SQLでも拒否できる。
- hard error は0件、warning は全件レビュー記録付きである。

## 15. リスクと対策

| リスク | 影響 | 対策 |
| :-- | :-- | :-- |
| PDF 表の改版・段組み変更 | 桁・行・単位の誤抽出 | source profile、schema 検知、control total、差分レビュー。未知版を自動公開しない |
| 同一 URL の上書き | 根拠版を再現できない | source version にバイナリ hash・取得日時・非公開原本、安定document editionと版別書誌観測を分離 |
| 一般会計と普通会計の混同 | 比較・説明が誤る | account と reporting scope を分離し、普通会計を議案へ直接結ばない |
| 当初・現計・予算現額・決算の混同 | 執行率や増減が誤る | 段階 enum、基準日、source label、計算式を必須化 |
| 単位・丸め | 1,000倍の誤り、比率差 | 原値・原単位保存、円 bigint、10進計算、公式丸めとの二重検算 |
| 空欄のゼロ化 | 合計・評価が誤る | null reason 制約、明示ゼロ fixture、unknown dash をレビュー |
| 分類・事業名の変更 | 偽の時系列 | 年度有効期間と人手確認した mapping。比較不能表示を許容する |
| 議案の誤結合 | 別会計・別補正の審議を表示 | category、年度、会計、回次の完全一致と人手 verification |
| 議決前の額を確定値表示 | 市民を誤認させる | proposed/passed と published/reviewed を分離し、審議中ラベルを常時表示 |
| 決算認定を金額確定と混同 | 不認定時に実績が消える | `bills.status` と `recognizes` の関連を別軸にし、決算金額セットを複製しない |
| 著作権・利用条件 | 再配布停止、信頼低下 | 事実だけを独自構成、原本非公開、最小引用、担当課・専門家確認、オープンデータ化提案 |
| 公開元の負荷・仕様変更 | アクセス制限、更新停止 | 1秒以上間隔、条件付き取得、低頻度、User-Agent、失敗時停止 |
| 大きな金額の JS 精度 | 円単位の下位桁が壊れる | API は文字列、アプリは bigint/decimal、JSON 数値へ変換しない |
| 指標の価値判断 | 「高い/低い」の誤解 | 定義・分布・過去推移を併記し、政策評価を断定しない |
| 固定資産の地図化 | 誤位置・同一施設の重複 | Phase 4 に分離し、補完データの出典・精度・集約ルールを表示 |

3. 初期リリースを令和6・8年度の二点に限定するか、令和5〜8年度まで広げるか。
4. 「現計予算額」「予算現額」の各公式資料での構成要素を担当課に確認できるか。
5. 当初予算書・決算書の詳細表を電子データで提供してもらえるか。
6. 補正予算の増減額を議案本文から取得するか、財政資料の補正後額から差分計算するか。
   差分計算しかできない場合は `derived` と表示する。
7. 修正可決・組替動議・専決処分に伴う予算変更を既存 `bills` でどこまで識別できるか。
8. 公開承認を誰が行い、warning を許容する基準を誰が管理するか。
9. CSV/JSON を既存 `/developers/open-data-api` に統合するか、財政専用 endpoint にするか。
10. グラフライブラリを導入するか。SSR、バンドル量、キーボード対応、表 fallback、
    テーマトークン対応を比較して決める。
11. 住民1人当たり指標の分母を住民基本台帳人口、国勢調査人口等のどれに統一するか。
12. 物価調整、類似団体区分の変更、会計再編をまたぐ長期比較をどのフェーズで扱うか。

## 17. 他テーマとの依存関係

| テーマ | 本機能が使うもの | 接続時の注意 |
| :-- | :-- | :-- |
| 議案・会期 | `bills`、`council_sessions`、`canonical_bill_key`、published審議イベント | 財政側で複製せずlink tableを使う。旧nullable組は候補生成だけに使い、QA後の`bills.id`へ確定する |
| 委員会・会議記録 | published会議・議題revision、`committee_review_observations.member_utterance_block_count`、published `bill_debate_revisions`、verified根拠 | 旧互換列を正本にしない。表示名は「委員発言ブロック数」とし、注目度・質問件数・支出効果の評価には使わない |
| 議員・会派別賛否 | published `faction_snapshot_revisions`・`faction_vote_result_revisions`とverified根拠 | `faction_votes`旧互換値や未掲載から全会一致を導かず、個人賛否を推測しない |
| 人口・世帯 | 住民1人当たり額の分母 | 基準日・統計種別を固定し、年度平均か期末かを示す |
| 市民意識・各種調査 | 政策ニーズ、満足度、属性別課題 | 予算増減と調査結果の相関を因果関係として表示しない |
| 政策分野マスタ | 一般質問計画の`policy_topics`、DB生成population snapshot、consumer別active release | 財政分類とは別にQA済み多対多で結ぶ。財政固有member / release itemを使い、名称一致だけで自動公開せず、active taxonomyが異なるconsumerを合算しない |
| 総合計画・行政評価 | 政策体系、成果指標 | 予算の目的分類とは別体系。対応表と有効年度が必要 |
| 組織・部局 | 事業担当、年度間改称 | 部局再編を安定 ID と有効期間で管理する |
| 契約・入札 | 主要事業の実行段階 | 予算額、契約額、支払額を別 measure として扱う |
| 施設・地理 | 固定資産と地域別投資 | 公式資産一覧に緯度経度がない。住所補完の出典と精度が必要 |
| 監査 | 決算審査意見、健全化判断比率 | 数値と監査意見を区別し、意見によって元数値を上書きしない |
| アクセシビリティ | グラフ、表、filter、出典 dialog | 既存監査の L1〜L4 に新画面を追加し、公開ゲートにする |
| オープンデータ・利用条件 | CSV/JSON、原本保存、出典 | 構造化事実の公開条件と原本再配布の条件を分ける |

## 18. 実装開始時の作業分割

独立したレビュー単位として、次の順に PR を分ける。
前提として、共通基盤0Aは別PRで完了させ、財政PRの所有範囲に含めない。

1. 財政データ辞書、enum、document edition・全source occurrence・書誌観測/
   reporting scope membership・根拠観測/coverage/event/安定amount set・set revision/
   分類正本・分類revision・分類根拠・年度間mapping正本/revision/根拠・
   安定amount・amount revision/source link/
   validation/link、consumer type・registry同期・publication guardのDB migration と型生成。
2. 共通のsource version取得・parse runを利用する財政staging、非公開保存、
   管理画面の版・解析・検算表示。
3. 令和6年度決算・主要施策報告パーサーと検算。
4. 令和8年度予算概要パーサーと検算。
5. 財政イベントと `bills` の候補生成・手動確定。
6. 公開 repository / loader / API と `/finance` の表中心 UI。
7. グラフ、年度比較、議案詳細パネル。
8. アクセシビリティ E2E、運用通知、公開手順。

各 PR で schema、types、repository、純粋関数テスト、必要な DB 統合テストを揃える。
画面だけを先に作り、会計区分や版を持たない暫定 JSON を本番データ源にしない。
