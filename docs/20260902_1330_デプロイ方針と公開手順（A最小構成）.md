# デプロイ方針と公開手順（A 最小構成）

> [!CAUTION]
> この文書は沼津市議会版の運用を記録した履歴資料です。
> 静岡県議会版では無効であり、記載されたコマンド、URL、
> project ID、Git ref、ドメインを実行・使用しないでください。
> 静岡県版の公開基盤を確定後、別の手順書を作成します。

作成日: 2026-09-02

## 1. 決定

**Vercel Hobby（web / admin）+ Supabase Free（東京）+ Cloud Run Job 無料枠（asia-northeast1）** で公開する。
ホスティング費用は月 0 円を目標にし、費用は LLM の API 利用料に集中させる。

### 比較した選択肢

| 構成 | 月額目安（LLM除く） | 性能 | 移行工数 | 判断 |
| :-- | :-- | :-- | :-- | :-- |
| **A. Vercel + Supabase + Cloud Run Job**（本家から引き継いだ構成） | 0〜45 ドル | CDN・ISR・Fluid compute が標準 | なし | **採用** |
| B. Cloud Run に web/admin もコンテナ化 | 20〜35 ドル | 東京。`min-instances=0` だとコールドスタート 2〜4 秒 | 中 | 単一ベンダーにしたい動機が無ければ不利 |
| C. Cloudflare Workers（OpenNext） | 5〜30 ドル | エッジ | 大 | `node:fs`・OpenTelemetry の互換確認が要る |
| D. Supabase 自前ホスト | サーバー代 | — | 大 | DB 30MB に対して割に合わない |

### 根拠になった事実

- データは DB 30MB・議案 1,149 件。無料枠に十分収まる
- Node ランタイム必須（OG 画像生成で `node:fs`、middleware で Basic 認証）。Edge 限定の環境は不可
- 本家の CI（`deploy.yml` / `deploy_worker.yml`）がこの構成に配線済み。移行作業ゼロ
- Vercel 固有の依存は `@vercel/speed-insights` と環境変数 2 箇所のみ。将来の移行障壁にはならない
- 利用者は沼津市民。東京リージョンに揃えれば十分

### 最小構成で受け入れる制約

| 制約 | 影響 | 対処 |
| :-- | :-- | :-- |
| Vercel Hobby は非商用限定 | 市民向けの非営利サービスなら範囲内。運営主体が法人になったら Pro（20 ドル/月）へ | 運営主体の決定時に見直す |
| Supabase Free は 7 日間無アクセスで停止 | 日次ジョブ（Cloud Scheduler 6:00 JST）が毎朝 DB を叩くので実質止まらない | ジョブを止めるときは注意 |
| Supabase Free にバックアップが無い | 障害時に復旧できない | 議案データは再取り込みで復元可能。**インタビュー回答は復元不能**なので、回答が増えてきたら Pro（25 ドル/月、日次バックアップ）へ |
| 関数の実行時間上限 | AI の返答（推論モデル）が切れる可能性 | `maxDuration = 60` を設定済み。Fluid compute を有効にすれば 300 秒まで上げられる |
| 同一プロジェクトに staging/production を同居できない（Free は 2 プロジェクトまで） | 初期は production のみ | staging が要るときは 2 つ目のプロジェクトを使う |

## 2. コード側で入れた設定

- `web/vercel.json` / `admin/vercel.json`: `"regions": ["hnd1"]`（東京）
- `web/src/app/api/{chat,interview/chat,interview/complete}/route.ts`: `export const maxDuration = 60`

## 3. 公開手順

以下はアカウントの操作を伴うため、人が行う。順番どおりに進める。

### 3.1 Supabase（DB・Auth）

Dashboard の操作は不要で、Management API と CLI で完結する。

1. https://supabase.com/dashboard/account/tokens で Personal Access Token を発行し、`.env` に `SUPABASE_ACCESS_TOKEN` として置く（チャットや Git に出さない）
2. プロジェクト作成は Management API で行う（CLI の `supabase projects create` は新形式のトークン `sbp_v1_…` を受け付けないことがある）:
   `POST https://api.supabase.com/v1/projects` に `{name, organization_id, region: "ap-northeast-1", db_pass}`
3. API キーは `GET /v1/projects/{ref}/api-keys?reveal=true` の `publishable` / `secret`
4. マイグレーションは **DB へ直接接続**して流す。`supabase link` は使わない:
   `supabase db push --db-url "postgresql://postgres.<ref>:<pw>@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres" --include-all --yes`
   （session pooler の 5432。直結の `db.<ref>.supabase.co` は IPv6 のみ）
5. Auth の設定は `PATCH /v1/projects/{ref}/config/auth` で行う。**`supabase config push` は使わない**（CLI のトークン問題）ので、`supabase/config.toml` の `[auth]` を手で対応づける。最低限:
   - `site_url`、`uri_allow_list`（カンマ区切り）
   - **`external_anonymous_users_enabled: true`** — AI チャットは匿名セッションを要求する。無効だと `{"error":"Anonymous session required"}` になる
   - `mailer_autoconfirm: true`（`enable_confirmations = false` 相当）、`password_min_length: 6`、`rate_limit_anonymous_users: 30`
   - 反映まで数秒かかる。`POST {SUPABASE_URL}/auth/v1/signup` に `{"data":{}}` を投げて `is_anonymous: true` が返れば有効
6. Google ログインは OAuth クライアント作成後に同じ API で `external_google_enabled` 等を設定する

Management API は Python の `urllib` など既定の User-Agent だと Cloudflare に **403（error code 1010）** で弾かれる。`curl` で叩くこと。

初回（2026-09-02）の実績: 組織 `HyuCode` に `numazugikai`（ref `kkjxkkuumjwkjjnmxobv`、東京）を作成。接続情報は `.env.production`（gitignore 対象）に保存。

### 3.2 Vercel（web / admin）

CLI とトークンで完結する。Git 連携（GitHub App）は使わない。

1. https://vercel.com/account/tokens でトークンを発行し、`.env` に `VERCEL_TOKEN` として置く
2. プロジェクト作成は API で `rootDirectory` を指定する（monorepo のため）:
   `POST https://api.vercel.com/v11/projects` に `{name, framework: "nextjs", rootDirectory: "web"}`（admin も同様）
3. 環境変数は `POST /v10/projects/{id}/env?upsert=true` で `target: ["production"]` を指定して投入する（一覧は下表）
4. デプロイはリポジトリのルートで `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` を環境変数に置き、`vercel deploy --prod --yes --token $VERCEL_TOKEN`。`vercel link` は使わない（web と admin で同じルートを共有するため）
5. Settings → Functions で **Fluid compute を有効**にする（AI の返答が 60 秒を超える場合に備える。有効にしたら `maxDuration` を上げてよい）

初回の実績: `numazugikai-web` / `numazugikai-admin` を作成。既定ドメインは `https://numazugikai-web.vercel.app` / `https://numazugikai-admin.vercel.app`。

| 変数 | web | admin | 値 |
| :-- | :--: | :--: | :-- |
| `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_URL` | ✓ | ✓ | Supabase の Project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | ✓ | ✓ | Publishable key |
| `SUPABASE_SECRET_KEY` | ✓ | ✓ | Secret key（サーバー側のみ） |
| `OPENAI_API_KEY` | ✓ | ✓ | AI 解説・チャット用 |
| `NEXT_PUBLIC_WEB_URL` | ✓ | ✓ | web の公開 URL |
| `ADMIN_URL` | ✓ | ✓ | admin の公開 URL |
| `REVALIDATE_SECRET` | ✓ | ✓ | admin → web のキャッシュ無効化に使う共通のランダム文字列 |
| `ADMIN_MCP_TOKEN` | | ✓ | MCP 接続用トークン |
| `CHAT_DAILY_USER_COST_LIMIT_USD` / `CHAT_DAILY_TOTAL_COST_LIMIT_USD` / `CHAT_MONTHLY_TOTAL_COST_LIMIT_USD` | ✓ | | **必ず設定する**。未設定だと上限なし。初期値 1 / 10 / 100 |
| `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` | ✓ | | 公開前の確認期間だけ設定。公開時に外す |
| `NEXT_PUBLIC_GA_TRACKING_ID` | ✓ | | 任意 |
| `LANGFUSE_*` | ✓ | | 任意（LLM の監視） |

### 3.3 GitHub（CI のシークレット）

`deploy.yml` は **main への push** で本番へデプロイする（staging は当面置かない。develop → main の昇格は `/deploy` コマンドで PR を作る）。Settings → Environments → `production` に以下を登録する。

| シークレット | 値 |
| :-- | :-- |
| `SUPABASE_DB_URL` | session pooler の接続文字列（3.1 の 4 と同じ） |
| `VERCEL_TOKEN` | Vercel のトークン |
| `VERCEL_ORG_ID` | Vercel のアカウント ID（プロジェクト API の `accountId`） |
| `VERCEL_PROJECT_ID_WEB` / `VERCEL_PROJECT_ID_ADMIN` | 各プロジェクトの `id` |

worker 用（`deploy_worker.yml`）: `GCP_PROJECT_ID` `GCP_SA_KEY`。未設定なら worker のデプロイはスキップされる。

### 3.4 Cloud Run Job（日次の取り込み・分析）

`infra/cloud-run/README.md` の手順に従う。要点:

1. GCP プロジェクトを作り、`infra/cloud-run/config.example.env` を `config.env` にコピーして値を埋める（`DEPLOY_ENV=staging`）
2. `bash infra/cloud-run/provision.sh` を実行（API 有効化・SA・Secret・Job・Scheduler を作る）
3. 以降のイメージ更新は CI が行う

無料枠の目安: Cloud Run Jobs は月 18 万 vCPU 秒、Cloud Scheduler は 3 ジョブまで無料。日次で数分の実行なら収まる。

### 3.5 初回デプロイと管理者の作成

1. 初回は手元の CLI で（3.2 の 4）。以降は `main` への push で `deploy.yml` が走り、マイグレーション適用 → Vercel デプロイ（web / admin 並列）の順で進む
2. **最初の管理者を作る**。本家ドメインによる自動付与は廃止したので、Auth Admin API で作る:
   `POST {SUPABASE_URL}/auth/v1/admin/users`（`apikey` / `Authorization: Bearer` に Secret key）に
   `{"email", "password", "email_confirm": true, "app_metadata": {"roles": ["admin"]}}`。
   メール/パスワードで admin にログインできる。2 人目以降は admin の「管理者」ページから追加できる
3. admin にログインし、議案の公開状態を確認する

### 3.6 初回データ投入

本番の Supabase は空なので、内容テーブルをローカルから複製する。再取り込み（数時間）と解説の再生成（LLM 費用）が不要になり、ローカルで確認した内容がそのまま出る。

対象は「内容」のテーブルだけにする。利用者データ（`interview_*`、`chat_usage_events` など）や本家由来の `mirai_stances`、開発用の `preview_tokens` は複製しない。

```bash
# 1) ローカルのテスト残骸を落とす（統合テストが残した「テスト議案」など）
psql "$LOCAL_DB" -c "delete from bills where council_session_id is null and name like 'テスト議案%'"

# 2) ローカル Supabase のコンテナ内 pg_dump（サーバーと同じ PG17）でデータのみダンプ
#    Homebrew の pg_dump（v14）は PG17 をダンプできない
TABLES=(council_sessions committees factions council_members committee_memberships faction_votes \
        bills bill_contents bill_debates tags bills_tags ingestion_sources ingestion_runs)
ARGS=(); for t in "${TABLES[@]}"; do ARGS+=(-t "public.$t"); done
{ echo "SET session_replication_role = replica;";
  docker exec supabase_db_mirai-gikai pg_dump -U postgres -d postgres --data-only --no-owner --no-privileges "${ARGS[@]}"; } > dump.sql

# 3) 本番へ1トランザクションで復元
psql "$SUPABASE_DB_URL" --single-transaction -v ON_ERROR_STOP=1 -f dump.sql
```

- `--disable-triggers` は使わない。本番の `postgres` ロールはスーパーユーザーではなく、FK のシステムトリガーを無効化できずに失敗する。`session_replication_role = replica` なら FK 順序と `updated_at` トリガーを気にせず流せる
- 復元後に各テーブルの `count(*)` をローカルと照合する
- **復元後に web のキャッシュを無効化する**。データ投入前にサイトへアクセスしていると、空の結果が 10 分間キャッシュされて「議案が1つも見えない」状態になる:
  `curl -X POST -H "Authorization: Bearer $REVALIDATE_SECRET" https://<web>/api/revalidate`
- 生成列（`status_order` など）はダンプに含まれず、復元時に再計算される

初回（2026-09-02）の実績: 13 テーブル・議案 1,146 件（公開 826）を複製し、全テーブルで件数一致を確認。

以降の更新は Cloud Run Job の日次取り込みに任せる。手で取り込む場合:

```bash
pnpm --filter @mirai-gikai/topic-analysis-worker run ingest   # 議案・会期・会議録
pnpm --filter @mirai-gikai/topic-analysis-worker run explain  # AI 解説（LLM 費用が発生）
```

## 4. 費用の見積もり

| 項目 | 月額 |
| :-- | :-- |
| Vercel Hobby ×2 | 0 円 |
| Supabase Free | 0 円 |
| Cloud Run Job + Scheduler | 0 円（無料枠内） |
| **LLM（OpenAI）** | **利用量次第** |

LLM の内訳:

- AI チャット・インタビュー: 推論モデルのため 1 回あたり数十円。利用者数に比例する。**上限を必ず設定する**（例: 利用者ごと 1 日 1 ドル、全体で 1 日 10 ドル、月 100 ドル）
- 議案解説の生成: 一度きり。初回取り込み時に発生
- 日次のトピック分析: 増分のみで少額
