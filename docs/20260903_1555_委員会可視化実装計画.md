## 0. 結論

委員会可視化は、**どの委員会が、いつ開かれ、何を審査・調査し、どの議案にどのような
委員会審査結果を出したか**を中心にする。市議会議員の発言数や質疑数を競わせる機能は
作らない。

最初に行うべきことはグラフ実装ではなく、AmiVoiceの取得範囲の再検証である。現行コードは
詳細検索で全10種類の`sch_mean`と全会議種別を送る一方、
`packages/numazu-ingest/src/services/ingest-amivoice.ts`のコメントには「一部委員会しか
取得できない」という古い理解が残っている。実測では検索結果全体が1990年まで遡るが、
市公式案内が委員会記録について保証するのは2015年5月以降である。

したがって、検索ヒット総数だけで「全委員会を網羅」と表示してはならない。会議種別、
委員会名、期間、本文の有無を分類・照合し、公式保証範囲と実測確認範囲を別々に表示して
から公開する。

## 1. 目的

### 1.1 市民に提供する価値

- 議案が本会議議決の前に、どの委員会でいつ審査されたか分かる。
- 委員会ごとの開催日、議案、請願、所管事務調査等を時系列で探せる。
- 会期をまたぐ継続審査や、同じ議案を複数日にわたり審査した経過を追える。
- 開催予定、実際に開かれた会議、会議記録公開済みを区別できる。
- 元の会議記録、日程PDF、議案審議結果、期間限定の委員会映像へ移動できる。
- どの年度・委員会のデータが揃っているか、欠けているか分かる。

### 1.2 運営側の目的

- 現在`bills`に平坦化されている委員会情報を、会議・議題・審査イベント単位へ正規化する。
- 現在の委員会名と過去の委員会名を、改称時期を失わずに扱う。
- PDF、HTML検索DB、現況ページ、動画の更新・保持期間の違いを吸収する。
- 数値の意味、抽出方法、出典、取得日時、カバレッジを監査可能にする。

## 2. 利用者が答えを得たい問い

| 利用者の問い | 表示するもの | 表示しない・断定しないもの |
| :-- | :-- | :-- |
| これから傍聴・視聴できる委員会はあるか | 日時、委員会、場所、予定議題、公式案内 | 予定を開催実績として表示すること |
| 最近どの委員会が開かれたか | 実開催日、会議種別、記録公開状態 | 開催回数による委員会の優劣 |
| この議案はどこで審査されたか | 委員会、開催日、議題順、委員会審査結果、会議記録 | 質疑量だけから重要度・審査品質を断定すること |
| 委員会では何が扱われているか | 議題種別、政策分野、所管事務調査等の時系列 | 公開日程に載らない会合まで網羅したとの表示 |
| 数字はどこまで揃っているか | 年×委員会×資料種別のカバレッジ | 未取得を0件として埋めた集計 |

## 3. 対象・対象外と数え方

### 3.1 対象

- 公式「常任委員会」ページに掲載された現在の常任委員会
  - 総務経済委員会
  - 民生病院教育委員会
  - 建設水道危機管理委員会
  - 一般会計予算決算委員会
  - 特別会計企業会計予算決算委員会
- 議会運営委員会、特別委員会、過去に存在した委員会
- 開催予定と開催実績
- 議案、請願、報告、所管事務調査等の議題
- 議案の付託、審査日、委員会審査結果、公式会議記録へのリンク
- 会議記録に明示された開会・閉会時刻、場所、出席状況。取得できる場合に限る。
- 機械抽出した委員発言ブロック数。ただし後段の限定条件を満たす場合だけ公開する。

上記は2026年8月3日更新時点の公式ページに掲載された名称であり、UIやseedへ固定配列で
埋め込まない。リポジトリ文書に記載された4委員会と現行公式ページの5委員会に差があるため、
実装前に用語資料も公式情報に合わせて更新する。

### 3.2 対象外

- 市議会議員別の発言数、質疑数、出席率ランキング
- 発言量、会議時間、議案件数による市議会議員・委員会の評価スコア
- 会議記録本文、委員会映像、日程PDF紙面の複製掲載
- 非公開の協議、公式日程に原則掲載されない勉強会・相談等を推測で補うこと
- 動画再生数を傍聴者数・市民数として扱うこと
- 現在の委員会所属を過去の会議へ遡及適用すること

### 3.3 指標の定義

| 指標 | 定義 | 解釈上の注意 |
| :-- | :-- | :-- |
| 開催実績数 | published・verifiedで`status=held`・`held_on`ありの会議単位 | 同日に複数委員会があれば別会議。予定件数を混ぜない |
| 議題数 | 会議記録・日程の議題単位 | 複数議案の一括議題は、議題1件と関連議案複数件を分けて保持する |
| 付託議案件数 | 委員会へ付託された異なる議案数 | 同一議案の複数日審査を重複計上しない |
| 審査イベント数 | 1会議日の1議題として確認できた審査 | 議案件数や委員発言数とは異なる |
| 委員発言ブロック数 | 会議記録の発言者ラベルが委員と確認できた発言ブロック数 | 質問文の数でも、論点数でも、審査品質でもない。市議会議員別には表示しない |
| 会議時間 | 上記開催実績のうちverified根拠付きの`opened_at / closed_at`が両方ある会議の差 | 休憩を含む場合があり、実質審査時間とは限らない |
| 記録公開率 | 開催実績のうち公式会議記録URLを確認できた割合 | 未公開と取得失敗を別状態にする |

現行の`committee_qa_count`は実装上「委員の発言ブロック数」に近く、名称から想像される
「質問の数」ではない。新規画面で「質疑数」と表示せず、定義を修正した新モデルへ移す。

### 4.2 公式保証範囲と実測範囲

- **公式保証範囲**: 委員会会議記録は2015年5月以降。
- **実測した検索結果全体**: 詳細検索は1990年10月以降の本会議・委員会・その他を
  含む多数の文書を返し、2026年9月2日の調査では全会議種別合計1,787件だった。
- 1,787件は委員会だけの件数ではなく、今後も同じ件数である保証はない。
- 2015年5月より前の委員会らしい文書は、会議名・本文・公式カテゴリを個別確認し、
  `empirical_verified`になった範囲だけを表示する。
- 公開画面では「公式案内上の提供範囲」「本サービスで取得確認済みの範囲」「QA済みの
  可視化範囲」を別々に示す。

### 4.3 取得・更新方針

- 委員会日程は週1回、開会中は1日1回まで確認する。
- AmiVoiceは年単位で検索し、空の検索語、全会議種別、全10種類の`sch_mean`、30件ごとの
  ページングを使用する。
- 直近6か月は週1回、それ以前は月1回、内容ハッシュと公開状態を再確認する。
- 1秒以上の取得間隔、識別可能なUser-Agent、内容ハッシュによる再解析抑止を維持する。
- 動画URLは期限切れになり得るため、最終確認日時と`available / removed / unknown`を持つ。

### 5.2 公開前に必ず解消する不整合

1. `ingest-amivoice.ts`の203～206行付近には、検索で一部の委員会しか取れないという
   古いコメントが残る。一方、`amivoice-client.ts`は全10種類の`sch_mean`を送る。
   実装、テスト、調査ノート、運用手順のカバレッジ記述を同じ検証結果へ揃える。
2. `parse-amivoice-search.ts`にも「全件を取る方法は見つかっていない」という古いコメントが
   残る。`hitCount`、取得行数、重複数、最終ページ判定をテストしてから更新する。
3. 実測の1,787件を「委員会1,787件」と解釈しない。会議種別・会議名ごとに分類する。
4. 市公式案内の委員会提供開始は2015年5月である。実測ヒットが古くても、分類QAなしに
   公式保証範囲を拡張しない。

### 5.3 データモデル・処理のギャップ

- 会議日と議題のテーブルがなく、1議案を複数日に審査した履歴を表せない。
- `updateBillCommitteeReview`は`bills`の1つの件数と1つのURLを更新するため、複数会議では
  後の処理が前の値を上書きする。合計にも履歴にもならない。
- `committee_qa_count`の算出は、発言者名が「委員」で終わる発言ブロックを数える方式で、
  文法上の質問数や論点数を数えていない。
- `extractCommitteeBillReviews`は委員長の「議題といたします」という定型句に依存し、
  所管事務調査、一括議題、継続審査、表記変更への網羅性が未確認である。
- `ingestAmivoiceArchive`は検索ヒットの会議種別を明示分類せず、会期外の記録を捨てる。
  閉会中審査や、会期を越えた継続審査を保持できない。
- 議案番号と開催日のみの突合は、会期重複、会期外審査、番号表記揺れで誤結合し得る。
- `committees.short_name`は全期間で一意、`committee_memberships`は期間なしの複合主キーで、
  改称、再編、再任、途中交代を履歴化できない。
- 公開Webには委員会ページ、Repository、loader、route、サイトマップ、Open Data APIがない。
- Webアプリに専用グラフライブラリはない。初期版はHTML/CSSと表を優先する。

## 6. データモデル案

### 6.1 共通の会議・出典モデル

[一般質問可視化計画](./20260903_1555_一般質問可視化実装計画.md)と共通の
`council_meetings`、`council_meeting_revisions`、会議出典テーブルを使う。
安定した`council_meetings`本体へ可変属性を置かず、公開画面は各会議のpublished revisionから
次を読む。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `meeting_id` | uuid | 安定した会議正本 |
| `revision_number` | integer | 訂正を追記する版番号 |
| `council_session_id` | uuid nullable | 会期外・突合待ちはnullのまま保持する |
| `committee_id` | uuid nullable | 正規化済み委員会。突合待ちはnull |
| `kind` | enum | `committee` / `steering` / `all_members` / `other` |
| `scheduled_on` | date nullable | 公式日程上の予定日 |
| `held_on` | date nullable | 実開催を確認した日。予定段階ではnull |
| `scheduled_starts_at` | timestamptz nullable | 日程資料の予定開始日時 |
| `opened_at` / `closed_at` | timestamptz nullable | 公式記録にある場合のみ |
| `venue` | text nullable | 公式資料上の場所 |
| `display_title` | text | 複数資料を照合した表示名。資料ごとの原表記は根拠側 |
| `status` | enum | `scheduled` / `held` / `cancelled` / `unknown` |
| `source_support_status` | enum | `official_supported` / `empirical_verified` / `partial` / `unknown` |
| `qa_status` | enum | `pending` / `verified` / `rejected` |
| `publication_state` | enum | `draft` / `reviewed` / `published` / `superseded` |

共通0Bは`status=held`で`held_on`を必須とし、それ以外では
`held_on / opened_at / closed_at`を禁止する。`scheduled / cancelled`は`scheduled_on`を
必須とする。`closed_at`がある場合は`opened_at`も必須で、`closed_at >= opened_at`を
CHECKする。published revisionの状態・実開催日・開閉時刻は、同じ会議に束縛されたverified
根拠の観測値で支持されなければならず、根拠の削除・却下・差し替えでも
`council_meeting_publication_guard`が再検査する。開催実績はpublished・verified・held・
実開催日あり、会議時間はさらに開閉時刻が両方ある会議だけから集計する。
`kind in ('committee', 'steering')`の場合だけ`committee_id`を必須とし、
`plenary / all_members / other`ではnullを要求する。`kind=steering`はsteering委員会、
`kind=committee`はstandingまたはspecial委員会を参照することを0Bの遅延guardで保証する。

同じ会議に予定PDF、会議記録、映像の複数資料があるため、一般質問計画と同じく、
共通基盤0Bで次を分けて保持する。

- `council_meeting_source_occurrences`: `meeting_id`、`ingestion_source_id`、
  `source_occurrence_key`、`source_system`、`external_id`を持つ。論理資料内では
  `(ingestion_source_id, source_occurrence_key)`を一意にし、AmiVoiceの`vcsv`等は
  `(source_system, external_id)`の部分一意制約で版やURLをまたいで同じ会議へ結ぶ。
- `council_meeting_source_evidence`: 対象revision、出現ID、`source_version_id`、
  `parse_run_id`、`meeting_id`、`ingestion_source_id`、`role`、`source_evidence_key`、
  `evidence_revision`、`locator`、
  `availability`、`qa_status`、`extraction_method`、`verified_by`、
  `verified_at`と、資料ごとの観測会議名・日付・時刻・場所・状態を持ち、
  取得版ごとの根拠を追記する。

共通基盤0Aでは`ingestion_source_versions(id, ingestion_source_id)`、0Bでは
`council_meeting_revisions(id, meeting_id)`と
`council_meeting_source_occurrences(id, meeting_id, ingestion_source_id)`も一意にする。
会議根拠からこれら三組へ複合外部キーを張り、別会議のrevision・出現や別論理ソースの
取得版を誤って結べないようにする。出典側一意キーは対象revisionを含めず、同じ根拠が
二つのrevisionへ割り当てられないようにする。
`extraction_method=parser`なら`parse_run_id`を必須、`manual`ならnullとするCHECK制約を
会議根拠へ設ける。manual根拠をverifiedとして扱う場合は取得版、空でない`locator`、
確認者、確認日時を必須にする。

`council_meetings`に単一の出典、正規化属性、公開状態、外部システムを持たせない。日付や
会議名だけで会議を自動統合せず、安定外部IDがない資料は候補をQAする。訂正時は旧published
revisionを残して新draftを確認し、同一トランザクションで`superseded / published`を
切り替える。本表、revision、二つの出典テーブルはテーマ別PRで作らず、共通基盤0Bで
一度だけ追加する。
0B自身が`common:council_meeting_revision` consumer type、registry同期trigger、
registry完全一致を検査する
`council_meeting_publication_guard`を所有し、委員会固有consumer typeから共通会議根拠を
除外する。

取得版と解析実行を両方持つ会議根拠、名称・所属履歴、議題根拠、審査観測、参加者、
期間カバレッジ根拠はすべて、個別の外部キーに加えて`(parse_run_id, source_version_id)`から
共通`ingestion_parse_runs(id, source_version_id)`への複合外部キーを持つ。別取得版の
解析実行を誤って結ぶことをDBで拒否し、パーサー由来では両列を必須、人手登録の根拠だけ
`parse_run_id`をnull可とする。両列がnullableなcoverage根拠等には
`CHECK (parse_run_id is null or source_version_id is not null)`も設け、解析実行だけが
指定された行を拒否する。

`committees`は安定した委員会IDと現在表示に使う。改称前後を同一の制度的系譜として
まとめるか、別委員会として扱うかは`canonical_family_key`を追加して表示時に選べるように
する。名称一致だけで自動的に同一視しない。

名称別名と所属期間の根拠にある`source_version_id`は共通の
`ingestion_source_versions.id`、`parse_run_id`は`ingestion_parse_runs.id`をそれぞれ
`ON DELETE RESTRICT`で参照し、原文内の位置は`source_locator`に持つ。
パーサー由来の根拠行は`parse_run_id`必須かつevidence revision 1、人手登録だけnullを許可する。
manualのverified根拠は取得版、空でないlocator、確認者、確認日時を必須にする。URLと取得日を
各行に重複保存しない。同じ期間を名簿ページと会議記録の両方で確認した場合は、
正本slotやrevisionを複製せず`committee_membership_period_sources`を2行追加する。
名称・所属の根拠にも`extraction_method`とparser/manualの組合せCHECKを設ける。

aliasは`(committee_id, alias_key)`、revisionは`(alias_id, revision_number)`と
`(id, alias_id, committee_id)`を一意にする。source occurrenceは
`(ingestion_source_id, source_alias_key)`を対象alias IDなしで一意にし、一つの原資料内名称を
別委員会へ二重対応させない。版別根拠は`(alias_source_occurrence_id, source_version_id,
parse_run_id, evidence_revision) UNIQUE NULLS NOT DISTINCT`とし、revision・occurrence・取得版・
解析実行へ対象alias・委員会・論理ソースを含む複合外部キーを張る。

aliasごとに`UNIQUE (alias_id) WHERE publication_state='published'`の部分一意インデックスを
設け、採用中のrevisionを一つだけにする。
published alias revisionは`qa_status=verified`かつ確認者・確認日時・`valid_from`があり、
同じaliasへ結ばれたverified根拠を一つ以上持つ場合だけ許す。`valid_to < valid_from`を拒否し、正規化名が同じ
published aliasの有効期間は委員会IDをまたいで重複させない排他制約を置く。同じ開催日に
候補が二つ出る状態をDBで拒否し、期間不明・候補重複はstagingのQAキューに残す。訂正は
旧published revisionを`superseded`にして新revisionを追加し、原表記や期間を上書きしない。

所属モデルには次のDB制約を設ける。

所属期間の排他制約を初めて追加するmigrationが`btree_gist`の導入も所有し、
同じmigration内で次を実行する。Supabase Dashboardでの手動有効化や、開発者ごとの
既存ローカルDB状態には依存しない。

```sql
create schema if not exists extensions;
create extension if not exists btree_gist with schema extensions;
```

- slotは`(committee_id, membership_key)`を一意にし、revisionは
  `(membership_slot_id, revision_number)`と
  `(id, membership_slot_id, committee_id, council_member_id)`を一意にする。
  slotにも`(id, committee_id, council_member_id)`を一意にする。
- revisionに`valid_to is null or valid_to >= valid_from`のCHECK制約を置く。
- published revisionは`valid_from`を必須とする。公開時はverifiedな
  `primary`根拠が1件以上あることを遅延制約トリガーで保証する。serviceは同じ検証関数を
  事前確認に使うが、DB保証の代替にはしない。
- 所属revisionは根拠の確認者とは別に`reviewed_by / reviewed_at`を持つ。2列の
  片方だけを禁止し、`qa_status=verified`の場合と非draftは両方と
  `qa_status=verified`を必須にする。公開後の確認情報のnull化と内容更新を禁止する。
- slotごとにpublished revisionを一つだけ許す。`btree_gist`と`daterange`を使い、
  **published revisionだけ**を対象として、同一`committee_id`・`council_member_id`の
  有効期間が重複しない除外制約を設ける。`valid_to`は在任を含む終了日とし、
  `daterange(valid_from, valid_to, '[]') WITH &&`で判定する。`valid_to=null`は上限なし、
  `valid_from=valid_to`は単日の有効期間として扱う。前行の`valid_to`と次行の`valid_from`が
  同日ならその日が二重所属となるため拒否し、翌日開始だけを連続期間として許す。
  旧supersededと新publishedの期間重複は許す。
- source occurrenceは`(ingestion_source_id, source_membership_key)`を対象slotなしで一意にし、
  同じソース内所属枠を取得版ごとに別slotへ割り当てない。根拠の出典側一意制約は対象IDを
  含めず、`(membership_source_occurrence_id, source_version_id, parse_run_id,
  evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。parser根拠のrevisionは1、人手再解釈は
  番号を増やす。occurrence・取得版・解析実行へ論理ソースを含む複合外部キーを張り、
  `(membership_revision_id, membership_slot_id, committee_id, council_member_id)`からrevision、
  `(membership_slot_id, committee_id, council_member_id)`からslotへ複合外部キーを張る。

既存の`committee_memberships`には有効開始日の根拠がない。移行時は期間を推測せず、
安定slotの候補と`valid_from=null`、`qa_status=pending`、`publication_state=draft`の
revision候補として保持し、
根拠行は作らない。
一次資料で期間と出典を確認した行だけを`verified`とし、公開viewに含める。

### 6.3 議題と関連議案

#### `committee_agenda_items`

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` | uuid | 主キー |
| `meeting_id` | uuid | `council_meetings.id`。監査履歴を連鎖削除しない`ON DELETE RESTRICT` |
| `canonical_item_key` | text | 複数出典をまたぐ同一議題の正本キー |
| `created_at` | timestamptz | 正本作成日時 |

順番、種別、要約と公開版選択は追記型の`committee_agenda_item_revisions`へ置く。

| 列 | 型 | 意味 |
| :-- | :-- | :-- |
| `id` / `agenda_item_id` / `meeting_id` | uuid | revision、安定議題、同一会議を保証するキー |
| `revision_number` | integer | 議題内の追記番号。1以上 |
| `item_order` | integer nullable | 公式記録上の順番 |
| `kind` | enum | `bill` / `petition` / `report` / `jurisdictional_study` / `consultation` / `other` / `unknown` |
| `public_summary` | text nullable | 人手確認した独自要約 |
| `qa_status` | enum | `pending` / `verified` / `rejected` |
| `publication_state` | enum | `draft` / `reviewed` / `published` / `superseded` |
| `reviewed_by` / `reviewed_at` | uuid / timestamptz nullable | 議題revision自身の確認者と確認日時 |

`canonical_item_key`は出典システム名を含めず、同一会議内の公式議題ID、
確定した関連議案キー、またはQA済みの議題枠識別子から作る。件名類似だけで
自動統合せず、候補はQA後に一つの正本へ結ぶ。正本は
`(meeting_id, canonical_item_key)`を一意にし、根拠との複合外部キー用に
`(id, meeting_id)`も一意にする。revisionは`(agenda_item_id, revision_number)`と
`(id, agenda_item_id, meeting_id)`を一意にし、議題ごとのpublished revisionを一つだけ許す。
published revisionで`item_order`が非nullの場合だけ`(meeting_id, item_order)`を一意にし、
旧publishedと同じ順序の新draftを並行してQAできるようにする。順番が資料にないときは
番号を作らない。

取得版と解析実行の履歴は正本行へ上書きせず、
`committee_agenda_item_sources`へ追記する。

その前段に`committee_agenda_item_source_occurrences(id, agenda_item_id, meeting_id,
meeting_source_occurrence_id, ingestion_source_id, source_item_key)`を置き、
`(meeting_source_occurrence_id, source_item_key)`を対象IDなしで一意にする。別parse runでも
同じソース内議題を二つの安定正本へ割り当てない。候補はstagingでQAしてから対応を確定する。
複合外部キーの参照先として、source occurrenceには
`(id, agenda_item_id)`と
`(id, agenda_item_id, meeting_id, ingestion_source_id)`を、それぞれ記載した列順の
`UNIQUE`として設ける。

| 列 | 意味 |
| :-- | :-- |
| `id` / `agenda_item_revision_id` / `agenda_item_id` | 根拠行、対象revision、安定議題のキー |
| `meeting_id` | 正本議題と会議のソース内出現が同じ会議に属することを保証するキー |
| `agenda_item_source_occurrence_id` | 安定したソース内議題との対応 |
| `ingestion_source_id` | 論理ソース。source occurrence・取得版との整合確認用 |
| `source_version_id` / `parse_run_id` | 取得版と解析実行。どちらも`ON DELETE RESTRICT` |
| `evidence_revision` | 同じ物理根拠の人手再解釈番号。parserでは1 |
| `source_locator` | 公式記録内のページ・議題区間 |
| `title_official_hash` | 取得版ごとの原表題変更の検知用 |
| `outcome_raw` | 議題単位で明示された原表記。正規化した手続結果の正本にしない |
| `extraction_method` / `qa_status` | `parser` / `manual`と根拠行の確認状態 |

source occurrenceからは、
`(agenda_item_id, meeting_id)`を`committee_agenda_items(id, meeting_id)`へ、
`(meeting_source_occurrence_id, meeting_id, ingestion_source_id)`を
`council_meeting_source_occurrences(id, meeting_id, ingestion_source_id)`へ、
それぞれ同じ列順で複合外部キーとして張る。版別根拠からは、
`(agenda_item_revision_id, agenda_item_id, meeting_id)`を
`committee_agenda_item_revisions(id, agenda_item_id, meeting_id)`へ、
`(agenda_item_source_occurrence_id, agenda_item_id, meeting_id, ingestion_source_id)`を
`committee_agenda_item_source_occurrences(id, agenda_item_id, meeting_id,
ingestion_source_id)`へ、それぞれ同じ列順で複合外部キーとして張る。
後者の4列に`ingestion_source_id`を冗長保持することで、別会議・別論理ソースの議題根拠を
結べないようにする。さらに版別根拠の`(source_version_id, ingestion_source_id)`を
取得版の`ingestion_source_versions(id, ingestion_source_id)`へ同じ列順で参照する。版別根拠は
`(agenda_item_source_occurrence_id, source_version_id, parse_run_id,
evidence_revision) UNIQUE NULLS NOT DISTINCT`とする。
パーサー由来は`parse_run_id`を必須とし、
`evidence_revision=1`に固定する。人手登録はparse runをnullとし、再解釈時はrevisionを増やす。
新しい取得版またはパーサー版の結果は
`parse_run_id`単位でstagingし、安定キーによる差分確認後にrevisionの公開版を切り替える。
削除候補を即時削除せずQAへ送る。
議題revisionも所属revisionと同じ確認者・確認日時の組合せCHECK、非draftの
verified必須、公開後の確認情報・内容凍結契約に従う。独自要約を含む訂正は
確認情報付きの新revisionで行う。

#### `committee_agenda_item_bill_links` とrevision・根拠

一括議題と誤突合の訂正を扱うため、議題内の関連枠を安定正本、リンク先を追記型revisionにする。
`committee_agenda_item_bill_links`は`id`、`agenda_item_id`、`link_key`を持ち、
`(agenda_item_id, link_key)`と`(id, agenda_item_id)`を一意にする。議案番号や
候補`bill_id`だけから正本を作らない。
ソース内の関連枠は`committee_agenda_item_bill_source_occurrences(id, link_id,
agenda_item_id, agenda_item_source_occurrence_id, source_bill_key)`へ一度だけ対応付け、
`(agenda_item_source_occurrence_id, source_bill_key)`を対象IDなしで一意にする。さらに
`(id, link_id, agenda_item_id, agenda_item_source_occurrence_id)`を一意にし、
`(link_id, agenda_item_id)`から安定リンク枠へ、
`(agenda_item_source_occurrence_id, agenda_item_id)`から議題のsource occurrenceへ
複合外部キーを張る。

各候補・確認・訂正は`committee_agenda_item_bill_link_revisions`へ追記する。

| 列 | 制約・意味 |
| :-- | :-- |
| `link_id` / `agenda_item_id` | 安定リンク枠と安定議題。複合外部キーで整合させる |
| `agenda_item_revision_id` | 根拠に対応する議題revision |
| `revision_number` | リンク枠内の追記番号。1以上 |
| `bill_id` | `bills.id` への外部キー。監査履歴を連鎖削除しない`ON DELETE RESTRICT` |
| `association_scope` | `exact` / `grouped` / `unknown`。一括議題の観測値を議案固有値にしない |
| `match_method` | `exact_fields` / `manual` / `candidate` |
| `confidence` | 候補生成の補助値。公開判定に使わない |
| `evidence_text` | 年・会期・議案番号等を照合した根拠 |
| `qa_status` / `publication_state` | 共通の確認状態と公開版選択 |
| `reviewed_by` / `reviewed_at` | 人手確認者と確認日時 |

revisionは`(link_id, revision_number)`と
`(id, link_id, agenda_item_id, agenda_item_revision_id)`を一意にし、
`(link_id, agenda_item_id)`から安定リンク枠へ、
`(agenda_item_revision_id, agenda_item_id)`から議題revisionへ複合外部キーを張る。
そのため議題revision側に`(id, agenda_item_id)`の一意制約も追加する。
安定リンク枠ごとにpublished revisionを一つだけ許す。

版別根拠は`committee_agenda_item_bill_link_sources(id, link_revision_id,
link_id, agenda_item_id, agenda_item_revision_id, bill_source_occurrence_id,
agenda_item_source_occurrence_id, agenda_item_source_id, evidence_revision, raw_bill_number,
raw_relationship, qa_status, verified_by, verified_at)`へ追記する。
`agenda_item_revision_id`と`agenda_item_source_occurrence_id`は、親テーブル間のjoinでしか
比較できない値にしないため、根拠行へ冗長保持する。次の三本の複合外部キーで、
議題revision、議題根拠、ソース内関連枠、安定議題が同じ組であることをDBで保証する。

- `(link_revision_id, link_id, agenda_item_id, agenda_item_revision_id)`から
  `committee_agenda_item_bill_link_revisions`の同じ4列へ参照する。
- `(bill_source_occurrence_id, link_id, agenda_item_id,
  agenda_item_source_occurrence_id)`から
  `committee_agenda_item_bill_source_occurrences`の同じ4列へ参照する。
- `(agenda_item_source_id, agenda_item_revision_id, agenda_item_id,
  agenda_item_source_occurrence_id)`から`committee_agenda_item_sources`の同じ4列へ参照する。

参照先の三表には、上記複合外部キーと同じ列順の`UNIQUE`を設ける。
版別根拠は`(bill_source_occurrence_id, agenda_item_source_id, evidence_revision)`を一意にし、
parser根拠はrevision 1、人手再解釈は番号を増やす。同じソース内関連枠は安定occurrenceにより
別リンク正本へ移らず、同じリンク内では旧根拠を残して訂正revisionへ新根拠を追加できる。

`match_method=candidate`または`association_scope=unknown`は必ず
`qa_status=pending, publication_state=draft`とし、`exact_fields`も人手確認なしでは公開しない。
公開には`qa_status=verified`、`publication_state=published`、`reviewed_by / reviewed_at`を必須にする。
さらにpublishedリンクrevisionには、同じ議題revision・source occurrenceに属する
`qa_status=verified`のリンク根拠を一つ以上必須にし、遅延constraint triggerで保証する。
公開切替repositoryは同じ検証関数を事前確認に使うが、DB保証の代替にはしない。
訂正時は旧revisionを`superseded`として残し、新しい`bill_id`のrevisionへ公開版を切り替える。

#### `committee_agenda_item_classification_sets` / `committee_agenda_item_topics`

議題の政策分野は、一般質問計画が共通基盤として所有する`policy_topics`と
`topic_classification_runs`を参照する。分類セットは`id`、`agenda_item_revision_id`、
`classification_run_id`、`taxonomy_id`、`qa_status`、`publication_state`、`reviewed_by`、
`reviewed_at`を持ち、
`(agenda_item_revision_id, classification_run_id)`と`(id, taxonomy_id)`を一意にする。多対多の分野は
`committee_agenda_item_topics(classification_set_id, taxonomy_id, policy_topic_id,
confidence)`へ置く。一般質問計画と同じtaxonomy複合外部キー契約を適用し、分類run、
分類セット、政策分野が別taxonomy版ならDBで拒否する。

分類セットは
`(agenda_item_revision_id, taxonomy_id) WHERE publication_state='published'`の部分一意制約にし、
別taxonomy版のセットを併存できるようにする。ただし公開view / APIはこの集合を
直接読まず、一般質問計画が共通所有する`topic_classification_releases`のうち
`consumer_type=committee_agenda_item`でpublishedの一行から読む。

委員会migrationは
`committee_classification_population_members(snapshot_id, agenda_item_revision_id, ordinal)`と
`committee_classification_release_items(release_id, population_snapshot_id, taxonomy_id,
agenda_item_revision_id, classification_set_id nullable, coverage_disposition,
exclusion_reason, reviewed_by, reviewed_at)`を追加する。共通の専用snapshot生成関数は
型付き会期または日付範囲、選択ルール版、関数が設定する生成時刻により、
そのトランザクションでpublished・verifiedかつ適格な親会議を持つ議題revisionを
一括列挙する。実績releaseの適格親はpublished・verified・held・実開催日ありに限定し、
予定は別planned consumer・releaseへ分離する。memberの並び順、件数、順序付きID hashはDBが生成し、呼び出し側の
指定とsnapshot / memberの後編集を禁止する。

release itemは`(release_id, agenda_item_revision_id)`を一意にし、
`(population_snapshot_id, agenda_item_revision_id)`からsnapshot memberへ複合外部キーを張る。
classifiedなら同じtaxonomyのcompleted runから作られたverifiedセット、
`not_applicable / excluded`ならセットなしと空でない理由・確認者・確認日時を
要求する。draft / reviewed releaseは`reviewed / published`セットを参照できるが、
published時は全classifiedセットをpublishedに限定する。guardはsnapshot memberとitemの
双方向`EXCEPT`が0件であることを検査する。releaseの識別・taxonomy・snapshot・itemは
draftの間だけ編集でき、reviewed以降の内容変更、draft巻き戻し、物理削除を禁止する。
委員会consumerのactive releaseは一つだけとし、APIはrelease ID、taxonomy ID・version、
DB生成snapshotの範囲・生成時刻・件数を返す。
分類runを差し替えた場合は旧セット全体を`superseded`にするため、旧topic Aと新topic Bが
同時公開されない。AI・ルール分類は`qa_status=verified`になるまで公開viewへ含めず、
分類run自体も一般質問計画で定義する`status=completed`の場合だけ採用する。
件名だけから政策上の結論や委員会の評価を生成しない。
`committee_agenda_item_topics`は親セットが`draft`かつ参照runが`running`の間だけ
INSERT / UPDATE / DELETEを許し、runがterminal化した後はdraftセットでもtopic行集合と
全列を不変にする。classification setの新規INSERTと議題revision・run・taxonomyの変更も
参照runがrunningの間だけ許し、terminal後はQA・publication・reviewerの状態遷移だけを許す。
分類訂正は既存行の編集ではなく、新しいrun・セット・topic行の追加と公開版切替で行う。
新版は母集団全件をreviewedセットで準備してから、セット・releaseの旧新を
同一トランザクションでsuperseded / publishedへ切り替える。一般質問consumerと
active taxonomyが異なる期間はテーマ別に
版を表示し、テーマ横断の政策分野系列へ合算しない。

| `id` | uuid | 主キー |
| `agenda_item_id` | uuid | `committee_agenda_items.id`。監査履歴を連鎖削除しない`ON DELETE RESTRICT` |
| `agenda_item_revision_id` | uuid | 指標を公開する議題revision |

| `reviewed_by` / `reviewed_at` | uuid / timestamptz nullable | 観測値自身の確認者と確認日時 |

`committee_agenda_item_sources`に
`(id, agenda_item_revision_id, agenda_item_id, meeting_id, source_version_id)`の
一意制約を置き、審査観測の同じ五列から複合外部キーを張る。さらに
`(parse_run_id, source_version_id)`から共通解析実行へ複合外部キーを張るため、別会議・
別議題の資料や別取得版の解析実行を指標へ結べない。出典側の一意制約は対象議題を含めず、
`(agenda_item_source_id, parse_run_id, metric_definition_version, evidence_revision)
NULLS NOT DISTINCT`とし、
同じ解析実行の再試行で観測行を重複作成しない。parser/manualの組合せCHECKも設ける。
parser観測のevidence revisionは1に固定し、人手再計数は番号を増やす。
同じ議題には公開中の観測行を1件だけ許す
部分一意インデックス`UNIQUE (agenda_item_id) WHERE publication_state = 'published'`を
設け、版切替は同一トランザクションで旧版を
`superseded`、新版を`published`にする。
審査観測は`reviewed_by / reviewed_at`の片方だけを禁止し、
`qa_status=verified`の場合と非draftは両方と`qa_status=verified`を必須にする。公開後の
確認情報のnull化と観測値の上書きを拒否し、再計数は新しい観測行へ切り替える。

CHECK制約で発言ブロック数の負値を禁止する。`observation_status=observed`では
`member_utterance_block_count`を必須とし、`unknown`または`not_applicable`のときは
発言ブロック数をnullとする。0は議題区間を最後まで確認した観測結果としてのみ保存する。

市議会議員別の発言ブロック数は公開集計テーブルに持たせない。内部で発言者区分のQAに
必要な場合も、公開viewは会議・議題単位に限定する。

既存の`bills.committee_qa_count`と`committee_minutes_url`は互換用キャッシュとして当面
残し、新テーブルを正とする。移行後は、QA済み審査イベントの合計・代表URLから生成する
viewまたは明示的な同期処理に切り替え、直接上書きを廃止する。

### 6.5 参加者・出席状態

参加者も安定slotと追記型観測を分ける。`council_meeting_participant_slots`は
`id`、`meeting_id`、`council_member_id nullable`、`participant_key`を持ち、
`(meeting_id, participant_key)`を一意にする。空キーを拒否し、議員を確定した場合は
`participant_key = 'member:' || council_member_id`の決定式CHECKと
`UNIQUE (meeting_id, council_member_id) WHERE council_member_id IS NOT NULL`を設ける。
未確定者のキーはQA済みsource occurrenceとソース内人物キーから決定的に作る。後日
議員を同定した場合は旧slotを書き換えず、新slotと訂正履歴へ公開観測を切り替える。
訂正され得る役割・出席状態はキーに含めず、氏名表記だけで別人を統合しない。
資料内の人物枠との安定した対応は
`council_meeting_participant_source_occurrences(id, participant_slot_id, meeting_id,
meeting_source_occurrence_id, ingestion_source_id, source_participant_key)`へ置き、
`(meeting_source_occurrence_id, source_participant_key)`を対象slotなしで一意にする。
`council_meeting_participant_observations`を設ける場合は、次を守る。

- `participant_slot_id`、`meeting_id`、`participant_source_occurrence_id`、
  `meeting_source_evidence_id`、`ingestion_source_id`、`source_version_id`、
  `parse_run_id`、`evidence_revision`、`council_member_id nullable`、
  `observed_name`、`display_name`、`role`、`attendance_status`、`source_locator`、`qa_status`、
  `publication_state`、`extraction_method`、`verified_by`、`verified_at`を持つ。
- `role`は`chair / vice_chair / member / administration / witness / secretariat / other /
  unknown`とし、会議上の役割を表す。
- `attendance_status`は`present / absent / excused / unknown`とし、役割と出席状態を混ぜない。
- 共通の`council_meeting_source_evidence`に`(id, meeting_id, source_version_id)`の一意制約を
  置き、参加者観測の同じ三列から複合外部キーを張る。参加者slotにも
  `(id, meeting_id, council_member_id)`を`NULLS NOT DISTINCT`で一意にし、観測の同じ三列から
  複合外部キーを張って同会議・同一議員または両方nullを保証する。解析実行は
  `(parse_run_id, source_version_id)`の複合外部キーで取得版と一致させる。
- 出典側の一意制約は対象slotを含めず、`(participant_source_occurrence_id,
  source_version_id, parse_run_id, evidence_revision) NULLS NOT DISTINCT`とする。同じソース内
  人物枠を二つのslotへ割り当てず、別取得版と再解析は追記できる。occurrence、会議根拠、
  取得版、解析実行へ会議・論理ソースを含む複合外部キーを張る。parser由来はrevision 1、
  人手再解釈は番号を増やす。slotごとのpublished観測は一つだけとし、旧観測を残して訂正できる。
- 原資料内の位置は`source_locator`に持ち、パーサー由来は`parse_run_id`必須、人手登録は
  nullとする。parser/manualと共通QA・公開状態の組合せはCHECK制約で保証する。
- 個人別出席率ランキングは作らない。会議詳細で公式記録上の構成を確認する用途に限る。
- 当局出席者は役職単位を基本とし、不要な個人情報を保持しない。

### 6.6 0・null・該当なし

- `null`: 資料未公開、未取得、解析失敗、判断不能。
- `0`: 対象資料を取得して会議・議題を確認し、該当する発言ブロック等が本当に無かった。
- `not_applicable`: 指標がその議題に適用されない。
- `cancelled`: 予定されたが中止を公式確認した。

`committee_qa_count=null`を0へ変換しない。会議行や議題行が一つもない期間も
状態を保存できるよう、対象の正本`committee_period_coverage`と追記型の
`committee_period_coverage_observations`を分けて設ける。

| 列 | 意味 |
| :-- | :-- |
| `committee_id` | 個別委員会。全委員会の取得監査はnull |
| `period_start` / `period_end` | 監査対象期間。期間逆転をCHECKで禁止する |
| `source_kind` | `schedule` / `minutes` / `agenda` / `bill_match` / `video` |

正本は`UNIQUE NULLS NOT DISTINCT (committee_id, period_start, period_end, source_kind)`により、
全体行を含む同じ監査対象を重複作成しない。対象付き根拠から参照するため
`(id, period_start, period_end, source_kind)`も一意にする。観測行は次を持つ。

| 列 | 意味 |
| :-- | :-- |
| `coverage_id` | `committee_period_coverage.id` |
| `period_start` / `period_end` / `source_kind` | 正本と同じ監査対象を複合FKで固定する冗長キー |
| `observation_key` | parse runまたは手動監査操作から作る決定的な冪等キー |
| `state` / `record_presence` | 共通基盤0Aのカバレッジ状態と`present / absent / unknown` |
| `support_scope` | `official_supported` / `empirical_verified` / `partial` / `unknown` |
| `expected_count` / `matched_count` | 公式件数と取得・突合件数。不明な場合はnull |
| `checked_at`, `qa_status`, `reviewed_by`, `reviewed_at` | 監査・確認履歴。`checked_at`は必須 |
| `publication_state` | `draft` / `reviewed` / `published` / `superseded` |

`(coverage_id, observation_key)`と
`(id, coverage_id, period_start, period_end, source_kind)`を一意にし、観測から正本へも
対象ID一式の複合外部キーを張る。同じcoverage対象で公開中の観測を一つだけ許す。再監査時は旧観測を上書きせず
`superseded`へ切り替える。非draft観測は`qa_status=verified`かつ
`reviewed_by / reviewed_at`が両方非nullの場合だけ許すCHECKを設け、未公表・取得不能・
対象外の観測も匿名の承認で公開できないようにする。

別委員会・別期間の資料を根拠へ流用できないよう、
`committee_period_coverage_source_occurrences`に`id`、`coverage_id`、
`period_start`、`period_end`、`source_kind`、`ingestion_source_id`、
`source_coverage_key`を持たせる。`(ingestion_source_id, source_coverage_key)`を
coverage IDなしで一意にし、期間とsource kindを含む複合外部キーでcoverage正本へ結ぶ。
`(id, coverage_id, period_start, period_end, source_kind, ingestion_source_id)`も一意にし、
観測根拠から対象付きで参照できるようにする。
`committee_period_coverage_observation_sources`は`observation_id`、`coverage_id`、
`period_start`、`period_end`、`source_kind`、`coverage_source_occurrence_id`、
`ingestion_source_id`、`source_version_id`、`parse_run_id`、`evidence_revision`、
`evidence_role`、`source_locator`、`extraction_method`、`qa_status`、
`verified_by`、`verified_at`を持つ。観測・occurrence・取得版・解析実行へ対象ID一式を
含む複合外部キーを張り、同じ物理根拠を二つのcoverage正本へ割り当てない。
parser/manual、追記型一意制約、不変性は他の版別根拠と同じ契約にする。
公開集計はcoverage観測が
`state=collected`、`qa_status=verified`、
`publication_state=published`で、指標観測も`publication_state=published`かつ
`observation_status=observed`の場合だけを分母にする。「対象200議題中、記録確認済み
150議題」のように確認済み分母を併記する。
publishedかつ`collected / partial`では論理ソース、取得版、`checked_at`を必須にし、
対象期間・source kindへ束縛されたverified primary根拠を一つ以上必須にする。
根拠版なし、別期間資料、別source kindによる「確認済み0件」を拒否する。

### 6.7 公開整合、原本保持、安定ID

表をまたぐ公開条件はDBで保証する。共通0Bが所有する
`council_meeting_publication_guard`に加え、委員会migrationで次のguard関数を作る。

- `committee_alias_publication_guard`: published alias revisionをverifiedかつ確認者・確認日時
  と`valid_from`ありに限定し、同じalias・委員会・source occurrenceへ結ばれたverified根拠と、正規化名の
  有効期間が他委員会のpublished aliasと重複しないことを要求する。
- `committee_membership_publication_guard`: published所属revisionに、同じslotへ結ばれた
  verified primary根拠とrevision自身の確認者・確認日時を要求する。
- `committee_agenda_item_publication_guard`: published議題revisionに、同じ会議・
  source occurrenceへ結ばれたverified根拠とrevision自身の確認者・確認日時を要求する。
  親会議revisionはpublished・verifiedで、
  `kind=committee / steering`、対応する`committee_id`があり、状態は
  `scheduled / held / cancelled`に限定する。親会議revisionの切替でも再検査する。
- `committee_bill_link_publication_guard`: published関連議案revisionに、同じ議題revision・
  source occurrenceへ結ばれたverified根拠を要求する。参照するまさにその
  `agenda_item_revision_id`がpublished・verifiedで、議題guardと親会議条件を満たすことも要求する。
- `committee_classification_publication_guard`: published分類セット自身を
  `qa_status=verified`かつ`reviewed_by / reviewed_at`が両方非nullに限定し、
  `status=completed`の同一taxonomyのrun、`published_at`が非nullのtaxonomy、
  published議題revisionを要求する。
- `committee_classification_release_guard`: 委員会consumerのpublished releaseを一つに限定し、
  公開済みtaxonomy、DB生成snapshotとitemの双方向`EXCEPT`が0件、同じtaxonomyの
  completed・verified・published分類セットまたは確認済み除外を全itemに要求する。
  snapshot・member・release・item・set・議題revision・親会議の変更でも再検査する。
- `committee_review_observation_publication_guard`: published審査観測に同じ議題revision・
  取得版のverified根拠、観測自身の確認者・確認日時を要求し、`observed`時の
  数値制約を検査する。参照する議題revision自身はpublished・verifiedかつ議題guard適格、
  親会議はpublished・verified・held・実開催日ありに限定する。
- `committee_participant_publication_guard`: published参加者観測に同じ会議・人物source
  occurrenceへ結ばれたverified根拠を要求し、親会議をpublished・verified・held・
  実開催日ありに限定する。
- `committee_coverage_publication_guard`: publishedの`collected / partial`観測に同じ対象の
  対象付きsource occurrenceを介した同じ委員会範囲・期間・source kindのverified primary
  根拠版を要求し、`present / absent`の意味を一致させる。

各関数は対象の正本・revision・観測・親revision・分類セット・分類topic子行・
classification population snapshot・member・release・item・根拠の
`INSERT / UPDATE / DELETE`後に発火する
`CONSTRAINT TRIGGER DEFERRABLE INITIALLY DEFERRED`から呼ぶ。最後のverified根拠の削除・
`rejected`化、別正本への付け替えもコミット時に拒否する。repository/serviceは同じ関数を
公開切替前の早期確認に使うが、DB保証の代替にはしない。manual根拠をverifiedとして数える
場合は取得版・根拠位置・確認者・確認日時を必須にする。

委員会固有のconsumer typeを共通0Aの`source_artifact_consumer_types`へ登録する。
通常同期triggerは公開判定に数えるparser根拠を
`published_source_version_references`へ登録し、`superseded / rejected`化でreleaseする。
各publication guardは公開集合とregistryの完全一致も検査し、共通の保持guardへ
委員会テーブル名をハードコードしない。委員会固有typeにはalias・所属・議題・関連議案・
審査・参加者・期間coverageの根拠を含めるが、0Bが所有する会議revision根拠は含めない。

安定正本の親ID・stable keyと、会議・alias・所属・議題・関連議案・参加者の全source occurrenceの
正本ID一式・`ingestion_source_id`・ローカルキーは`prevent_stable_identity_update`で
通常UPDATEを拒否する。revisionと版別根拠も対応先・取得版・解析実行・抽出内容の上書きを
禁止し、QA・公開・確認情報だけを状態遷移で変更する。誤突合候補はstagingで確認し、
監査対象の物理DELETEを行わない。aliasも対象委員会・正規化名・期間・取得版・解析実行・
原表記を通常UPDATEせず、訂正は新しいrevisionと根拠行として追記する。その他の訂正も新revisionと
`superseded / rejected`で残す。

新規テーブルはすべてRLSを有効化し、ポリシーは定義しない。公開schemaに
集計viewを作る場合は`WITH (security_invoker = true)`を必須とし、
`anon`・`authenticated`への直接権限を付与しない。DB functionは原則
`SECURITY INVOKER`とする。`SECURITY DEFINER`が必要な場合は`search_path`を固定し、
`PUBLIC`・`anon`・`authenticated`から`EXECUTE`をrevokeして`service_role`のみにgrantする。

## 7. 取り込み・正規化・人手QA

### 7.1 Phase 0のカバレッジ監査

1. 年ごとにAmiVoice詳細検索を実行し、`hitCount`、取得件数、重複件数、最古・最新日を保存する。
2. 全10種類の`sch_mean`と全会議種別がPOSTされることをrequest-level testで固定する。
3. 全検索ヒットを、本会議、常任委員会、議会運営委員会、特別委員会、全員協議会、
   不明へ分類する。
4. 年×会議種別×正規化済み委員会名の件数を出し、公式検索画面で年ごとに照合する。
5. 2015年5月以降は公式保証範囲、以前は実測確認範囲として別状態を付ける。
6. 調査ノート、parserコメント、serviceコメント、運用手順の矛盾を解消する。

`hits.length === hitCount`だけでは分類の正しさを保証しない。会議名が空の行、本文が空の行、
同じ`vcsv`の重複、検索画面にだけある行を別々に検出する。

### 7.2 会議・日程取り込み

1. 年度日程PDFを取得し、`ingestion_source_versions`と
   `ingestion_parse_runs`を登録してから、予定会議を`status=scheduled`でstagingへ入れる。
2. PDF内の各会議とAmiVoiceの`vcsv`を、それぞれ
   `council_meeting_source_occurrences`へ冪等にupsertする。取得版ごとの根拠は
   `council_meeting_source_evidence`へ追記する。
3. AmiVoice会議名を開催日と`committee_aliases`の有効期間で正規化する。
4. 会議記録のヘッダー・補助フレームから、開催日、開閉時刻、場所、出席状況を抽出する。
5. 予定と実績は安定外部IDを優先し、無い場合だけ委員会、日付、時刻で候補突合する。
   不一致はQAキューへ送り、日付や名称だけで自動統合しない。
6. 実績を確認しても予定レコードを削除せず、同一会議へ根拠を追加し状態を更新する。
7. 会期外会議も捨てず、`council_session_id=null`で保持し後から関連を確認する。

### 7.3 議題・議案突合

- 委員長の議題宣告、議事日程、議案番号を組み合わせて議題区間を抽出する。
- 抽出時に会議ソース内の`source_item_key`を決定的に生成し、
  `parse_run_id`とともにstagingする。
- 一括議題は1つの`committee_agenda_items`と複数の関連議案として保存する。
- 突合キーは議案番号だけにせず、会期、委員会、開催日、PDFの付託情報を使う。
- 閉会中・継続審査は、前会期の議案へ人手で紐づけられるよう候補を保持する。
- 所管事務調査、報告、請願等を議案パーサへ無理に通さず、別の`kind`にする。
- 公式資料間で結果が異なるときは、公開日の新しい資料で自動上書きせず差分レビューする。

### 7.4 発言ブロックの抽出

- 発言者ラベルと本文を処理中だけ解析し、発言全文をDBへ永続化しない。
- 委員、委員長、当局、参考人、事務局、不明を役割分類する。
- 「委員」で終わるだけの現行ルールをfixtureで評価し、役職名・氏名表記の例外を追加する。
- 数える単位と公開指標名を「委員発言ブロック数」に固定し、
  質問文数、疑問文数、論点数、質疑数とは呼ばない。
- 0は、議題区間と全発言者ラベルを人手または高信頼のparserで確認できた場合のみ確定する。
- 公開値は議題単位の合計に限り、市議会議員ごとの内訳を生成しない。

### 7.5 人手QA

管理画面に、次を同時表示するレビューキューを設ける。

- 公式会議記録へのリンク、開催日、会議名、`vcsv`
- 正規化した委員会、会期候補、予定との突合結果
- 抽出した議題、関連議案、議題種別、`outcome_raw`
- 発言者役割別のブロック数。本文は必要最小限の一時表示とし、保存方針を別途決める。
- 前回QA済み値との差分、会議の`source_occurrence_key`、議題の`source_item_key`、
  `parse_run_id`、取得日時
- 未解決理由: `unknown_committee`、`ambiguous_bill`、`empty_minutes`、`count_mismatch`等

初期公開範囲は少なくとも1年間を100%照合し、その後のバックフィルは年・委員会単位の
公式件数照合、全エラー行確認、無作為標本確認を組み合わせる。名称改称年、年度境界、
継続審査、発言ブロック0の議題は必ず全件確認する。

## 8. 画面・可視化

### 8.1 情報設計

候補ルートは次のとおり。実装時は`web/src/lib/routes.ts`へ追加し同期テストを通す。

- `/committees`: 現在・過去の委員会、開催カレンダー、カバレッジ
- `/committees/[committeeSlug]`: 委員会の役割、名称期間、開催・議題の時系列
- `/meetings/[meetingId]`: 1会議の日時、議題、関連議案、出典
- 議案詳細: Phase 4完了後の接続PRで「委員会での審査」セクションを追加し、
  該当会議へリンクする

委員会所属は「取得日時点の現況」または有効期間を明記する。履歴が無い期間では、現在の
委員一覧を過去会議の横に表示しない。

### 8.2 初期版の可視化

1. **開催カレンダー**
   - 予定、開催済み、会議記録公開済み、中止、未確認を状態ラベルで分ける。
   - 傍聴・映像・公式日程へのリンクを提供する。
2. **年・月別の開催実績**
   - 委員会別の開催実績数を時系列で表示する。
   - 委員会間の優劣ではなく、制度・所管・改称の違いを注記する。
3. **議題構成**
   - 議案、請願、報告、所管事務調査等の構成を積み上げ棒と表で示す。
   - 公式日程に載らない会合があるため「公開資料で確認できた議題」と表示する。
4. **議案の審査フロー**
   - 議案提出、委員会付託、委員会審査、委員会審査結果、本会議議決を時系列で示す。
   - 複数日審査と継続審査を1つの値へ潰さない。
5. **審査記録の有無と発言ブロック**
   - QA済み範囲に限り、議題ごとの委員発言ブロック数を表示する。
   - 「質疑が多い議案ランキング」ではなく、会議詳細の補助情報と分布表示に限定する。
   - 数え方、parser版、確認済み件数を図の直上に置く。
6. **カバレッジマトリクス**
   - 年×委員会について、日程、会議記録、議題、議案突合、QAの状態を示す。
   - これを他のグラフより先に公開し、欠損を利用者が判断できるようにする。

### 8.3 絞り込み・並び順

- 年度、会期、委員会種別、委員会、議題種別、資料公開状態をURLクエリに保持する。
- 基本順序は開催日の新しい順または古い順とし、市議会議員別の件数順を提供しない。
- 結果件数は「12件の会議」「35件の議題」のように単位を明記する。
- 現在の委員会と過去の委員会を混ぜる場合は、名称の有効期間をフィルターに表示する。
- CSV/APIには出典、取得日時、QA状態、公式保証・実測区分、null状態を必須で含める。

## 10. 段階的実装

### Phase 0: 取得範囲の再検証とデータ契約

- 共通基盤0Aの`ingestion_source_versions`、`ingestion_parse_runs`、
  カバレッジ・QA語彙と、0Bの`council_meetings`、
  `council_meeting_revisions`、`council_meeting_source_occurrences`、
  `council_meeting_source_evidence`を前提にする。
  委員会テーマPRから共通テーブルやenumを重複作成しない。
- parser由来の公開根拠は共通基盤0Aの保持ポリシーに従い、取得時の不変原本が
  `retained`の間だけ公開へ用いる。保持終了時は同じトランザクションで別版または
  manual確認済み根拠へ切り替える。
- 委員会固有のconsumer type、registry同期trigger、九つのpublication guardを最初の
  委員会migrationで登録する。0Bの`common:council_meeting_revision` type・同期trigger・
  guardを再定義しない。
- AmiVoiceの年別ヒット総数・取得数・分類数を再計測する。
- 古いコードコメントと調査ノートを、検証済みの同一事実へ揃える。
- 常任委員会を4つとする固定値を`rg`で棚卸し、少なくとも`AGENTS.md`、
  `web/src/lib/prompt/source-code/templates/shared-sections.ts`、関連するparser・UIのテスト、
  `packages/seed/**`、`supabase/seed.sql`、委員会マスタを入れるmigrationを確認する。
  現況マスタの4→5委員会変更と、過去資料を4委員会として読む履歴fixtureは分け、
  過去資料の観測値を現行名で上書きしない。
- 公式保証、実測確認、QA済み公開の3範囲を定義する。
- `committee_period_coverage`、追記型観測、対象付きsource occurrence・版別根拠の粒度、
  欠損状態、確認済み分母を確定する。
- 「委員発言ブロック数」の定義と、市議会議員ランキング禁止をデータ契約へ明記する。

### Phase 1: 共通会議モデルと直近日程

- 共通基盤0A・0Bを利用し、委員会aliasの正本・revision・source occurrence・版別根拠、期間付き所属、
  `committee_period_coverage`と追記型観測、staging、QAキューを追加する。
- 共通0Bの会議status・予定日・実開催日・開閉時刻CHECK、verified根拠付きpublication guard、
  kind・委員会参照の整合、開催実績・会議時間の集計条件を同じ基盤PRで固定する。
- 所属期間の排他制約を追加するmigration自身が`extensions` schemaの作成と
  `btree_gist`の有効化を所有する。手動設定済みDBを前提にせず、freshな
  `pnpm db:reset`でmigration順だけから制約を構築できることを統合テストで確認する。
- 2024年度以降の日程PDFを取り込み、予定と実績を区別する。
- 現在の委員会ページを取得版付きの現況として取り込む。既存所属は
  期間を推測せず`pending`で移行する。
- 現況取込みと同一PRで、`AGENTS.md`と`shared-sections.ts`の用語、
  現況委員会マスタを作るseed・新規migration、それらのテスト期待値を公式の5委員会へ
  同時に更新する。適用済みmigrationは書き換えず、追加migrationで更新する。
  5委員会の集合と現行表示・prompt・seedが一致する回帰テストを同じPRの受入条件にする。

### Phase 2: 2015年5月以降の会議記録インデックス

- 会議名、開催日、開閉時刻、場所、公式URLを取り込む。
- 年×委員会カバレッジを公開し、未分類・本文空・取得失敗を表示する。
- この段階では議題・発言ブロックが未解析でも会議一覧を公開できる。

### Phase 3: 議題・関連議案・読み取りview準備

- 出典非依存の`canonical_item_key`付きで議題を構造化し、
  会議ソース内`source_item_key`と`parse_run_id`は根拠行に付け、
  順番の無い資料へ仮の`item_order`を付与しない。
- 複数議案の一括審査、継続審査、所管事務調査等を構造化し、
  関連議案のPK・FKと`association_scope`を有効にする。
- 共通`policy_topics`への候補分類を作り、人手確認済みの
  `committee_agenda_item_topics`を母集団全件分準備する。consumer別classification releaseを
  原子的に切り替え、active releaseの項目だけを政策分野フィルターへ出す。
- publishedの会議・議題revision・関連議案リンクrevisionを結ぶ読み取りviewを用意し、
  委員会画面と会議詳細が利用する議題・リンクのデータ契約を確定する。
- このPhaseでは議案詳細UIを変更せず、`bills.committee_qa_count`等の旧平坦列の
  書込み・読み取りも切り替えない。

### Phase 4: QA済み審査指標

- parserの役割分類精度をfixtureと全件QAで確定する。
- `committee_review_observations`を解析実行単位で追記し、承認済みの現行版を
  トランザクションで公開する。
- 委員発言ブロック数、会議時間、記録公開率を、定義・カバレッジ付きで公開する。
- 市議会議員別ランキングを生成しないことをレビューゲートにする。

### Phase 4完了後の接続PR: 議案詳細との統合

- Phase 3のpublished会議・議題・関連議案リンクviewと、Phase 4のQA済み
  `committee_review_observations`が揃った後に着手する。
- 議案詳細へ「委員会での審査」タイムラインを追加し、該当する委員会・会議・議題と
  QA済み審査指標へリンクする。この接続PRが議案詳細UIの変更を所有する。
- `bills.committee_qa_count`等の旧平坦列の直接上書きを止め、同じ接続PRで新モデルからの
  派生値または移行中の互換読み取りへ切り替える。Phase 4完了前には派生へ切り替えない。
- 同一議案の複数会議・継続審査・指標未確認を潰さず表示する結合テストと、旧列からの
  移行件数・URL突合をこのPRの受入条件にする。

### Phase 5: 履歴と実測範囲の拡張

- 2015年5月以降の公式保証範囲を委員会・年単位でバックフィルする。
- それ以前の検索ヒットは個別分類し、`empirical_verified`として別表示する。
- 過去の委員会名称・所属履歴は一次資料を確保できた期間だけ公開する。

### Phase 6: Open Data API

- QA済みの会議・議題・関連議案・集計指標を出典付きで提供する。
- 会議記録本文、個人別発言量、内部QA用データを返さない。
- rate limit、カーソルpagination、取得日時、schema versionを既存API方針に合わせる。

## 11. テスト計画

### 11.1 Unit

外部依存を持たない正規化・分類・集計・表示変換は用途に応じた`utils/`の
純粋関数へ切り出し、新規関数ごとに同階層の`*.test.ts`を作成する。

- AmiVoice検索が空の検索語、全会議種別、全10種類の`sch_mean`を送ること
- 30件境界、複数ページ、最終ページ、重複`vcsv`、ヒット総数不一致
- 会議名が空、旧委員会名、特別委員会、議会運営委員会、全員協議会の分類
- 会議記録本文が空、発言者なし、定型句変更、一括議題、複数日、継続審査のfixture
- 委員、委員長、当局、参考人、不明の役割分類
- `role`と`attendance_status`が混ざらず、委員長は`role=chair`かつ
  `attendance_status=present`と表現できること
- 委員発言ブロック数の定義と、質問数・質疑数として表示しない変換
- `null`、0、適用外、中止、未公開の集計・表示
- 会期外会議を捨てずに保持し、後から関連付けできること
- 同じ議案の複数会議が上書きされず別イベントになること
- 政策分野の分類run差し替え、未確認分類の除外、公開版の一意性

### 11.2 DB・Integration

- 新規テーブルはRLSを有効化し、ポリシーなし、Server側の`createAdminClient()`経由とする。
- 既存extensionがないfreshなローカルDBで`pnpm db:reset`を実行し、migrationだけで
  `btree_gist`が`extensions` schemaへ作成され、所属期間の排他制約まで適用されることを
  統合テストで確認する。`pg_extension`と`pg_namespace`で配置先も検証し、Dashboardでの
  手動有効化や前回resetの残存状態をテスト前提にしない。
- 同じ議題の異なる会議ソース内`source_item_key`が同じ`canonical_item_key`へ結び、
  同じ出典内出現の取得版・パーサー版違いも同じ会議・議題へ結び、
  根拠と解析実行だけが追記されることを検証する。
- 会議・議題の根拠へ別論理ソースの取得版を結べないことを複合外部キーで検証する。
- 議題根拠の
  `(agenda_item_source_occurrence_id, agenda_item_id, meeting_id, ingestion_source_id)`が、
  親source occurrenceの`(id, agenda_item_id, meeting_id, ingestion_source_id)`を同じ列順で
  参照することを実DBで検証する。会議または`ingestion_source_id`だけを別値にしたINSERTは
  拒否され、4列すべてが一致するINSERTは保存できることを確認する。
- `(source_system, external_id)`、`(ingestion_source_id, source_occurrence_key)`、
  議題順の部分一意、関連議案のPK・FK、観測行の一意制約を実DBで検証する。
- 別会議の議題と会議ソース内出現を根拠行で結べず、同じ会議ソース内議題を二つの
  正本議題へ結べない一方、別会議では同じ`source_item_key`を使えることを、複合外部キーと
  一意制約で検証する。
- 会議・alias・所属・議題・関連議案・参加者のsource occurrenceについて、対象正本ID一式、
  `ingestion_source_id`、ローカルキーの直接UPDATEを拒否し、誤突合を別正本へ
  付け替えられない。
- 会議・alias・所属・議題・関連議案・参加者・分類の安定正本では親IDとstable key、revision・
  観測では正規化内容、版別根拠では対応先・取得版・解析実行・抽出値の通常UPDATEを拒否する。
  QA・publication・確認情報だけの許可された状態遷移は成功し、対象表へのtrigger付与漏れを
  migrationテストで検出する。
- 会議・所属・議題・審査観測のrevision / 観測自身は`reviewed_by / reviewed_at`の片方または
  両方を欠くverified化・非draft遷移を拒否する。根拠の確認情報だけでは代用せず、公開後の
  確認者・日時のnull化を拒否し、両方とverified根拠を持つ新旧版の原子的切替は成功する。
- 所属・議題・参加者等のmanual根拠は、同じsource occurrenceのV1・V2取得版へそれぞれ
  追記できる一方、同じoccurrence・取得版・parse run・evidence revisionの二重INSERTを
  拒否する。
- 別の取得版に属する解析実行を根拠・履歴・coverage根拠へ指定すると、複合外部キー違反で
  保存できず、解析実行だけ、または論理ソースなしで取得版だけを指定したcoverage根拠も
  CHECK制約で拒否される。
- 所属期間の逆転とQA済み期間の重複がDB制約で拒否され、根拠のない既存行は
  `pending`のまま公開viewに出ないことを検証する。`valid_from=valid_to`の単日所属は保存でき、
  一方のinclusiveな`valid_to`と次の`valid_from`が同日のpublished期間は重複として拒否、
  翌日開始は保存でき、`valid_to=null`が将来のpublished期間と重複する場合も拒否する。
- 同じ論理ソースのalias local keyを二つの委員会へ割り当てられず、同じ正規化名のpublished
  有効期間が別委員会と重複する状態を拒否する。別取得版の原表記は同じoccurrenceへ追記でき、
  published aliasの`valid_from`、またはmanual verified根拠の取得版・非空locator・確認者・
  確認日時が欠ける場合は公開できない。
- 同じalias rootのV1 publishedとV2 draftは併存できるが、二つのpublishedは部分一意制約で
  拒否する。同一トランザクションでV1をsuperseded、V2をpublishedへ切り替えると成功し、
  旧revisionの名称・期間・根拠も復元できる。
- 関連議案根拠に別の議題revision、または別の
  `agenda_item_source_occurrence_id`に属する議題根拠を組み合わせたINSERTは、
  三本の複合外部キー違反で拒否される。同じ議題revision・source occurrenceの
  整合した組と、同じ物理根拠の`evidence_revision`追記は保存できる。
- verifiedリンク根拠のないpublishedリンクrevisionを拒否し、候補または
  `association_scope=unknown`のリンクが公開viewへ出ないことを検証する。
- 関連議案・審査観測は、参照する議題revisionがdraft・superseded・未確認または親会議が
  不適格なら公開できない。公開中の子を残す親議題だけのsuperseded化を拒否し、親議題・
  関連議案・審査観測を同一トランザクションで新revisionへ切り替える操作は成功する。
- 参加者slotの空または任意の既知議員key、同一会議・同一議員の別slot、観測とslotの
  `council_member_id`不一致を拒否する。別会議・別議員・別source人物枠の未確定者は受理し、
  未確定者を後日同定した場合は旧slotを残した原子的な観測切替ができる。
- 会議行が0件の期間でも`committee_period_coverage`を保存でき、
  未取得、確認済み0件、対象外を区別できることを検証する。
- 再監査前のcoverage観測が残り、公開中の観測は対象ごとに一つだけになる。共通契約で
  無効なstate・record presence、負の件数、matched超過はDB制約で拒否される。
- coverage観測は`reviewed_by / reviewed_at`の片方でも欠くと、取得済み・未公表・取得不能・
  対象外のいずれも`reviewed / published / superseded`へ進めない。
- 別委員会範囲、別期間、別`source_kind`のcoverage source occurrence・取得版は
  複合外部キーで拒否され、対象へ束縛されたverified primary根拠だけがpublished観測を
  支えられる。
- 共通会議guardと九つの委員会publication guardについて、repositoryを迂回した直接SQLでも、
  根拠のないpublished行、最後のverified根拠のDELETE・`rejected`化、別正本または
  別取得版の根拠への付け替えをコミット時に拒否する。新旧根拠を同一トランザクションで
  正しく切り替える操作は成功する。
- 会議revisionは`held`なら`held_on`必須、非heldなら実績日・開閉時刻なし、
  `scheduled / cancelled`なら`scheduled_on`必須となる。`closed_at`だけ、または
  `closed_at < opened_at`のINSERT / UPDATEを拒否する。published状態・日時を支えるverified
  根拠の削除・却下も拒否し、正しい予定→開催済み、中止、時刻あり開催への切替は成功する。
- 会議の`plenary / all_members / other`へ`committee_id`を設定する操作と、
  `committee / steering`で委員会IDがnullまたは委員会種別不一致の操作を拒否する。
  議題をplenary・unknown会議へ、審査観測・参加者をscheduled・cancelled会議へ公開できず、
  親会議だけの不適格revision切替も拒否する。親子を同一トランザクションで正しく切り替えられる。
- `council_session_id`のあるpublished会議は実開催日または予定日が会期範囲内であり、
  unknownは会期IDを持てない。別会期・境界外・日付なしを拒否し、両境界日と閉会中の
  `council_session_id=null`を受理する。公開後の会期期間縮小は関連会議を残す限り拒否し、
  会期・会議・子の原子的訂正は成功する。
- published会議revision自身の確認者・日時を必須にし、予定日・開始予定時刻はverified schedule
  根拠と一致させる。片欠け、根拠値不一致、最後の根拠却下、reviewed後のdraft巻き戻しを拒否する。
- 開催実績の集計へ予定・中止・unknown・実開催日なしを混ぜず、会議時間の集計へ
  開閉時刻の片方だけ、未確認時刻、負の差を混ぜない。
- 共通会議のpublished parser根拠は0Bの
  `common:council_meeting_revision`としてregistryへ一度だけ登録され、委員会固有typeへ
  重複しない。manual会議根拠は取得版、空でないlocator、確認者、確認日時のいずれかを
  欠くとverified根拠として数えない。
- published parser根拠の追加・`superseded / rejected`化で、委員会固有consumer typeの
  active referenceが共通registryと完全に同期する。参照中取得版の
  `retained → expired / not_permitted / pending`変更またはobject key除去は単独UPDATEでは
  失敗し、同一トランザクションで別保持版またはmanual確認済み根拠へ切り替えた後は成功する。
- manual根拠は取得版・根拠位置・確認者・確認日時がなければverified根拠として数えない。
- 観測行の公開版は同じ議題に1件だけで、版切替で旧版が`superseded`になることを検証する。
- 同じ議題・taxonomyで公開中の分類セットを二つ作れず、別taxonomyのセットは併存できる。
  run切替後の公開viewはactive releaseの新セット配下だけを返す。
- 議題ごとのpublishedセットにtaxonomy v1・v2が混在していても、公開view / APIは
  `committee_agenda_item`の単一active releaseに列挙された一つのtaxonomyだけを返す。
  同consumerのactive release二つ、未公開taxonomy、未完了run、未確認set、snapshot memberの
  欠落・余分・別snapshot item、理由未確認の除外を拒否する。DB生成の件数・hash・memberを
  直接変更できず、snapshot後の新規議題は旧snapshotへ入らない。全件reviewedの新版を用意し、
  set・releaseの旧新を同一トランザクションでsuperseded / publishedへ切り替えられる。
- reviewed releaseの識別・taxonomy・snapshot・item集合の変更、draft巻き戻し、物理削除を
  拒否する。actual snapshotはpublished・verified・heldの適格会議だけを含み、予定は別planned
  releaseへ分離して実績と合算しない。
- active releaseのitem追加・削除・set差し替えを拒否し、API契約テストでrelease ID、
  taxonomy ID・version、母集団coverageが固定される。一般質問と委員会のactive taxonomyが
  異なる場合は横断集計せず、同じ場合だけ合算する。
- terminal化したrunの分類セット新規作成・identity変更と、同runを参照するtopicの
  追加・変更・削除を、親セットがdraftでも直接SQLで拒否する。running中にセットとtopicを
  作成してからcompletedへ進める操作は成功し、訂正は新しいrun・draftセットでだけ行える。
- 分類run・結果セットと異なるtaxonomy版の政策分野は複合外部キー違反で保存できない。
- `running / failed / rejected`の分類run、未確認の分類セット、または
  `reviewed_by / reviewed_at`の片方でも欠くセットは公開できず、`completed` runと
  `qa_status=verified`、確認者、確認日時が揃うセットだけが公開できる。
- `policy_taxonomies.published_at`がnullのtaxonomyを参照する分類セットは、runと確認情報が
  揃っていても公開できない。
- DB functionを追加・変更するPRでは、functionごとに
  `tests/supabase/db-function/{kebab-case-function-name}.test.ts`を作成し、
  `tests/supabase/utils.ts`を利用してローカルSupabase実DBで検証する。戻り値、ソート、
  フィルター、集計、権限を対象とし、DBはmockしない。
  `anon`で基底テーブル、view、functionを直接読み出せないことと、
  `security_invoker`・EXECUTE権限・固定`search_path`を検証する。
- 予定→開催済み、記録未公開→公開済み、名称不明→QA済みの状態遷移を検証する。
- Phase 4完了後の接続PRで、旧`bills`列から新審査イベントへの移行件数とURLを突合する。
- APIが未承認行、会議記録本文、市議会議員別発言量を返さないことを検証する。
- 公式サイトへのlive testは通常CIから分離し、保存fixtureで再現可能にする。
- AmiVoice・DiscussVision・HTTPクライアントはインターフェース経由でDIし、
  通常CIの契約テストでは保存fixtureを返すFakeを使う。`vi.mock("server-only")`は使用せず、
  外部依存のない変換処理を純粋関数へ分離する。

## 12. 受入条件

- 公式保証範囲、実測取得範囲、QA済み可視化範囲が別々に表示される。
- 「1990年以降の全委員会を網羅」など、分類QAで証明していない完全性を主張しない。
- AmiVoiceの各年で`hitCount`、取得件数、重複、空本文、未分類を記録・確認できる。
- 公開する会議は、開催日、公式会議名、正規化委員会、公式URL、取得日時、QA状態を持つ。
- 公開する会議・所属・議題・審査観測の各revision / 観測自身に確認者・確認日時があり、
  議題・関連議案・審査観測・参加者は適格なpublished・verified親の連鎖だけから返る。
- すべての公開事実からsource occurrence、取得版、解析実行、根拠位置へ辿れ、保持中の
  parser原本から同じ設定で再解析できる。
- 予定と開催実績、会議未開催と記録未公開、nullと0を区別する。
- 開催実績数はpublished・verified・held・実開催日あり、会議時間はさらにverifiedな
  開閉時刻が両方ある会議だけから算出される。
- 一括議題、複数日審査、会期外・継続審査が上書き・破棄されない。
- 政策分野は分類runとQA状態を持ち、未確認候補を公開しない。
- 政策分野の公開view / APIは委員会の単一active releaseへ束縛され、taxonomy versionと
  DB生成snapshotの範囲・生成時刻・件数を返す。snapshot memberとrelease itemが完全一致し、
  新版切替の途中状態や一般質問との異版を同じ系列へ混在させない。
- 確定議員の参加者slotは会議内で重複せず、未確定人物枠は根拠付き決定キーで区別される。
- 委員発言ブロック数は指標定義版・parse run・確認済み分母を伴い、
  「質疑数」と誤表示されない。
- 市議会議員別の一般質問数、質疑数、発言数、出席率ランキングや評価スコアがない。
- すべてのグラフに同値の表またはリストがあり、色だけに依存しない。
- 会議記録本文・映像を複製せず、公式ページへリンクする。
- 公開中parser根拠と共通registryのactive referenceが一致し、根拠なし公開、最後のverified
  根拠の削除、参照中原本の保持終了を直接SQLでも拒否できる。
- WCAG 2.2 AA・JIS X 8341-3:2016の公開ゲートを満たし、キーボードと
  スクリーンリーダーで、委員会・年度・資料状態の絞り込み、会議一覧、表閲覧、
  議案・公式資料への移動という主要タスクを完了できる。
- 320 CSS px（1280 CSS px幅を400%拡大した相当条件を含む）で主要情報と操作を
  二次元スクロールなしに利用でき、200%・400%拡大でも再配置される。
- 絞り込み後の件数と適用条件が`aria-live="polite"`で簡潔に通知される。
- 「みらい議会＠沼津市」が沼津市・沼津市議会の公式サービスではない旨と、既存の
  フッター文言「これは政党チームみらいが運営しているものではありません」が維持される。

## 13. リスク・未決事項

| リスク・論点 | 対応・決めること |
| :-- | :-- |
| 取得範囲の矛盾 | Phase 0でコード・調査ノート・公式案内を再照合し、根拠別の範囲を表示する |
| HTML・検索仕様変更 | adapter分離、fixture、ヒット総数監視、自動公開停止、議会事務局への照会 |
| 過去委員会の改称・再編 | 有効期間付きaliasと系譜キーを使い、名称だけで自動結合しない |
| 日程PDFの非網羅性 | 「公開日程で確認できる範囲」と表示し、勉強会・相談等を推測しない |
| 予定と実績の混同 | 別状態・別日時を持ち、会議記録で実績確定する |
| 発言ブロック数の誤解 | 「質問数」を使わず、定義・分母・限界を常時表示。個人別集計禁止 |
| `bills`の平坦列 | 新イベント表へ移し、互換列は派生値にする。移行完了時期を決める |
| 会期外・継続審査 | 会議を捨てず、関連会期・議案をnullableとし、QAで後付けする |
| 会議記録の著作権・個人情報 | 本文を永続化・再掲載せず、事実・独自要約・公式リンクに限定。公開前に専門家レビュー |
| 動画の削除 | 可用性を定期確認し、会議記録を恒久的な導線の第一候補にする |
| 委員会間比較 | 所管・制度・期間が異なることを注記し、成果・活発さの順位にしない |
| 履歴資料不足 | 現況と履歴を分け、一次資料を確保できない期間は所属者を表示しない |
