## 1. 結論

この可視化の中心は「何件可決されたか」ではなく、各議案について、

1. いつ、誰から提出されたか
2. どの委員会へ付託されたか、または付託が省略されたか
3. 委員会でどのような審査記録が確認できるか
4. 本会議で賛成討論・反対討論があったか
5. 本会議でどのような結論になったか
6. 会派別賛否が公式資料にどの範囲で掲載されているか
7. それぞれの情報が「無い」のか「まだ調べられていない」のか

を、出典とデータの状態を伴って示すことである。

特に、現行スキーマの `null` や関連レコード0件だけから、次の意味を導いてはならない。

- `bill_debates` が0件だから「討論なし」
- `committee_qa_count` が `null` だから「委員発言なし」
- `faction_votes` が0件だから「全会一致」
- 議会だよりに議案が見当たらないから「全会一致」
- 反対討論をした議員だから採決でも反対した
- 会派の賛否から所属議員全員の個人票を推測できる

この誤読を防ぐため、画面実装より先に、情報源ごとの取得・公開・解析・確認状況を表す
**source coverage（出典カバレッジ）**を導入する。会派別賛否については、公式資料に
「全会一致」と明記された場合を除き、未掲載だけから全会一致とは表示しない。

## 2. 背景と目的

### 2.1 背景

沼津市の[令和6年度市民意識調査](https://www.city.numazu.shizuoka.jp/shisei/pr/cyousa/doc/r6-full.pdf)は、
市議会に関する設問を含む最新の公開調査である。同調査では、市議会情報の入手先として
「ぬまづ市議会だより」が64.1％を占める一方、
市議会だよりを「読まない」は43.6％で、20歳代では80.0％、30歳代では67.1％だった。
調査は18歳以上2,150人を住民基本台帳から抽出し、回答1,041人、回収率48.5％である。
若い年代ほど回収率が低く、非回答バイアスの可能性はあるが、PDFや会議録を自力で横断しなくても
審議の流れを把握できる入口には意義がある。

現行リポジトリは、すでに沼津市議会の公開情報から議案の骨格、本会議の討論、
委員会での委員発言ブロック数を取り込む基盤を持つ。しかし、値が取得済みかどうかを示す
カバレッジがなく、単一の集計値で上書きする箇所もある。表示を先に増やすと、
欠測を「事実が存在しない」と誤認させる危険がある。

### 2.2 目的

- 市民が議案の審議経路と現在地を短時間で理解できるようにする。
- 結論だけでなく、委員会審査、本会議討論、公式な会派別賛否を同じ議案に結び付ける。
- すべての表示から、根拠となる沼津市議会の公式ページへ移動できるようにする。
- 「未取得」「未公開」「対象外」「確認済みだが掲載なし」を区別する。
- 過去資料の形式差や公開遅延を隠さず、比較可能な範囲だけを比較する。
- 自動抽出結果を人が確認してから公開する運用を成立させる。

### 2.3 成功の定義

成功は、可決率の算出や議員ランキングの作成ではない。次を満たす状態を成功とする。

- 一つの議案について、提出から本会議議決までを出典付きで追える。
- 情報が表示されない理由を、利用者が画面上で判別できる。
- 自動抽出の誤突合や公式資料の未公開を管理者が発見できる。
- 同じ会期内の議案を、分類、付託先、審査記録、討論の有無で探索できる。
- 個人票を推測せず、公式資料に記載された粒度を保つ。

## 3. 利用者が答えを得たい問い

| 利用者 | 問い | 主な表示 |
| :-- | :-- | :-- |
| 初めて見る市民 | この議案は何で、いまどこまで進んでいるか | 議案概要、審議タイムライン、現在の状態 |
| 生活への影響を調べる市民 | どの委員会で扱われ、公式記録をどこで読めるか | 付託先、委員会開催日、公式記録リンク |
| 審議内容を追う市民 | 委員会での審査記録や、本会議討論があるか | 委員発言ブロック数、討論一覧、カバレッジ表示 |
| 会派の立場を知りたい市民 | 会派別賛否は公式資料でどう示されているか | 会派別賛否表、出典号、掲載状態 |
| 過去と比較したい市民・記者 | 同じ分類の議案はどの経路を通ってきたか | 会期・分類フィルター、件数分布、比較可能期間 |
| 運営者 | どの出典・議案が未取得、部分取得、要確認か | カバレッジ管理画面、未突合一覧、取込実行履歴 |

次の問いには答えない。

- 「働いた議員」「反対が多い議員」などのランキング
- 委員発言ブロック数だけを使った議案・議員・委員会の優劣評価
- 討論で表明した立場から個人の採決行動を推測すること
- 会派別の情報から所属議員全員の個人票を生成すること
- 可決率だけを議会活動の良否と結び付けること

## 4. 対象と対象外

### 4.1 対象

- 定例会・臨時会と、そこに掲載された議案、報告、発議、請願
- 議案番号、件名、分類、提出者、提出日、付託先、委員会審査結果、議決日、議決結果
- 委員会会議記録から確認できる議案別の審査記録
- 本会議で明示された賛成討論・反対討論
- 議会だより等に公式に掲載された粒度での会派別賛否
- すべての事実の出典、取得状況、確認状況

### 4.2 初期公開の期間

期間は、すべての機能について一律に「完全」と宣言しない。情報層ごとに扱う。

| 情報層 | 初期方針 |
| :-- | :-- |
| 議案の骨格・議決結果 | 現行DBに取り込み実績がある2019年以降を監査し、確認済み会期から公開する |
| 本会議討論 | 会議録テキストの取得実績が確認できる2022年以降を候補とし、会期単位のカバレッジ確認後に公開する |
| 委員会審査記録 | AmiVoiceの全件検索について再現可能な実測監査を行い、会期・委員会単位で確認できた範囲だけ公開する |
| 会派別賛否 | 現在取得できる議会だより各号を棚卸しし、表の意味と掲載範囲を確認できた号から公開する |

第20期以降、2004年まで遡れる議案審議結果PDFは、初期公開後のバックフィル対象とする。
過去に遡るほど委員会記録、討論、議会だよりの公開状況が異なるため、議案の骨格があることと、
審議過程の全要素がそろっていることを分けて表示する。

### 4.3 対象外

- 会議録・会議記録の全文再配布
- 議員ごとの発言アーカイブや個人別集計ページ
- 議会中継動画の転載・再配信
- 公式資料にない個人別採決結果の推定
- 自動抽出だけで作る人物・会派の評価点
- 議案本文PDFや議会だよりPDFの複製配布
- 市長部局への「市民の声」「陳情・要望」を、市議会の請願・陳情として混在させること
- パブリックコメント、予算執行、選挙、傍聴者数の本計画内での本実装

S1の期別URLとPDFは、現在の規則では次の形である。

```text
https://www.city.numazu.shizuoka.jp/shisei/g-shigiki/g-sigiki/annai/houkoku/teirei_{期}.htm
https://www.city.numazu.shizuoka.jp/shisei/g-shigiki/g-sigiki/annai/houkoku/teirei_{期}_pdf/gian-{元号年2桁}{月2桁}.pdf
```

期別ページとPDF本文の「第○回（令和○年○月）定例会」を正とする現行方針を維持する。

### 5.2 更新頻度

固定の時刻だけでなく、会期と公開遅延に合わせて取得する。

| データ源 | 通常時 | 開会7日前から閉会14日後 | 未公開資料の再確認 |
| :-- | :-- | :-- | :-- |
| 会期予定HTML | 週1回 | 1日1回 | 変更ハッシュを検知するまで |
| 議案審議結果PDF | 週1回、存在確認 | 1日1回 | 閉会後30日までは週1回、その後月1回 |
| 本会議のお知らせ | 週1回 | 1日1回 | 閉会後はリンク消失を正常状態として記録 |
| DiscussVision | 週1回 | 週1回 | `source_not_published` を月1回再確認 |
| AmiVoice | 週1回 | 2～3日に1回 | 公開遅延中は週1回。常に1秒以上の間隔を置く |
| 議会だより | 月1回 | 月1回 | 新号発行を検知したら対象会期を再解析 |

正確な運用頻度は、初回1か月のリクエスト数と公開タイミングを計測して調整する。
相手サイトへのアクセスは現行クライアントどおり1秒以上の間隔を置き、連絡先を含む
User-Agent、指数バックオフ、同一内容の再解析抑制を使う。

### 5.3 二次利用方針

[沼津市の著作権表示](https://www.city.numazu.shizuoka.jp/about/copyright.htm)と既存の
[著作権整理](./20260816_0215_議会情報の二次利用に関する著作権法上の整理.md)に従い、
議案番号、日付、付託先、議決結果、公式に掲載された賛否などの事実を独自のデータモデルへ
再構成する。PDFの紙面、写真、文章、動画は転載しない。

会議録・会議記録は解析時にのみ取得し、全文を公開DBや画面へ配信しない。討論は、
「誰が・どの議案について・どの立場の討論をしたか」という確認可能な事実と公式リンクを扱い、
発言をまとめた個人別アーカイブは作らない。AI要約を公開する場合は原文の表現を再現せず、
人による確認を必須にする。

## 6. 現行実装との適合とギャップ

### 6.1 利用できる現行実装

| 現行要素 | 適合する点 |
| :-- | :-- |
| `packages/numazu-ingest` | HTTP取得、1秒間隔、PDFの一時処理、内容ハッシュ、DI可能なクライアント、純粋パーサーをすでに持つ |
| `bills` | 会期、議案番号・種別・数値、分類、提出者、提出日、委員会、委員会結果、議決日、状態、出典URLを保持する |
| `council_sessions` | 回次、定例会・臨時会、期間、公式URL、DiscussVision IDを保持する |
| `bill_debates` | 議案、発言者名、議席番号、議員ID、賛成・反対討論、公式URLを保持する |
| `committee_qa_count` / `committee_minutes_url` | 委員会会議記録への入口と、委員発言ブロック数を互換値として保持する |
| `faction_votes` | 会派単位の賛否、会派内で分かれた場合の明示的な人数、出典URLを保持できる |
| `ingestion_runs` / `ingestion_sources` | 実行成否、統計、エラー、URLごとのハッシュ・ETag・最終取得時刻を記録する |
| 議案詳細画面 | 4段階の審議ステータスと本会議討論をすでに表示する |

### 6.2 解消すべきギャップ

| ギャップ | 問題 | 対応 |
| :-- | :-- | :-- |
| `bills.status` が最新状態だけ | 継続、付託、委員会決定、本会議議決の履歴と各出典を表現できない | 審議イベントを追加し、`status` は互換用スナップショットとして派生更新する |
| `bills.source_url` が期別HTML | どのPDFのどの版から得た値か分からない | 出典資料テーブルと議案別カバレッジを追加する |
| ハッシュだけで再解析を省略 | パーサー改善後も同じ本文なら再解析されない | 取得版と`ingestion_parse_runs`を分け、取得版・パーサー名・版・設定の完了組が同じ場合だけ省略する |
| `committee_qa_count` が単一値 | 複数委員会日、再審査、一括議題を最後の値で上書きし得る | 委員会計画の会議・議題・審査観測へ分離する |
| 「質疑回数」という現行名 | 現行パーサーが数えるのは委員の発言ブロックであり、質問・答弁の組数や審議の質ではない | `member_utterance_block_count`と定義し、画面では「委員発言ブロック数」と表示する |
| 一括審査の按分 | 複数議案を一括して宣告した区間の発言数を各議案へ同じ値で付け得る | 委員会計画の`association_scope=grouped`を保持し、議案固有値として比較しない |
| `bill_debates` 0件の意味が不明 | 討論なし、会議録未公開、未取得、抽出失敗を区別できない | 討論カバレッジを追加し、「討論なし」は確認済みの場合だけ表示する |
| 討論の一意制約 | 同一議員が同じ立場で複数回発言した場合に存在情報へ畳み込む | 出典内の発言単位キーを追加する。人数表示と発言件数を分ける |
| `faction_votes` はスキーマのみ | 取込・公開UIがなく、会派構成の時点も持たない | 議会だより棚卸し、パーサー、会派スナップショット、確認UIを追加する |
| `faction_votes` のテーブルコメント | 「レコードがない議案は全会一致とみなす」としており、未取得・未発行を誤認する | コメントを修正し、未掲載から全会一致を導かないデータ契約へ変更する |
| `factions.member_count` が現在値 | 過去の会期へ現在の人数を当てはめる危険がある | 任期・号時点の `faction_snapshots` を追加する |
| AmiVoiceの記述が不一致 | 調査ノートは1990年以降1,787件の実測、コードコメントと既定年は2015年以降を前提とする | 本番相当条件で年別件数を再監査し、その結果をカバレッジとして保存してから文言・既定値を直す |
| `all` モードの不足 | 現在の `all` はAmiVoice委員会記録と議会だより賛否を実行しない | `amivoice`、将来の `dayori`、`coverage-audit` を順序付きで追加する |
| 公開画面の委員会審査記録 | 現状は管理画面のバッジのみで、公開画面では経路が見えない | 出典・定義・カバレッジ付きで議案詳細へ追加する |
| `mirai_stances` が残存 | 沼津市議会の会派別賛否と別概念で、APIにも残る | 後方互換期間を設けて `faction_votes` へ移行し、廃止予定を明示する |

AmiVoiceについては、詳細検索に全10種の `sch_mean`、全4種の `sch_type`、空の検索語、
30件ごとのページングを送る現在のクライアント実装自体は、最新の調査結果と整合する。
一方、サービス側のコメント、2015年開始の既定値、既存DBの投入実績は整合していない。
「検索可能だった期間」と「正しく議案へ突合して公開できる期間」を同一視しない。

## 7. データ契約

### 7.1 「ない」の状態を明示する

共通基盤0Aの三つの軸を混ぜずに使う。

| 軸 | 値 | 意味 |
| :-- | :-- | :-- |
| coverage | `uncollected` / `source_not_published` / `source_unavailable` / `not_applicable` / `partial` / `collected` / `error` | 取得・解析の到達状態 |
| QA | `pending` / `verified` / `rejected` | 人手確認の状態。不整合・未知表記・曖昧な突合は理由コード付き`pending` |
| publication | `draft` / `reviewed` / `published` / `superseded` | 公開版の選択 |

`qa_status=verified`は「レコードが存在する」という意味ではない。確認済み資料内に対象記録が
なかった場合は`record_presence=absent`を併記する。その場合も、資料の掲載方針から結論を
導けるかは別に扱う。

### 7.2 表示規則

| データ状態 | 表示例 |
| :-- | :-- |
| 討論レコードあり、カバレッジ確認済み | 「本会議で賛成討論・反対討論が記録されています」 |
| 討論0件、対象日程の全文確認済み | 「確認した公式記録では討論の記載を確認できませんでした」 |
| 討論0件、会議録未公開 | 「討論情報の公式記録はまだ公開されていません」 |
| 委員会付託省略 | 「委員会付託は省略されました」 |
| 委員会記録未取得 | 「委員会審査記録は未取得です」 |
| 会派別賛否表に掲載あり | 公式表記の粒度で会派別賛否を表示 |
| 賛否表を確認したが対象議案の掲載なし | 「この資料には会派別賛否の掲載がありません。全会一致を意味するとは限りません」 |
| 公式資料に全会一致と明記 | 「公式資料に全会一致と記載されています」 |

「討論なし」「委員発言なし」「全会一致」の短い断定は、対応する根拠が確認済みで、
その資料からその結論を導ける場合に限る。

新テーブルへ二重書きして検証後に読み取り先を切り替える。

```sql
  coverage_id uuid not null references bill_fact_coverage(id) on delete restrict,
  bill_id uuid not null references bills(id) on delete restrict,
  fact_kind bill_fact_kind_enum not null,
  observation_key text not null,
  state coverage_state_enum not null default 'uncollected',
  record_presence record_presence_enum not null default 'unknown',
  checked_at timestamptz not null,
  qa_status qa_status_enum not null default 'pending',
  publication_state publication_state_enum not null default 'draft',

  review_note text,

    or (state = 'partial' and record_presence in ('present', 'unknown'))

      and record_presence = 'unknown'
    )
  ),
  check (expected_count is null or expected_count >= 0),
  check (matched_count is null or matched_count >= 0),
  check (
    expected_count is null
    or matched_count is null
    or matched_count <= expected_count
  ),
  check (record_presence <> 'absent' or coalesce(matched_count, 0) = 0),
  foreign key (coverage_id, bill_id, fact_kind)
    references bill_fact_coverage(id, bill_id, fact_kind) on delete restrict,
```

`bill_fact_coverage`は対象の正本、`bill_fact_coverage_observations`は各確認時点の
append-onlyな観測とする。再取得で前回のpartial、error、確認済み0件を上書きせず、
公開版だけを同一トランザクションで切り替える。公開viewは二表を結び、現在の
`published`観測だけを返す。

全新規テーブルでRLSを有効にし、ポリシーは定義しない。公開側は既存方針どおり
`createAdminClient()` を使うServer Component・loader経由で必要項目だけを返す。
公開viewは`WITH (security_invoker = true)`を必須とする。DB functionは原則
`SECURITY INVOKER`とし、`SECURITY DEFINER`が必要なときは`search_path`を固定し、
PUBLIC・anon・authenticatedから`EXECUTE`をrevokeしてservice roleだけにgrantする。

`ingestion_source_versions`は取得物の同一性とHTTPメタデータだけを表す。同じ取得版を
新しいパーサーで再解析した履歴は`ingestion_parse_runs`へ追記し、完了済みの
`source version × parser name/version × configuration`がある場合だけ再解析を省略する。
取得版と解析実行を両方持つ全テーブルは、個別の外部キーに加えて
`foreign key (parse_run_id, source_version_id) references
ingestion_parse_runs(id, source_version_id) on delete restrict`を持つ。これにより、別の
取得版に属する解析実行を誤って組み合わせることをDBで防ぐ。パーサー由来の根拠では
両列を必須、人手登録では`parse_run_id`だけnull可とする。
取得版の本文をDBへ直接保存しない。再解析に使う取得時バイト列は暗号化した非公開
ストレージへ不変オブジェクトとして置き、`private_object_key`と
`artifact_retention_state`で有無を明示する。公開parser根拠が参照する版は`retained`を必須とし、
保存期限前に根拠の差し替えまたは延長判断を行う。保存条件上保持できない版は
`not_permitted`、期限後は`expired`とし、現在URLの内容を旧版として再解析しない。
保持状態、object key、再解析期限の変更は0Aの
`transition_ingestion_source_version_retention`だけに許可する。この関数は変更前後、
操作者、理由、日時をappend-onlyの監査表へ記録し、active referenceが残る保持終了を
遅延guardで拒否する。通常roleから取得版表の直接UPDATE権限を外し、内容識別列は
`ingestion_source_versions_identity_immutable`で常に不変にする。
`ingestion_parse_runs`はrunningでだけ追加し、
`finalize_ingestion_parse_run`で一度だけterminalへ進める。terminal行と
parser profile・取得版・開始日時の直接UPDATEは不変性triggerで拒否する。
保持期間、アクセス権、削除監査は共通基盤0Aで公開前に確定する。複数資料を根拠にした場合は、
次の議案用関連テーブルを追加する。

任意の取得版だけを使った「確認済み0件」を公開させない。

### 8.2 議案の識別子

現行の`bills.id`は内部主キーとして維持する。一方、現行の
`unique (council_session_id, bill_number)`は両列がnullableであり、nullを含む重複を
防げないため、公開データの正本キーとはみなさない。`bills.slug`もURL用でnullableなため、
取込同一性には使わない。

`bills.normalized_bill_number text`と`bills.canonical_bill_key text`を追加し、
次の決定的キーを保存する。

```text
numazu:{verified_session_slug}:{normalized_bill_number}
例: numazu:2026-13:議第58号
```

移行は次の順で行う。

1. 公式の会期名・開始日・終了日を照合して`council_sessions.slug`をバックフィルし、
   一意制約を確認後にNOT NULL化する。
2. `bill_number`を公式表記から専用の純粋関数で正規化する。前後空白、
   全角・半角数字、空白の有無は同じ`normalized_bill_number`へ収束させるが、
   番号を追加・推測しない。会期と番号が公式根拠で確認できた行だけ
   `canonical_bill_key`を生成する。議案名や資料URLからは生成しない。
3. 既存行の未確定候補をQAし、重複を解消するまでは
   `canonical_bill_key is not null`の部分一意インデックスを使う。
4. 全既存行の移行後に`canonical_bill_key`をNOT NULLかつUNIQUEにする。新規取込は
   移行期間中もこのキーを必須とし、未確定行を公開しない。

`bill_number`には「議第58号」のような公式表記を残し、同じ表示値を別列へ複製しない。
安定キーは正規化値による同一性判定、原表記は表示と監査に使い分ける。
移行中から`(council_session_id, normalized_bill_number)`の部分一意制約を設け、
`canonical_bill_key`が`numazu:` + 参照先の不変`council_sessions.slug` + `:` +
`normalized_bill_number`と完全一致することを遅延guardで検査する。該当議案に
正本キーが設定された後は、議案の`council_session_id / normalized_bill_number /
canonical_bill_key`と、参照される会期の`slug`を通常UPDATEで変更できない。
訂正は新しい議案正本を作り、関係と根拠を監査可能に結び直す専用migrationで行う。

- 突合は会期と正規化した議案番号の組を第一候補とし、議案名だけでは自動突合しない。
- 同じ番号は年・会期をまたいで再利用されるため、番号だけをキーにしない。
- 継続審査等で別会期にも現れた案件は、自動的に同一議案へ統合しない。
- 公式資料と件名を確認後、次の関係で明示的に結ぶ。

### 8.3 状態と審議イベント

現行 `bills.status` は「審議中」と「最終結果」を同じenumで表し、履歴を持たない。
互換列として残しつつ、表示の正本をイベントへ移す。

`not_certified`は既存enumへ追加したトランザクション内では安全に参照できないため、
次を単独の先行migrationファイルで適用・commitし、Supabase型を再生成してからイベント表の
migrationへ進む。

```sql
alter type bill_status_enum
  add value if not exists 'not_certified' after 'certified';
```

`committee_recommendation=passage`、「承認すべきもの」は`approval`とし、本会議の
`passed`へ置き換えない。本会議結果は既存`bill_status_enum`のうち
`passed / rejected / consented / approved / certified / adopted / not_adopted / continued`
に`not_certified`を加えた値だけをCHECK制約で許可する。撤回と議決を要しない報告は、
本会議結果として重複保持せず、
それぞれ`withdrawal_recorded`、`report_received`のイベントで表す。
原案どおりか修正かは`decision_form`で分け、互換用の
`bills.status=passed`へ畳んでもイベント正本では失わない。`event_type`ごとに許される
結果列をCHECK制約で固定する。`committee_decided`は委員会推奨結果だけ、
`plenary_decided`は本会議結果だけを必須とし、その他のイベントでは両方をnullにする。
`decision_form=original / amended`は委員会推奨の`passage`と本会議結果の`passed`だけに使い、
同意、承認、認定、不認定、採択、不採択、継続等の非修正型結果は`not_applicable`とする。
委員会の不認定推奨は`non_certification`、本会議の不認定は`not_certified`として別に保持し、
既存`bills.status`、生成型、TypeScript型、表示ラベル、parser、一覧filterを同じmigration・PRで
更新する。同じPRで`web/public/openapi/open-data-api.json`の議案`status` enumにも
`not_certified`を追加し、一覧・詳細レスポンスとOpenAPI仕様を先に一致させる。
`bills.status_order` generated列はenum依存のため一度削除して
`not_certified`を明示したCASEで再作成し、Web / Adminの`BILL_STATUS_ORDER`と同じ順序にする。
DBの`bill_status_group`とWebの`toBillStatusGroup`では不認定を`rejected`群へ、
`shouldAutoCloseInterviewOnBillStatus`では結論済みへ加える。各DB function・変換・
表示ラベル・filter・自動終了の回帰テストに不認定fixtureを追加し、NULL順・waiting群・
インタビュー継続へ誤って落ちないことを固定する。
`to-open-data-bill.ts`の変換テストに不認定fixtureを加え、実レスポンスをOpenAPI schemaで
検証する契約テストで、列挙値と生成client / response validatorの互換性を固定する。
互換列や公開APIへ同期できない旧クライアントを先に残さない。
未知語彙を`other`や`passed`へ丸めず、理由コード付き`qa_status=pending`とする。
原表記は出典関連側の`raw_result`に残す。

`event_key`は議案内の同一手続を表す決定的キーとし、資料の差し替えで安定イベントを
重複作成しない。正規化した日付、順序、結果、委員会、決定形は追記型の
`bill_proceeding_event_revisions`へ置き、訂正時は新しい`revision_number`をdraftで追加する。
旧published revisionを保持したまま差分をQAし、承認時に旧行を`superseded`、新行を
`published`へ同一トランザクションで切り替える。イベントごとのpublished revisionと、
同一議案内のpublished `event_order`は部分一意制約で一つにする。各出典は対象revisionへ
`bill_proceeding_event_sources`で結び、公開revisionには少なくとも一つの検証済み根拠を
必須とし、`bill_proceeding_event_publication_guard`でDB保証する。パーサーで得た根拠は
`parse_run_id`を必須にし、人手で直接登録した根拠だけnullを許可する。
source occurrenceの一意キーには`event_id`を含めず、同じ議案・論理ソースの
`source_event_key`を別の正本イベントへ結べないようにする。取得版が差し替わるか
新しいパーサーで再解析しても
既存occurrenceの対応先を変えず、版別根拠を追記する。同じ一括議決の出典内キーが
複数議案に適用される場合だけ、異なる`bill_id`での対応を許し、個別議案固有の観測とは
`association_scope=grouped`で表示上区別する。`unknown`はQA完了まで公開しない。

publishedイベントで`occurred_on`がある場合は、議案が参照する会期の
`start_date / end_date`内を原則とする。閉会中継続審査等の公式記録がある例外だけ、
`outside_session_reason_code`と確認者・確認日時、同日付を支持するverified根拠を
必須にする。例外行は通常の会期内日数・所要日数集計から除外し、画面で理由を
表示する。日付未確定の`occurred_on=null`も順序表示だけに使い、日付集計へ入れない。
別会期で継続した案件は同じ議案の会期を差し替えず、別の議案正本と
`continued_from`関係を作る。guardはイベントの公開切替だけでなく、議案の会期参照や
会期期間の訂正でも関連する公開イベントを再検査する。

タイムラインは各イベントのpublished revisionから作る。付託省略は明示イベントで表し、イベントがないことから
付託省略を推定しない。`bills.status` は検証済みの本会議議決、継続、撤回等のうち
互換列に対応するイベントからだけ同期し、委員会の推奨結果では更新しない。同日や
日付不明のイベントも`event_order`で公式資料上の順序を保持し、DOM順にも使う。

### 8.4 委員会審査と委員発言ブロック数

委員会審査の正本は、委員会計画の`council_meetings`、
`committee_agenda_items`、`committee_agenda_item_bill_links`とそのpublishedリンクrevision、
`committee_review_observations`とする。本計画では同じ事実を保持する
`bill_committee_reviews`を重複して作らない。

議案詳細は、これらを結ぶrepositoryまたは`bill_committee_review_summary` viewから、
publishedの会議revision、議題revision、議案リンクrevision、審査観測だけを結び、会議日、
委員会、議題、関連議案、発言ブロック数、観測状態、出典版を取得する。

- 数える対象は、現行パーサーと同じく、議案の審査区間内で「○○委員」と記録された発言単位とする。
- 委員長の議事進行、当局の答弁、同じ委員の発言内に含まれる文の数は数えない。
- `0` は、対象区間が取得でき、最後まで解析できた場合だけ保存する。
- 一括審査は `grouped` とし、同じ数を各議案固有の「委員発言ブロック数」として
  重複集計しない。
- 複数開催日は行を分ける。合計値は検証済みの `exact` だけ、または画面上で一括審査分を
  分けて集計する。
- この数は注目度、審議の深さ、賛否の強さを表す指標として順位付けしない。

移行期間は `bills.committee_qa_count` と `committee_minutes_url` に互換値を同期する。
委員会側テーブルの監査後、公開画面はjoin/viewを読む。旧列は利用箇所がなくなってから
別PRで削除する。

### 8.5 本会議討論

既存`bill_debates`は討論発言の安定正本として維持するが、話者、立場、日付、要約、
公開状態は追記型revisionへ移す。同じ発言者が同じ立場で複数回討論しても残せるよう、
正本には内容や資料位置から独立した不変の`debate_key`を一度だけ発番し、会議の
ソース内出現と発言位置は後述するsource occurrence側のキーにする。

```sql
alter table bill_debates
  add column debate_key text;

-- 安定正本と後続の監査履歴を親削除へ連鎖させない。
alter table bill_debates
  drop constraint bill_debates_bill_id_fkey,
  add constraint bill_debates_bill_id_fkey
    foreign key (bill_id) references bills(id) on delete restrict,
  drop constraint bill_debates_council_member_id_fkey,
  add constraint bill_debates_council_member_id_fkey
    foreign key (council_member_id) references council_members(id) on delete restrict;

create unique index bill_debates_debate_key
  on bill_debates (bill_id, debate_key)
  where debate_key is not null;

alter table bill_debates
  add constraint bill_debates_id_bill_id_key unique (id, bill_id);

create table bill_debate_revisions (
  id uuid primary key default gen_random_uuid(),
  debate_id uuid not null references bill_debates(id) on delete restrict,
  bill_id uuid not null references bills(id) on delete restrict,
  revision_number integer not null check (revision_number >= 1),
  council_meeting_id uuid references council_meetings(id) on delete restrict,
  council_member_id uuid references council_members(id) on delete restrict,
  speaker_display_name text not null,
  seat_number integer,
  spoken_on date,
  stance debate_stance_enum,
  summary text,
  association_scope text not null default 'exact',
  normalization_reason_code text,
  qa_status qa_status_enum not null default 'pending',
  publication_state publication_state_enum not null default 'draft',
  verified_by uuid,
  verified_at timestamptz,
  created_at timestamptz not null default now(),
  check (association_scope in ('exact', 'grouped', 'unknown')),
  check (
    stance is not null
    or (
      publication_state = 'draft'
      and qa_status in ('pending', 'rejected')
      and normalization_reason_code is not null
    )
  ),
  check (
    (publication_state = 'draft' and qa_status in ('pending', 'rejected'))
    or (publication_state <> 'draft' and qa_status = 'verified')
  ),
  check (
    qa_status <> 'verified'
    or (verified_by is not null and verified_at is not null)
  ),
  check (
    publication_state <> 'published'
    or (association_scope <> 'unknown' and stance is not null)
  ),
  foreign key (debate_id, bill_id)
    references bill_debates(id, bill_id) on delete restrict,
  unique (debate_id, revision_number),
  unique (id, debate_id, bill_id)
);

create unique index bill_debate_one_published_revision
  on bill_debate_revisions (debate_id)
  where publication_state = 'published';

create table bill_debate_source_occurrences (
  id uuid primary key default gen_random_uuid(),
  debate_id uuid not null references bill_debates(id) on delete restrict,
  bill_id uuid not null references bills(id) on delete restrict,
  ingestion_source_id uuid not null references ingestion_sources(id) on delete restrict,
  source_occurrence_key text not null,
  created_at timestamptz not null default now(),
  foreign key (debate_id, bill_id)
    references bill_debates(id, bill_id) on delete restrict,
  unique (bill_id, ingestion_source_id, source_occurrence_key),
  unique (id, debate_id, bill_id, ingestion_source_id)
);

create table bill_debate_sources (
  id uuid primary key default gen_random_uuid(),
  source_occurrence_id uuid not null,
  debate_revision_id uuid not null references bill_debate_revisions(id) on delete restrict,
  debate_id uuid not null,
  bill_id uuid not null,
  ingestion_source_id uuid not null references ingestion_sources(id) on delete restrict,
  source_version_id uuid not null references ingestion_source_versions(id) on delete restrict,
  parse_run_id uuid references ingestion_parse_runs(id) on delete restrict,
  evidence_revision integer not null default 1 check (evidence_revision >= 1),
  source_locator text,
  observed_speaker_name text,
  observed_stance text,
  observed_spoken_on date,
  observed_council_meeting_id uuid references council_meetings(id) on delete restrict,
  observed_summary_hash text,
  extraction_method extraction_method_enum not null,
  qa_status qa_status_enum not null default 'pending',
  verified_by uuid,
  verified_at timestamptz,
  created_at timestamptz not null default now(),
  check (
    (
      extraction_method = 'parser'
      and parse_run_id is not null
      and evidence_revision = 1
    )
    or (extraction_method = 'manual' and parse_run_id is null)
  ),
  check (
    qa_status <> 'verified'
    or (verified_by is not null and verified_at is not null)
  ),
  check (
    extraction_method <> 'manual'
    or qa_status <> 'verified'
    or nullif(btrim(source_locator), '') is not null
  ),
  foreign key (source_occurrence_id, debate_id, bill_id, ingestion_source_id)
    references bill_debate_source_occurrences(
      id, debate_id, bill_id, ingestion_source_id
    ) on delete restrict,
  foreign key (debate_revision_id, debate_id, bill_id)
    references bill_debate_revisions(id, debate_id, bill_id) on delete restrict,
  foreign key (parse_run_id, source_version_id)
    references ingestion_parse_runs(id, source_version_id) on delete restrict,
  foreign key (source_version_id, ingestion_source_id)
    references ingestion_source_versions(id, ingestion_source_id) on delete restrict
);

create unique index bill_debate_sources_observation_key
  on bill_debate_sources (
    source_occurrence_id,
    source_version_id,
    parse_run_id,
    evidence_revision
  ) nulls not distinct;
```

parser根拠の`evidence_revision`は1に固定し、人手による再解釈は同じsource occurrenceの
revisionを増やす。source occurrenceは`bill_id + ingestion_source_id + source_occurrence_key`
で一意にし、取得版・正本ID・revision IDをキーへ含めない。このため、同じ議案内の
一つの出典観測を二つの正本討論へ結べず、資料差し替えや新しいパーサーでも対応先を
変更できない。一つの討論発言が複数議案を一括して扱う場合は、同じ
`source_occurrence_key`を異なる`bill_id`へ結ぶことを許し、各行を
`association_scope=grouped`として個別議案固有の討論数・立場には集計しない。
`association_scope=unknown`はDBの公開CHECKでも非公開にする。

published討論は`council_meeting_id`を必須にし、共通0Bのpublished・verified・
`status=held`・`kind=plenary`な会議revisionだけを参照する。会議の
`council_session_id`は議案の会期と一致し、`spoken_on`は会議の`held_on`と一致する。
必要根拠は同じ`council_meeting_id`と観測日を持つverified行に限る。討論、
会議revision、会期参照、根拠のいずれを切り替えた場合も
`bill_debate_publication_guard`が再検査する。

既存行の`debate_key`は、内容を再ハッシュせず既存`id`から一度だけ発番する。元の出典URL、
会議日、議案、発言順の根拠を確認してsource occurrenceをバックフィルする。
資料内位置を確認できない行は公開revisionを作らず理由コード付きの移行候補とし、
管理画面で解消する。現行の話者・立場・要約・`source_url`列は
読み取り移行中の互換列として残し、
公開側をpublishedの`bill_debate_revisions`とverified根拠の結合へ切り替えた後に、
nullable化・廃止を別PRで判断する。
パーサー由来の根拠は`parse_run_id`を必須とする。published revisionには
`debate_key`がnon-nullの安定正本とverified根拠を必須にし、訂正時は旧publishedを
維持したまま新revisionをdraftでQAしてから同一トランザクションで切り替える。
この条件は`bill_debate_publication_guard`でDB保証する。

旧`UNIQUE (bill_id, speaker_name, stance)`は、現行取込writerの
`onConflict: "bill_id,speaker_name,stance"`が依存しているため、最初のmigrationでは落とさない。
次の二回のdeployに分ける。

1. **Migration A + app deploy**: `debate_key`、revision、source occurrence、版別根拠を追加し、
   既存行をバックフィルする。writerを新モデルへのdual-writeへ切り替えるが、旧UNIQUEは維持する。
2. 新旧件数、失敗run、writer・管理画面・公開loaderの参照を確認し、
   `rg 'bill_id,speaker_name,stance'`等で旧conflict keyへの依存が0件であることを確認する。
3. **Migration B + app deploy**: writerと読み取りが新モデルだけを使う次のreleaseで、旧UNIQUEを
   初めて削除する。必要なら`debate_key`をNOT NULL化し、同一話者・同一立場の複数発言を許可する。

Migration Bだけに次を含める。

```sql
alter table bill_debates
  drop constraint bill_debates_bill_id_speaker_name_stance_key;
```

画面では次を分ける。

- 討論者数: 重複しない発言者数
- 討論記録数: 公式記録上の発言単位数

ただし、一覧で人数や件数を競わせない。個別議案で、発言者、明示された討論の立場、
公式記録へのリンクを示す。ここでいう `stance` は「討論で表明した立場」であり、
個人の採決結果ではないことを常時表示する。

`summary` を使う場合は、原文引用ではなく独自表現の要約とし、`qa_status=verified`かつ
`publication_state=published`のものだけ公開する。検索用に抽出した発言全文は処理後に破棄し、
公開DBへ保存・配信しない。parser根拠として公開する取得時の原本バイト列は、再解析用の
非公開ストレージへ不変オブジェクトとして置き、共通の保持期限・最小権限・アクセス監査に
従う。原本を保持できない場合はparser根拠のまま公開せず、manual確認済みの別根拠へ切り替える。

既存`faction_votes`は`vote NOT NULL`および`UNIQUE (bill_id, faction_id)`を持つため、
版付きの正本にしない。公開読み取りを切り替えるまでの最新値キャッシュとし、
確認済みで公開中の`faction_vote_result_revisions`だけを同期する。新旧読み取りの一致を確認後、
旧制約・旧テーブルの扱いを別PRで判断する。

`faction_vote_result_revisions.normalized_vote`の `for | against | split | excluded` は、
公式凡例と実データを棚卸しした後に不足語彙を追加する。未知の記号を推測で正規化せず、
根拠側に`raw_mark`を保存して`normalized_vote=null`、`qa_status=pending`にする。
パーサー由来の根拠は`parse_run_id`を必須とし、人手登録だけnullを許可する。
`for_count` と `against_count` は、公式資料が人数を明示した場合だけ保存する。
会派人数を使って内訳を計算しない。
人数がない場合、`for / against / split`は両countをnullで保存できる。人数がある場合は
`for = 1以上 / 0`、`against = 0 / 1以上`、`split = 両方1以上`だけを許し、
`excluded`は常に両方nullとする。片方null、負値、0対0、賛否と逆向きの人数をCHECKで拒否する。
published人数は同じ版のverified根拠にある`raw_for_count / raw_against_count`と一致し、
合計が参照する会派snapshotの`member_count`を超えないことを遅延guardで検査する。

`faction_vote_editions`は議会だより号または公式採決資料版の安定正本と会期を表し、
edition revisionと版別根拠で公表日・基準日・取得版を追記する。同じ紙面から得たedition、
会派snapshot、賛否は複合外部キーで同じ`edition_id / edition_revision_id / source_version_id`
へ束縛する。billの`council_session_id`はeditionの会期と一致し、`decided_on`がある場合は
verified根拠付きsnapshotの`valid_from / valid_to`内でなければ公開できない。
`decided_on`が未確定なら、同じedition内の議案番号・会期を照合したverified根拠を必須にし、
日付範囲による集計からは除外する。現在号のsnapshotを過去議案へ流用しない。

賛否の安定正本は`(bill_id, faction_id)`で一つとし、snapshotはrevision側で選ぶ。
同じ会派の別snapshot rootを使った相反する二つのpublished結果を許さず、訂正は同じ正本の
新revisionで行う。同じ論理ソースの取得版が差し替わるか、新しいパーサーで再解析された場合も、
`ingestion_source_id + source key`で既存source occurrenceへ収束させ、同じ
`faction_snapshots`または`faction_vote_results`正本へ固定したまま、版別根拠だけを
追記する。正規化結果が変わる場合は`faction_snapshot_revisions`または
`faction_vote_result_revisions`のrevision番号を増やし、旧結果を削除せず、QA後に公開版を
同一トランザクションで切り替える。公開viewは各正本につき一つのpublished revisionだけを返す。
`source_snapshot_key`と`source_vote_key`は資料内の行・セルを一意に識別するキーとし、
source occurrenceの一意制約に正本IDを含めない。同じ出典内行・セルを二つの正本へ結べず、
別の`source_version_id`で同じローカルキーを観測した根拠は別々に保存できる。
parser根拠の`evidence_revision`は1に固定し、同じ紙面の手動再解釈は番号を増やして追記する。

publishedの会派スナップショットrevisionと賛否revisionには、それぞれ対応する
`qa_status=verified`の根拠を一つ以上必須にする。さらにpublished賛否revisionが参照する
`faction_snapshot_revision_id`は、同じ安定`faction_snapshot_id`のpublishedかつverifiedな
revisionで、同じedition・会派・取得版でなければならない。会派スナップショットを訂正するときは、それを参照する
公開賛否も同じトランザクションで新しいrevisionへ切り替え、旧組合せを履歴として残す。
これらの表をまたぐ条件は、`faction_snapshot_publication_guard`と
`faction_vote_publication_guard`の遅延constraint triggerで保証し、資料なし・時点未確定の
会派名、人数、賛否を公開しない。

会派別賛否の対象は`bill_fact_coverage(fact_kind='faction_vote')`、各確認時点と公開状態は
その`bill_fact_coverage_observations`で管理する。

- 資料未取得: `uncollected`
- 該当会期の議会だより未発行: `source_not_published`
- 過去号が削除され取得不能: `source_unavailable`
- 賛否表を解析したが対象議案への突合が曖昧: `state=partial`、
  `record_presence=unknown`、`qa_status=pending`
- 表を確認し対象議案が掲載: `state=collected`、`qa_status=verified`、`record_presence=present`
- 表を確認し対象議案が未掲載: `state=collected`、`qa_status=verified`、`record_presence=absent`
- 公式資料が明示的に全会一致と記載: 上記の`present`と明示的な結果コード

`qa_status=verified`かつ`record_presence=absent`を「全会一致」に変換しない。
初期リリースでは、公式資料に明記がない限り
「会派別賛否の掲載なし」と表示する。

### 8.7 公開整合と出典の訂正・差し替え

#### 公開整合を保証するDB制約

表をまたぐ公開条件はrepositoryだけへ委ねない。各テーマmigrationで次のguard関数を作り、
対象revision・coverage観測・根拠関連表の`INSERT / UPDATE / DELETE`後に同じ関数を呼ぶ
`CONSTRAINT TRIGGER DEFERRABLE INITIALLY DEFERRED`を設定する。公開切替repositoryは
同一トランザクションで新旧状態と根拠を更新するが、直接SQLでもコミット時に同じ条件を
満たさなければ拒否されるようにする。

- `bill_fact_coverage_publication_guard`: publishedの`collected / partial`観測に、同じ
  議案・fact kindのverified primary根拠を一つ以上要求する。`present`は`matched`、
  `absent`は`absent`の根拠だけを許す。
- `bill_relation_publication_guard`: published関係revisionに、同じ安定関係へ結ばれた
  verified根拠を一つ以上要求する。
- `bill_proceeding_event_publication_guard`: publishedイベントrevisionにverified根拠を
  一つ以上要求し、`association_scope=unknown`の根拠は必要件数へ数えない。
  日付がある通常行は議案の会期内、例外行は理由・確認情報・同日付の
  verified根拠を必須にし、議案または会期期間の変更でも再検査する。
- `bill_debate_publication_guard`: published討論revisionについて安定正本の`debate_key`、
  `association_scope <> 'unknown'`、同じ討論へ結ばれたverified根拠を要求する。
  加えて同一会期のpublished・verified・held本会議、`spoken_on=held_on`、
  同会議・同日付のverified根拠を要求し、親会議の切替でも再検査する。
- `faction_snapshot_publication_guard`: published会派スナップショットrevisionにverified根拠を
  一つ以上要求する。editionの会期・公表日・基準日、snapshotの会派と
  有効期間、edition根拠とsnapshot根拠の取得版一致も検査する。
- `faction_vote_publication_guard`: published賛否revisionにverified根拠を一つ以上要求し、
  参照する`faction_snapshot_revision_id`が同じスナップショットのverifiedかつpublished
  revisionであることを要求する。議案・editionの会期、edition、会派、取得版、
  議決日とsnapshot有効期間の一致、人数の賛否値とverified原文値の一致、
  `for_count + against_count <= member_count`も検査する。スナップショット、edition、議案、
  根拠のいずれを切り替えた場合も既存published賛否を再検査する。
- `ingestion_source_version_retention_guard`: 共通0Aの
  `published_source_version_references`に同じ取得版へのactive referenceが残る間は、
  `retained`から`expired / not_permitted / pending`への変更と非公開object keyの除去を拒否する。
  registryは`released_at >= activated_at`をCHECKし、`activated_at`を不変、`released_at`を
  `null`から非nullへの一度だけの遷移に限定する。同じ根拠の再公開も旧行を巻き戻さず、
  新しいactive行を追加する。このguard・lifecycle trigger・registryは0Aが所有し、
  テーマ別migrationでは再定義しない。

各guardがparser根拠を必要件数へ数えるのは、その取得版が
`artifact_retention_state=retained`で、不変原本とハッシュを再検証できる場合だけとする。
manual根拠は取得版・空でない根拠位置・確認者・確認日時を必須にするが、parserの
再現可能性は要求しない。
guardは対象行だけでなく、必要根拠を削除・`rejected`化した場合や、参照する
スナップショットを`superseded`へ切り替えた場合にも発火させる。公開viewはguardを通った
published revisionとverified根拠だけを返す。
六つの議案publication guardと通常同期triggerは、公開判定に数えるparser根拠について
namespacedなconsumer typeとactive referenceを共通registryへ登録し、superseded・rejected化で
releaseする。遅延guardは公開集合とregistryが完全一致することも検査するため、後続テーブルを
0Aの保持guardへ静的に書き足さない。

監査対象の正本、revision、source occurrence、根拠、coverage観測では外部キーを
`ON DELETE RESTRICT`に統一する。さらに共通の`prevent_audit_delete`トリガーで物理DELETEを
拒否し、取消・誤抽出・訂正は`rejected / superseded`と新revisionで残す。保持期間満了等の
例外削除は、参照関係と公開影響を確認する専用migrationだけで扱う。

一意制約は二重INSERTを防ぐだけで、既存行の付け替えは防がない。全安定正本では親IDと
stable keyを、全source occurrenceでは正本ID一式・`ingestion_source_id`・ローカルキーを、
`BEFORE UPDATE`の`prevent_stable_identity_update`トリガーで不変にする。revisionと版別根拠は
内容・対応先・取得版・解析実行を直接更新できず、QA・公開・確認者等の状態列だけを許可する
`enforce_append_only_revision_update`を適用する。候補はstagingでQAし、誤った正本対応を
通常UPDATEで直さない。例外訂正は影響範囲と旧新IDを記録する専用migrationだけで行う。

#### 出典の訂正・差し替え

同じURLのPDFが更新された場合、古い抽出行を残したまま新しい行をupsertしてはならない。

1. 新しい内容を一時領域で解析する。
2. 旧版との追加・変更・削除差分を作る。
3. 件数減少、識別子変更、未知語彙があれば自動公開せず、理由コード付き
   `qa_status=pending`にする。
4. 確認後、同一トランザクションで現行版を切り替える。
5. `ingestion_runs.stats` に旧・新ハッシュ、追加、更新、削除、未突合件数を残す。

取得時の原本バイト列は、公開parser根拠を再現できる期間だけ非公開ストレージへ保持する。
検索用の抽出全文は永続化せず、公開・再配布もしない。期限満了時は、参照する公開根拠を
別版またはmanual検証へ切り替えてから原本を削除し、取得版メタデータ、ハッシュ、URL、
取得日時、抽出した事実、変更差分、削除監査ログは残す。

## 9. 取り込みとcoverage管理

### 9.1 パイプライン

```text
出典発見
  → 取得・ハッシュ計算
  → 出典資料メタデータ保存
  → 純粋パーサーで構造化
  → 会期・議案・委員会・会派へ突合
  → 不変条件とクロスソース検証
  → coverage更新
  → 管理画面で差分確認
  → 人の確認
  → 公開用loader/APIへ反映
```

実行モードは次の単位に分ける。

```text
sessions
bills
minutes
amivoice
amivoice-archive
dayori          # 新規
coverage-audit  # 新規
all
```

`all` は `sessions → bills → members → minutes → amivoice → dayori → coverage-audit`
の順で実行する。外部ソースの一つが未公開でも、他の取得済み事実を巻き戻さない。
一方、失敗した情報種別は `error` または `source_not_published` として必ず記録する。

### 9.2 議会だより取込

1. 索引HTMLから号、発行日、PDF URL、対象会期候補を取得する。
2. PDFを `pdftotext -layout` で一時的にテキスト化する。
3. 号ごとの見出しと凡例を解析し、賛否表の掲載範囲を保存する。
4. 議案番号は会期候補と組み合わせ、現行の会期・議案番号の組へ突合する。
5. 会派名は時点スナップショットへ突合する。
6. 未知の記号、OCR崩れ、複数候補、人数不整合は自動採用しない。
7. 管理画面で原資料へのリンクと抽出表を並べ、人が確認する。

PDFが画像主体でテキスト抽出できない場合は、OCRやLLMを補助に使っても、その結果を
`verified` に自動昇格させない。人が公式紙面と照合する。

### 9.3 AmiVoiceカバレッジ監査

現状の「検索では1990年まで取得可能」という調査結果を、そのまま「議案別質疑が完全」とは扱わない。
年ごとに次を記録する。

- 検索画面が示す総件数
- 全ページから取得できたユニークな `vcsv` 件数
- 会議種別・委員会名別件数
- 開催日を正確な会期へ紐づけられた件数
- 議案番号を一意に突合できた審査区間数
- 一括審査、会期外、未知委員会、本文空、重複の件数
- 公式検索総数と取得数の差

この監査が完了するまで、既存DBの `committee_qa_count is null` を未掲載・質疑なしと解釈しない。
会期期間が議案日から仮置きされている場合は、自動突合の信頼度を下げる。

### 9.4 公開ゲート

次のいずれかを満たすレコードだけを公開する。

- S1の議案骨格: パーサーの不変条件を通過し、会期単位の件数を原資料と確認済み
- 討論・委員会審査記録: 議案番号と会期が一意に突合し、出典リンクが開き、カバレッジが `verified`
- 会派別賛否: 号、凡例、会派、議案番号、記号を人が確認済み

既存方針どおり、議案の公開ステータスは自動的に `published` にしない。
新規・変更・削除は管理画面でレビューし、公開中の議案に重大な差分があれば警告する。

## 10. データ品質保証

### 10.1 自動検証

議案審議結果PDFごとに次を検証する。

- 会期見出しから回次、元号年、月が取得できる。
- 議案番号が1件以上あり、同一会期内で重複しない。
- `bill_number_kind` と公式表記の接頭辞が一致する。
- 議案名が空でない。
- 提出日、議決日が妥当な日付で、議決日が提出日より前でない。
- 付託先「省略」を委員会マスタとして作らない。
- 委員会審査結果と本会議結果を取り違えない。
- 未知の分類・提出者・結論語彙を黙って既知値へ変換しない。
- すべての議案に直接の出典資料が紐づく。

クロスソースでは次を検証する。

- 会期名ではなく会期キーと日付で突合している。
- 討論・委員会記録に現れる議案番号が当該会期に一意に存在する。
- 委員会記録の委員会名が議案の付託先と矛盾しない。予算決算等の例外はルール化する。
- 討論の日付が会期内または公式な継続案件として説明できる。
- 会派別賛否の会派名と時点スナップショットが一致する。
- `for_count + against_count` を使う場合、公式に人数内訳があり、スナップショット人数と
  不整合なら公開を止める。

### 10.2 管理画面のQAキュー

次を優先度付きで表示する。

- 公式資料の件数と抽出件数が一致しない会期
- 議案番号は一致するが件名が大きく異なるレコード
- 複数会期へ突合できる会議記録
- 一括審査区間
- 未知の議決結果、委員会名、会派名、賛否記号
- 前回版から消えた議案・討論・会派別賛否
- 公開済みだが出典URLが404になったレコード
- `source_not_published` のまま想定期間を超えた資料

管理者は、採用、修正、対象外、保留を選び、理由と確認者、確認日時を残す。

### 10.3 coverage指標

内部運用では、会期ごとに次の件数を表示する。ただし公開画面で品質を一つの点数に丸めない。

- 議案総数
- 議案骨格の `verified` 件数
- 委員会審査対象件数と、記録を確認できた件数
- 本会議議決対象件数と、討論範囲を確認できた件数
- 議会だより対象会期数と、賛否表を確認できた会期数
- `partial`、`error`、`qa_status=pending`、未突合件数

## 11. 画面と可視化

### 11.1 議案一覧

既存カード・検索を保ち、ランキングではなく探索支援を追加する。

- 会期、議案分類、付託委員会、審議状態で絞り込む。
- 「委員会記録あり」「本会議討論あり」「会派別賛否掲載あり」で絞り込む。
- カバレッジ未確認の議案を「なし」と見せず、「確認中」と表示する。
- 並び順の既定は会期・議案番号または提出日とし、委員発言ブロック数や反対討論数を既定順位にしない。

### 11.2 議案詳細

#### A. 審議タイムライン

```text
議案提出
  ↓
委員会付託 ── または「付託省略」
  ↓
委員会審査・委員会の結論
  ↓
本会議討論
  ↓
本会議議決
```

各ノードに日付、公式表記、出典リンク、確認状態を置く。日付不明・対象外・未公開を
空白にせず文字で示す。現行の4段階プログレスは、最終状態だけから全ノードを完了扱いするのではなく、
審議イベントを根拠に描画する。

#### B. 委員会審査

- 委員会名、開催日、委員会審査結果
- 「委員発言ブロック数 ○件」または「一括審査区間で○件」
- 数え方の説明
- 公式会議記録へのリンク
- 未取得・未公開・対象外の状態

発言数を棒グラフで競わせず、個別議案の記録量を理解する補助情報として示す。

#### C. 本会議討論

- 賛成討論・反対討論を明確な見出しで分ける。
- 発言者名、議席番号、討論で明示された立場、公式記録リンクを表示する。
- 「討論の立場は個人の採決結果を示すものではありません」と明記する。
- 記録未公開、未取得、確認済みだが記載なしを区別する。

#### D. 会派別賛否

- 議会だよりの号・発行日・出典リンクを冒頭に置く。
- 行を会派、列を「公式な賛否」「明示された人数内訳」とする通常のデータ表を基本にする。
- 色に加え、賛成、反対、会派内で分かれた、除斥、確認中を文字とアイコンで示す。
- 個人名や推定票は表示しない。
- 未掲載の場合は「全会一致」と置き換えない。

### 11.3 会期概要

可決率を主役にせず、次の小さな可視化を組み合わせる。

- 議案分類別件数
- 「付託あり／付託省略／対象外／未確認」の件数
- 議案を行、提出・委員会・討論・議決・会派別賛否を列にした審議過程マトリクス
- 会期内の日付順タイムライン
- データカバレッジ表

マトリクスでは、完了、記録あり、記録なし、未公開、対象外を形とテキストで区別する。
「記録が多いほど良い」という序列は付けない。

### 11.4 出典と免責

- 各カードに直接の公式出典を置く。
- 最終取得日と確認日を分けて表示する。
- 「本サービスは沼津市および沼津市議会の公式サービスではありません」と、フッター文言
  「これは政党チームみらいが運営しているものではありません」を維持する。
- AI要約にはAI生成・人による確認状態を表示する。
- 誤りの指摘窓口を用意する。

## 12. アクセシビリティ

WCAG 2.2 AAとJIS X 8341-3:2016を公開ゲートとし、既存のアクセシビリティ計画に
沿って自動・手動・支援技術による確認を完了する。

## 14. テスト計画

### 14.1 純粋関数・パーサー

- `parse-gian-result-pdf`: 既存の平成16年、令和6年、令和8年fixturesを維持し、
  議案件数・分類・日付・付託先・結果を固定する。
- `parse-committee-minutes`: 0件、1件、一括審査、複数開催日、委員長発言、本文欠落を追加する。
- `parse-minutes`: 同じ議員の複数発言、複数議案への討論、未知表現を追加する。
- 審議イベント: 原案可決と修正可決、同日の複数イベント、日付不明の順序を固定する。
- `parse-dayori-votes`: テキスト表、画像/OCR崩れ、未知記号、会派名変更、掲載なしを実物fixtureで試す。
- coverage表示: 共通契約で有効な`state × record_presence`をテーブル駆動テストにし、
  未知値・不正組合せは集計せず「確認が必要」と表示する。
- 議案キー: 公式表記の前後空白、全角・半角数字、空白の有無が同じ
  `normalized_bill_number`へ収束し、年・会期をまたぐ同じ議案番号は衝突しない。
  空値、番号を推測する入力、不正形式は候補に残し、正本キーを生成しない。

純粋関数は実装と同階層に `*.test.ts` を作り、外部サービスをmockするために
`server-only` をmockする構造にはしない。

### 14.2 DB統合テスト

- 同じ資料・同じパーサーバージョンの再実行が冪等である。
- 会期または議案番号が未確認の行は`canonical_bill_key`を生成・公開できず、同じ正本キーの
  重複は移行中の部分一意インデックスと移行後のNOT NULL・UNIQUE制約で拒否される。
- `canonical_bill_key`の任意値・空値・参照先と異なる会期slugを拒否し、
  全角・半角等の表記違いで同じ`(council_session_id, normalized_bill_number)`を
  二重登録できない。正本キー設定後の議案識別列と参照済み会期slugの
  通常UPDATEを拒否する。
- パーサーバージョン変更で再解析される。
- 同じURLの内容変更で、旧抽出行が現行公開集合に残らず、監査履歴には残る。
- 議案関係は同じ正本に旧publishedと新draftを同時保持でき、二つのpublished、
  verified根拠がない候補、同じsource occurrenceの別正本への付け替えを拒否する。
  同じ論理ソース・ローカルキーは取得版が変わっても同じ正本へ収束し、訂正後も
  旧revisionと複数根拠が監査履歴に残る。
- 議案coverage根拠は、同じ論理ソース・`source_fact_key`のV1/V2が同じ
  `bill_fact_source_occurrences`と議案へ収束する。別議案へのINSERT・UPDATE付け替えと、
  occurrenceの論理ソース・ローカルキー変更をDBで拒否する。
- 審議イベントは同じ正本に旧publishedと新draftを保持でき、二つのpublishedと
  published順序の重複を拒否する。公開切替後も旧revisionを保持する。
- 原案可決と修正可決が別の`decision_form`として保存される。提出・付託・委員会決定・
  本会議議決・撤回・報告について、委員会ID、委員会推奨、本会議結果、決定形の
  有効な組合せを受理し、不正な組合せを拒否する。
- 委員会の`approval / certification / non_certification / adoption / non_adoption / continued`と、
  本会議の`consented / approved / certified / not_certified / adopted / not_adopted / continued`は
  `decision_form=not_applicable`で保存でき、架空の`original`を要求しない。
- 未知の委員会推奨・本会議結果は理由コード付き`pending / rejected + draft`だけを許し、
  published viewから除外する。
- 同日または`occurred_on=null`のイベントが`event_order`で安定して並ぶ。
- publishedイベントの会期内日付と両境界日を受理し、会期外日付は
  理由・確認者・確認日時・同日付のverified根拠が揃う例外だけ受理する。
  議案の会期参照または会期期間だけを変更して不整合にする操作を拒否する。
  別会期への継続は新しい議案正本と`continued_from`関係で保持できる。
- 同一発言者・同一立場の複数討論が、発言単位で消えずに保存される。
- 同じ審議イベントに複数の取得版・解析実行を根拠として追加できる。
- 討論は同じ安定正本に旧publishedと新draftを保持でき、二つのpublished、
  安定`debate_key`やverified根拠のないpublished revisionを拒否する。
- published討論は議案と同会期のpublished・verified・held本会議を参照し、
  `spoken_on=held_on`かつ同会議・同日付のverified根拠を持つ。別会期、committee会議、
  scheduled / cancelled会議、根拠日不一致、親会議だけの不適格revision切替を拒否する。
- 同じ議案・論理ソースのイベントまたは討論ローカルキーは、取得版・解析実行が変わっても
  同じsource occurrenceと正本へ収束し、二つの正本へ結べず、
  一括討論だけは異なる議案へ`association_scope=grouped`で結べる。
- 一括イベント・一括討論の`grouped`根拠は議案固有の件数へ集計されず、`unknown`は
  公開viewから除外される。
- 別の取得版に属する解析実行を根拠行へ指定すると、複合外部キー違反で保存できない。
- source occurrenceと異なる論理ソースの取得版を根拠へ指定すると、
  `(source_version_id, ingestion_source_id)`の複合外部キー違反で保存できない。
- `bill_fact_coverage_observation_sources`は観測と異なる議案・fact kindの根拠を拒否する。
  publishedの`collected / partial`観測はverified primary根拠を一つ以上必要とし、
  `present`に`matched`、`absent`に`absent`以外のprimary根拠を結ぶと公開を拒否する。
- 同じcoverage対象・`observation_key`の再実行は重複を拒否し、異なる再確認キーの
  観測は旧行を残して追記できる。対象ごとのpublished観測は一つだけになる。
- `uncollected + present`、`not_applicable + present`、`partial + absent`、負の件数、
  `matched_count > expected_count`はcoverage観測のCHECK制約で拒否される。
- 未知の賛否記号が`normalized_vote=null`と理由コード付き`qa_status=pending`で保存される。
- `null`、`0`、`absent`、`not_applicable` を相互に変換しない。
- 一括審査の発言数が議案別の正確値として集計されない。
- 過去の会派票が現在の会派人数から補完されない。
- 同じ論理ソースの会派行・賛否セルは、取得版が変わっても同じsource occurrenceと正本へ
  収束し、二つの正本へ結べない。版ごとの根拠は競合せず保存できる。
- `ingestion_sources`の`id`、`source`、`url`、`created_at`のUPDATEと物理DELETE・TRUNCATEを
  拒否する。`content_hash`、`etag`、`last_modified`、`last_fetched_at`だけの更新は成功し、
  取得元の種別またはURLが変わる場合は別のsource行をINSERTして旧版の参照先を保つ。
- 取得版の`content_hash`、論理ソース、取得メタデータを直接UPDATEすると拒否される。
  保持状態・object key・再解析期限は監査付き遷移関数からだけ変更でき、active referenceを
  残した保持終了は拒否される。
- parse runは`running`以外で直接INSERTできず、parser名・版・設定hash・取得版・開始日時の
  UPDATEを拒否する。finalize関数による一度だけのterminal遷移は成功し、完了後のstatus・
  `parse_stats`・完了日時を含む再UPDATEは拒否される。
- fact、関係、イベント、討論、会派スナップショット、賛否の六つの根拠は、parserだけでなく
  `parse_run_id=null`のmanual根拠でも同じsource occurrenceのV1/V2を競合せず追記できる。
  いずれもverified manual根拠は取得版・確認者・確認日時・空でない根拠位置の一つでも
  欠くとCHECK制約で拒否される。
- 関係、イベント、討論、会派スナップショット、会派別賛否のrevisionは、
  `qa_status=verified`で確認者または確認日時を欠くINSERT / UPDATEをCHECK制約で拒否する。
- 会派スナップショットと賛否はそれぞれ同じ正本に旧publishedと新draftを保持でき、
  二つのpublishedを拒否する。同じ紙面の手動再解釈は`evidence_revision`を増やして残す。
- 同じ議案・会派の賛否は別snapshot root経由でも二重公開できず、
  別会派の行は保持できる。訂正時の旧新revision・snapshot切替は同一
  トランザクションだけ成功する。
- published会派スナップショット・賛否はverified根拠を必須とし、published賛否が
  pendingまたはdraftの会派スナップショットrevisionを参照する状態を拒否する。
  スナップショット訂正時は賛否も新しい`faction_snapshot_revision_id`へ切り替わり、
  旧賛否revisionを旧スナップショットrevisionと組み合わせて再現できる。
- snapshotと賛否の会派不一致、edition・会期・取得版の不一致、過去議案への
  現行snapshot流用を拒否する。`decided_on`は対応snapshotの有効期間内とし、
  未確定行は検証済み議案番号・会期根拠があっても日付集計から除外する。
- 人数なし、`for`、`against`、`split`、`excluded`の有効行列を受理し、片方null、
  負値、0対0、賛否と逆向き、`excluded`の人数、会派人数超過、verified原文値との
  不一致を拒否する。snapshotの`member_count`変更時も公開賛否を再検査する。
- 議案分類のDB生成snapshot memberとrelease itemは双方向に完全一致し、
  議案consumerのpublished releaseは一つだけになる。未公開taxonomy、未完了run、
  未確認set、snapshot外議案、itemの欠落・追加を拒否し、release後の内容更新も許さない。
- 六つのテーマ固有publication guardについて、通常repositoryを迂回した直接INSERT/UPDATEでも
  根拠なしpublished、`unknown`根拠だけのpublished、最後のverified根拠の削除・rejected化を
  コミット時に拒否する。
- 共通`ingestion_source_version_retention_guard`は、publishedのparser根拠が参照する版を、
  同一トランザクションで根拠切替せず`retained`以外へ変える操作と、非公開object keyを
  外す操作をコミット時に拒否する。公開・差し替え・却下ごとに
  `published_source_version_references`のactive集合が実際の公開parser根拠と一致し、
  registry行の直接INSERT・識別列UPDATE・DELETEは権限または不変性制約で拒否される。
  公開→release→同じ根拠の再公開ではregistry履歴が2行になり、旧`released_at`は不変で、
  `activated_at`変更、`released_at`の巻き戻し・再変更、時刻順序違反をDBが拒否する。
- 監査対象の正本・revision・source occurrence・根拠・coverage観測の物理DELETEを拒否し、
  取消・訂正は`rejected / superseded`と新revisionで残る。
- stable rootの親・stable key、source occurrenceの正本tuple・論理ソース・ローカルキー、
  revision・根拠の内容列を通常UPDATEで変更すると不変性トリガーが拒否し、状態列だけの
  正しい公開切替は通る。
- publishedの付託・委員会決定イベントが参照する委員会のDELETEは`RESTRICT`で拒否され、
  `committee_id`をnull化して履歴を壊さない。
- 論理URLの内容が変わった後も、`retained`な旧取得版は`private_object_key`の不変バイト列と
  ハッシュから新parserで再解析できる。`expired / not_permitted`な旧版では現在URLを
  代用せず、再解析不能を明示して公開parser根拠への昇格を拒否する。
- RLSが有効で、基底テーブル、view、functionのいずれも匿名クライアントから直接取得・実行できない。
- Migration A適用直後も現行writerの`onConflict: "bill_id,speaker_name,stance"`が成功し、
  writer・loader切替前に旧UNIQUEを削除しない。Migration Bの事前検査で旧conflict keyへの
  依存が0件になり、削除後は同一話者・同一立場の複数討論を別`debate_key`で保存できる。
- DB functionを追加・変更するPRでは、functionごとに
  `tests/supabase/db-function/{kebab-case-function-name}.test.ts`を作成し、
  `tests/supabase/utils.ts`を利用してローカルSupabase実DBで検証する。戻り値、ソート、
  フィルター、集計、権限を対象とし、DBはmockしない。

### 14.3 loader・API・UI

- 公開対象外の議案や未確認レコードが返らない。

### 14.4 外部ソースの監視

外部サイトを直接読むテストを通常CIの必須テストにしない。DIしたFakeを使う契約テストと、

既知の議案1件、レスポンス時間を確認し、変更を通知する。

PR前はリポジトリ標準の次をすべて実行する。

```bash
pnpm lint

```

## 16. リスクと未決事項

| リスク・未決事項 | 影響 | 対応 |
| :-- | :-- | :-- |
| 議案PDFの形式変更 | 件名や列の誤抽出 | Zod・不変条件・実物fixture・件数差で公開を止める |
| 過去PDF・議会だよりの404 | 履歴が途中で欠ける | `source_unavailable` と記録し、市議会事務局へ安定URL・オープンデータを要望する |
| DiscussVision APIが未文書化 | 予告なく形が変わる | スキーマ検証、canary、公式画面へのリンク、AmiVoiceとの相互確認 |
| 会議録公開の遅延 | 直近議案が「討論なし」に見える | `source_not_published` とし、再確認ジョブを続ける |
| AmiVoiceの公開範囲と実装説明の不一致 | 完全性を過大表示する | 年別の再現可能な監査を先に行い、実測coverageだけを公開する |
| 会期日が仮置き | 委員会記録を別会期へ誤突合する | S2の確定期間を優先し、曖昧な候補は人手確認へ送る |
| 委員発言ブロック数の意味 | 注目度・質・質問数と誤読される | 定義を常時表示し、ランキング・評価点に使わない |
| 複数議案の一括審査 | 同じ数を各議案へ誤配分する | `grouped` を保持し、個別値と分離する |
| 討論の立場と採決の混同 | 個人票の誤推測 | ラベル、説明、APIフィールドを分離し、個人別集計を作らない |
| 会派名・人数の時系列変化 | 過去賛否の誤表示 | 出典号時点の `faction_snapshots` を使う |
| 議会だよりの「未掲載」の意味 | 全会一致の誤断定 | 凡例・編集方針を号ごとに確認し、未掲載は未掲載のまま表示する |
| 議案の継続・再提出 | 別案件の統合または重複 | 会期付きキーを維持し、関係は出典確認後に手動で結ぶ |
| 元資料の訂正・上書き | 古い抽出結果との混在 | ハッシュ差分、版切替、削除差分、監査ログを実装する |
| 発言本文の権利・個人情報 | 不適切な再配布 | 検索用全文を公開DBへ永続化・再配布せず、表示は事実・独自要約・公式リンクに限定する。再解析用原本は期限・権限・監査付きの非公開保管とする |

実装開始前に決める事項は次のとおり。

1. 初期公開を第25期全体にするか、直近の確認済み4定例会に限定するか。
2. 議会だよりが明示する賛否表の掲載基準を、全号共通ルールとして扱えるか。
3. 「全会一致」を公式資料の明記がある場合だけ表示する方針を恒久化するか。
4. 一括審査の委員発言ブロック数を議案詳細に表示するか、会議単位だけに表示するか。
5. `bill_debates` の発言者名表示を維持しつつ、個人別集計を禁止するAPI契約をどう固定するか。
6. 既存オープンデータAPIの `miraiStance` 廃止にバージョニングが必要か。

推奨は、直近の確認済み会期を小さく公開し、`3` は恒久方針、`4` は会議単位表示、
`5` は議案詳細内だけ、`6` は非破壊的な追加後に廃止予告期間を設けることである。

| :-- | :-- | :-- |
| 一般質問・政策テーマ | 共通の`policy_topics`で横断検索できる | マスタは複製せず、議案との多対多関係を人手確認後に公開する |
| 予算可視化 | `category = budget` の議案から予算案・補正予算案へ結べる | 共通の議案キーと出典資料を使う。予算額の取込を待たず審議経路は実装可能 |
| パブリックコメント | 条例案・計画案の議案提出前の参加過程になり得る | 将来 `bill_relations` で関連付ける。市長部局の制度であり市議会の手続とは分ける |
| 請願・陳情 | 議案審議結果PDFに掲載される請願は同じタイムラインを利用できる | 市議会への陳情は非公開部分があり、請願と同じ完全性を期待しない |
| 市民意識調査 | 議会情報の取得方法・閲読状況を示す | UI優先順位の背景に使うが、審議事実や代表的意見とは混ぜない |
| 選挙・議員・会派 | 会派スナップショットの時点確認に関係する | 個人の投票履歴やランキングは作らない。会派の公式公開単位のみ利用する |
| 傍聴・動画 | 審議へのアクセス手段 | 再生数を市民数・理解度とみなさず、公式記録リンクとして扱う |

複数テーマで共通化すべきものは、共通基盤0Aの`ingestion_source_versions`・解析履歴・
coverage状態、0Bの会議正本・revision・根拠、会期・議案の識別子、出典表示コンポーネントである。
予算、市民参加、選挙の各テーマが独自に
「未取得」を表現すると意味がずれるため、coverageの語彙と表示ルールを先に共通化する。

## 18. 実装順の最終判断

最初の実装PRはグラフではなく、Phase 0のcoverageデータ契約と誤った全会一致判定の除去にする。
次にS1だけで成立する審議タイムラインを公開し、委員会記録、討論、会派別賛否を、
それぞれのカバレッジ監査が完了した順に追加する。

この順序なら、情報がそろっていない期間にも議案の骨格を安全に見せられ、後からデータが増えても
「以前は全会一致だったのに変わった」のような誤解を生じさせずに段階的に拡張できる。
