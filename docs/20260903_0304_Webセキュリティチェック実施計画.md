# Web セキュリティチェック実施計画

## 1. 文書の位置付け

本書は、みらい議会＠沼津市の公開 Web アプリケーションについて、
セキュリティチェックを安全かつ再現可能な形で実施するための計画書である。
本書に記載する重点項目は事前調査で選定した確認候補であり、脆弱性の検出結果ではない。

チェックでは、ソースコードだけでなく、Web が利用する API、Server Actions、
共有パッケージ、Supabase の権限境界、デプロイ設定までを一つの攻撃面として扱う。
本番環境に対する攻撃的なテストは行わず、ローカル環境または分離した
プレビュー環境で検証する。

## 2. 目的

- 公開 Web から到達できる機能とデータの信頼境界を明らかにする
- 認証・認可、入力検証、秘密情報、依存関係、設定上の弱点を検出する
- チャットやインタビュー機能の濫用、AI 利用料金の異常増加、サービス妨害を防ぐ
- 検出事項に再現手順、影響、修正案、回帰テスト案を付けて実装へ引き継ぐ
- 一度限りの診断にせず、CI と定期運用へ組み込むべき検査を整理する

## 3. 評価基準

2026 年 9 月時点の以下の公式資料を基準にする。

- [OWASP Application Security Verification Standard 5.0][asvs]
- [OWASP API Security Top 10 2023][api-top-10]
- [OWASP Web Security Testing Guide][wstg]
- [Next.js: Content Security Policy][next-csp]
- [Next.js: HTTP Headers][next-headers]
- [Supabase: Row Level Security][supabase-rls]
- [Supabase: Production Checklist][supabase-production]

OWASP の Top 10 は確認漏れを防ぐための分類として使い、合否判定には
より具体的な ASVS の要件と、実際の攻撃成立性・事業影響を用いる。

ASVS は Level 2 を基準とし、Level 1 を含む適用可能な要件を ID 単位で
`Pass`、`Fail`、`N/A`、`未確認`に分類する。各判定にはコード、テスト結果、
HTTP レスポンスなどの証拠を紐付ける。`N/A` には理由を必須とし、Level 3 は
今回の基準外として、追加保証が必要な機能だけ個別に採用する。

## 4. 対象範囲

### 4.1 対象

| 対象 | 確認内容 |
| :-- | :-- |
| `web/src/app/` | 公開ページ、Route Handlers、レイアウト、メタデータ |
| `web/src/features/` | Server Actions、サービス、Repository、入力処理 |
| `web/src/lib/` | 認証、Cookie、環境変数、Markdown、ログ、テレメトリー |
| `web/src/middleware.ts` | Basic 認証、Supabase セッション、ルート制御 |
| `web/next.config.ts` | HTTP ヘッダー、画像、リダイレクト、ビルド設定 |
| `packages/shared/` | Web から呼ばれる共通ロジック |
| `packages/supabase/` | Supabase クライアントと型定義 |
| `packages/topic-analysis-core/` | Web の公開読み取り・分析結果取得経路 |
| `supabase/migrations/` | RLS、GRANT、RPC、`SECURITY DEFINER`、Storage |
| `.github/workflows/` | CI/CD 権限、Action 固定、秘密情報の受け渡し |
| デプロイ済みプレビュー | HTTP、Cookie、CORS、キャッシュ、動的挙動 |

公開 API は少なくとも次を対象とする。

- `POST /api/chat`
- `POST /api/interview/chat`
- `POST /api/interview/complete`
- `GET /api/bills/{billId}/topic-analysis`
- `GET /api/open-data/bills`
- `GET /api/open-data/bills/{billId}`
- `GET /api/open-data/interviews`
- `POST /api/revalidate`
- `GET /api/og/bill`
- `GET /api/og/report`
- `GET /api/og/site`

すべての `"use server"` ファイルは、画面上の導線に関係なく直接呼び出される
可能性があるものとして棚卸しする。

### 4.2 条件付き対象

- `admin/` 自体の包括監査は別タスクとする
- ただし、Web と共有するパッケージ、DB、認証設定、デプロイ経路は対象に含める
- Supabase、Vercel、GitHub の管理画面設定は、権限が提供された場合に読み取り確認する
- 外部サービスの侵入試験は、各サービスの規約と許可範囲内に限定する

### 4.3 対象外

- 本番環境へのアクティブスキャン、負荷試験、総当たり、DoS、破壊的入力
- 実在利用者のデータを使った検証
- ソーシャルエンジニアリング、フィッシング、物理セキュリティ
- Supabase、Vercel、OpenAI など外部事業者自身の基盤に対する診断
- `admin/`、Cloud Run worker の包括的な単体監査

## 5. 事前準備と実施条件

### 5.1 検証環境

1. `develop` から監査専用ブランチと worktree を作る
2. ローカル Supabase を起動し、検証用 seed データを投入する
3. ローカル Web または監査専用 Vercel Preview を起動する
4. 本番と同等の設定名を使いつつ、値は検証専用シークレットに置き換える
5. ログ、DB、AI 使用量を監視できる状態にする
6. 動的スキャンの送信元、時間帯、最大リクエスト数を記録する

プレビュー環境が本番 DB や本番の外部 API キーを参照している場合、動的スキャンを
開始しない。Supabase Preview Branch またはローカル DB への接続を確認してから進める。

本番固有の TLS、CDN、HSTS、Cookie、キャッシュ、公開エンドポイントは、プレビューの
結果で代替しない。プレビューでの検証完了後に、通常の `GET`／`HEAD` と管理画面の
読み取りだけでパッシブ確認する。本番へ payload を変形したリクエスト、認証回避、
大量リクエスト、データ変更リクエストは送らない。権限がなく確認できない設定は
`未確認`として残す。

### 5.2 テスト用主体

- 未認証のブラウザー
- 匿名セッション A
- 匿名セッション B
- 必要に応じて通常認証ユーザー
- 運営権限を持つ検証用ユーザー
- Basic 認証あり・なしのリクエスト

主体ごとに Cookie jar とブラウザープロファイルを分離する。同じ Cookie を使い回して
別ユーザー試験を行わない。

### 5.3 安全上の制限

- 自動スキャンは最初にパッシブモードで実行する
- アクティブスキャンは対象 URL と HTTP メソッドを allowlist で限定する
- レート制限試験は低い上限から開始し、サービスと DB の状態を監視する
- メール送信、外部通知、AI 課金を伴う経路は fake または検証用接続先へ差し替える
- 作成したデータとログには監査用識別子を付け、終了後に対象を確認して削除する
- Critical 相当の可能性が見つかった場合は、横展開せず最小限の再現で停止する

### 5.4 動的テスト開始チェックリスト

開始前に、次の値を実施記録へ転記し、プロジェクト責任者または運用責任者が
go／no-go を判断する。

- 対象 commit SHA と allowlist 済みの origin／パス
- 接続先 Supabase project ref と、本番ではないことの確認結果
- OpenAI、Langfuse、メール、通知が fake または検証用資格情報であること
- 監視するログ、DB メトリクス、AI 使用量と、監視担当者
- 初期値は同時実行数 1、毎分 30 リクエスト以下とする
- エンドポイントごとの総リクエスト上限と、増加を許可する責任者
- HTTP 5xx、想定外の外部通知、急激な AI 使用量増加が出た場合の即時停止
- 作成データの識別子、保存先、削除担当者

上限変更はテスト中に暗黙で行わず、理由、新しい値、判断者を記録する。

### 5.5 Critical 候補のエスカレーション

1. 最小限の再現で検証を停止し、証拠からトークン、Cookie、個人情報をマスクする
2. 公開 Issue や通常ログには書かず、アクセス制限された保管先へ証拠を保存する
3. 開始前に定めたプロジェクト責任者と運用責任者へ直ちに非公開で連絡する
4. 責任者が公開停止、シークレット失効、ログ保全などの封じ込めを判断する
5. 修正環境で再検証するまで、攻撃範囲や対象データを広げない

## 6. 実施手順

### Phase 1: 攻撃面とデータフローの棚卸し

#### 実施内容

- App Router のページ、Route Handlers、Server Actions を機械的に列挙する
- 各入口について、HTTP メソッド、認証主体、入力、出力、DB 操作を記録する
- ブラウザーから Server Component、Repository、Supabase までのデータフローを追う
- OpenAI、Langfuse、Supabase Storage など外部通信先を列挙する
- 個人情報、会話、フィードバック、利用量、秘密情報をデータ分類する
- 公開仕様、実装、デプロイ済みエンドポイントの差分を確認する

#### 成果物

- エンドポイント台帳
- 認証主体と操作権限のマトリクス
- 信頼境界を示した簡易データフロー図
- 重点テストケース一覧

### Phase 2: 静的解析とサプライチェーン確認

#### 実施内容

- `pnpm audit` と OSV Scanner で直接・推移依存の既知脆弱性を確認する
- Semgrep の TypeScript、React、Next.js 向けルールで危険なパターンを確認する
- Gitleaks で現在のツリーと Git 履歴の秘密情報を検査する
- `.env*`、ビルド成果物、Source Map、ログへの秘密情報混入を確認する
- GitHub Actions の `permissions`、Action の commit SHA 固定、PR 由来入力を確認する
- ロックファイルの整合性と、不要・未使用・保守停止依存を確認する

採用ツールは `pnpm audit`、OSV Scanner、Semgrep、Gitleaks を基本とする。
実施記録にはバージョン、ルールセット、コマンド、除外、出力ファイルを残す。
利用できないツールを代替する場合は、変更理由と失われる検査範囲を監査開始前に
記録する。SAST 結果は可能な限り SARIF、その他は JSON またはテキストで保存する。

#### 判定上の注意

ツールの出力だけでは脆弱性と判定しない。利用バージョン、到達可能性、実行環境を
確認し、成立しないものは根拠を添えて誤検知または影響なしと分類する。

### Phase 3: 認証・認可レビュー

#### 実施内容

- Supabase セッションの生成、更新、失効、Cookie 更新を追跡する
- Basic 認証の設定有無、HTML と API への適用範囲、失敗時レスポンスを確認する
- 全 Route Handler と Server Action で認証・認可が処理の前に行われるか確認する
- URL、本文、Cookie から渡される ID に所有者・公開状態の検査があるか確認する
- 匿名セッション A の ID を匿名セッション B が参照・更新できないことを確認する
- 非公開レポート、未公開分析、会話、フィードバックの取得経路を確認する
- 認可失敗時にデータ有無を推測できる差がないか確認する
- キャッシュがユーザー固有レスポンスを別ユーザーへ返さないか確認する

### Phase 4: 入力・出力・ブラウザーセキュリティレビュー

#### 入力検証

- JSON schema、Zod、型だけに依存しない実行時検証
- 必須値、列挙値、UUID、文字数、配列件数、ネスト深度、総 payload サイズ
- 不正な `Content-Type`、壊れた JSON、重複キー、予期しないプロパティ
- 検索・並び替え・ページング値の上限と異常値
- SQL、ログ、ヘッダー、テンプレートへのインジェクション
- 外部 URL を扱う箇所の protocol、host、IP、redirect 検証

#### 出力処理

- Markdown から React 要素へ変換する際の sanitize schema
- AI 応答を表示する全コンポーネントでの HTML・URL 処理
- `dangerouslySetInnerHTML`、iframe、Web preview、リンク遷移
- エラーレスポンス、スタックトレース、内部 ID、SQL 情報の露出
- JSON、CSV、OGP など形式別の `Content-Type` とダウンロード動作

#### ブラウザー制御

- Content Security Policy と `frame-ancestors`
- Strict Transport Security
- `X-Content-Type-Options: nosniff`
- Referrer Policy
- Permissions Policy
- Cookie の `Secure`、`HttpOnly`、`SameSite`、Path、Domain、有効期限
- CORS の許可 origin、資格情報、preflight
- CSRF、Origin／Referer 検証、クリックジャッキング
- ページ、API、ユーザー固有レスポンスの Cache-Control
- Next.js の識別ヘッダーや Source Map による不要な情報露出

### Phase 5: API と業務フローの濫用確認

#### 共通 API

- 許可していない HTTP メソッドが拒否されること
- 認証なし、改変 Cookie、期限切れトークンでの動作
- Object ID とプロパティの改変による BOLA／BOPLA
- 管理相当機能への Broken Function Level Authorization
- API 応答に不要な内部フィールドが含まれないこと
- ページング回避や大量取得によるリソース消費
- 同一操作の並行実行、二重送信、競合状態
- エラー条件による情報推測とログ汚染

#### `POST /api/revalidate`

- シークレット未設定時に fail closed となること
- Bearer 値の漏えい経路、保管、ローテーション手順
- 不正タグ、重複タグ、巨大配列、壊れた JSON の処理
- 総当たりや連打に対する制限
- キャッシュ全無効化がサービス妨害に使われないこと

#### オープンデータ API

- 公開対象と非公開対象の境界
- 下書き、内部 ID、会話、個人情報など不要フィールドの露出
- フィルター、ソート、ページングの上限
- 大量取得とスクレイピングが可用性へ与える影響
- CORS、キャッシュ、利用規約と実装の一致

### Phase 6: AI・チャット固有の確認

- クライアントから受け取るメッセージの件数、長さ、role、metadata の検証
- system／developer 指示を上書きするプロンプトインジェクション
- DB や外部コンテンツに保存された間接プロンプトインジェクション
- モデル出力に含まれる HTML、Markdown、URL、偽の内部リンク
- 内部プロンプト、API キー、個人情報、非公開データの抽出試行
- 入力 token、出力 token、実行時間、同時実行数の上限
- 日次・月次・ユーザー単位コスト上限の競合状態と回避可能性
- 別セッションの会話や利用量へのアクセス
- Langfuse／テレメトリーへ送信するデータとマスキング
- OpenAI 障害、timeout、stream 中断時の課金・DB 状態・再試行
- AI 応答を命令としてサーバー側で自動実行していないこと

### Phase 7: Supabase・PostgreSQL 権限監査

#### スキーマと権限

- `public` など exposed schema の全テーブルで RLS が有効か確認する
- `public`、`anon`、`authenticated` の table／sequence／function GRANT を列挙する
- ポリシーを置かない本プロジェクト方針どおり、デフォルト全拒否になっているか確認する
- 新規オブジェクト向け default privileges が安全か確認する
- Storage bucket と object policy の公開範囲を確認する
- Realtime publication に機密テーブルが含まれないか確認する

#### RPC と管理クライアント

- 全 RPC の owner、実行ロール、引数、戻り値を確認する
- `SECURITY DEFINER` に固定された安全な `search_path` があるか確認する
- 動的 SQL と識別子組み立てを確認する
- `createAdminClient()` の利用箇所が server-only な経路に限定されるか確認する
- 管理クライアント呼び出し前にアプリ層の認可が完了するか確認する
- `SUPABASE_SECRET_KEY` が Client Component やブラウザーバンドルへ入らないことを確認する

#### DB テスト

- `anon`、`authenticated`、`service_role` ごとの allow／deny を検証する
- 別ユーザー ID、存在しない ID、公開／非公開状態を組み合わせる
- RPC 変更箇所は `tests/supabase/db-function/` の統合テスト対象とする
- 全テーブルスキャンや無制限集計による DoS リスクを実行計画で確認する

### Phase 8: 動的セキュリティテスト

1. Playwright で正常系のベースラインと対象 HTTP 通信を記録する
2. `curl` 等で認証、メソッド、Content-Type、境界値を個別検証する
3. OWASP ZAP のパッシブスキャンを実行する
4. allowlist したプレビュー URL に限定してアクティブスキャンを実行する
5. 匿名セッション A／B によるオブジェクト認可テストを実行する
6. 小規模な並行リクエストでレート制限と競合状態を確認する
7. HTTP ヘッダー、Cookie、TLS、CORS、キャッシュを実レスポンスで確認する
8. 検出事項を手動で最小再現し、スキャナーの誤検知を除外する

負荷を増やす場合は、各段階の送信数、同時実行数、停止条件を先に記録する。
閾値を確認するために、本当にサービスを停止させる必要はない。

## 7. 重点確認候補

事前のソース確認から、初回チェックでは次を優先する。以下は脆弱性の認定ではなく、
設計上の権限またはコスト影響が大きいため優先度を上げた項目である。

1. `createAdminClient()` を使う公開読み取り・更新処理の呼び出し元認可
2. チャット／インタビュー API の入力上限、レート制限、コスト上限の競合耐性
3. Basic 認証が HTML ナビゲーションだけに適用され、API や fetch を通す設計の妥当性
4. Web 全体の CSP、HSTS、クリックジャッキング対策など HTTP ヘッダー
5. Markdown、AI 応答、Web preview、内部リンクの XSS と URL 検証
6. `POST /api/revalidate` の秘密情報管理と濫用耐性
7. `SECURITY DEFINER` RPC、function GRANT、default privileges
8. 未公開レポート、会話、フィードバックのオブジェクト単位認可

## 8. 検出事項の評価方法

### 8.1 重大度

| 重大度 | 目安 | 対応方針 |
| :-- | :-- | :-- |
| Critical | 認証不要の機密情報大量取得、管理権限奪取、秘密鍵露出など | 公開・展開を停止し、直ちに封じ込める |
| High | 他ユーザー情報へのアクセス、任意データ更新、永続 XSS など | リリース前に修正する |
| Medium | 条件付き情報漏えい、CSRF、レート制限不足など | 期限と担当を決めて修正する |
| Low | 防御層不足、限定的な情報露出、設定改善など | 通常の改善計画へ入れる |
| Informational | 直接の悪用は確認できないが改善余地がある | リスク受容または継続改善を判断する |

重大度は CVSS の数値だけで決めず、必要権限、再現性、対象データ、影響範囲、
AI 利用料金、可用性、既存の緩和策を合わせて判断する。

### 8.2 1 件ごとの記録項目

- ID、タイトル、重大度、確度
- 対象ファイル、行、URL、HTTP メソッド
- 前提条件と最小再現手順
- 期待結果と実際の結果
- リクエスト／レスポンス、ログなどの証拠（秘密情報はマスク）
- 技術的影響と利用者・運用への影響
- OWASP ASVS／API Top 10 の対応項目
- 推奨修正と代替案
- 回帰テスト案
- 対応状況、担当、期限、リスク受容理由

## 9. 修正時の方針

- Critical／High は原則として他の改善より先に修正する
- 認可は UI ではなく Route Handler、Server Action、サービス層で強制する
- 管理 Supabase クライアントを使う処理は、認可と公開条件をテストで固定する
- 純粋な入力判定や変換は `utils/` に切り出し、同階層に単体テストを置く
- DB function の変更には統合テストを追加する
- 脆弱な入力の再現ケースを、安全な回帰テストとして残す
- 修正確認はローカルまたは別環境で行い、本番で試行錯誤しない
- 一つの PR に無関係な修正を混在させない

## 10. 継続的チェックへの移行

初回監査後、費用と誤検知を見ながら次を CI または定期実行へ移す。

- PR ごと: lint、typecheck、test、build、SAST、秘密情報検査
- 依存更新時: OSV／package audit、ロックファイル確認
- DB migration 変更時: RLS、GRANT、RPC の統合テスト
- デプロイ後: セキュリティヘッダーと公開エンドポイントの smoke test
- 定期: ZAP パッシブスキャン、Supabase Security Advisor、依存関係再評価
- インシデントまたは大規模機能追加時: 脅威モデルと本計画の見直し

CI へ追加する検査は、最初から全警告を失敗扱いにしない。初回結果を基準化し、
新規 Critical／High、秘密情報、認可テスト失敗など、確度と影響が高いものから
段階的にゲート化する。

## 11. 成果物

チェック完了時に以下を提出する。

1. 対象と実施環境を記録した監査サマリー
2. エンドポイント台帳と認証・認可マトリクス
3. ASVS Level 2 の要件 ID、判定、証拠、`N/A` 理由を記録した対応表
4. 重大度順の検出事項一覧
5. 各検出事項の再現証拠、影響、修正案、回帰テスト案
6. 実行したコマンド、ツール、バージョン、設定、対象 commit SHA
7. 誤検知、未検証、対象外、残存リスクの一覧
8. 修正 PR の分割案と優先順位
9. CI／運用へ追加する継続チェック案

## 12. 完了条件

以下をすべて満たした時点で初回チェックを完了とする。

- 対象ページ、API、Server Actions、RPC の台帳が作成されている
- ASVS Level 2 の適用可能な要件が ID 単位で判定され、証拠が紐付いている
- `N/A` と `未確認`が明示され、理由または残作業が記録されている
- 各入口について認証主体、入力、データ操作、出力が確認されている
- 匿名セッション A／B を使ったオブジェクト認可試験が完了している
- 依存関係、秘密情報、SAST、HTTP 設定、Supabase 権限が確認されている
- AI 機能の入力上限、コスト制御、出力表示、データ露出が確認されている
- 自動検出事項が手動確認され、誤検知と未確認が区別されている
- Critical／High の有無と、公開継続可否の判断が明記されている
- 全検出事項に修正案またはリスク受容の判断材料がある
- 本番環境に破壊的または高負荷なリクエストを送っていない
- 本番固有の HTTP／エッジ設定がパッシブ確認済みか、`未確認`として分離されている

## 13. 初回見積もりと再見積もり

| 日 | 主な作業 |
| :-- | :-- |
| 1 日目 | 環境確認、攻撃面・データフロー棚卸し、依存・秘密情報・SAST |
| 2 日目 | 認証認可、API、Server Actions、AI、Supabase の手動レビュー |
| 3 日目 | 優先対象の動的テスト、再現確認、暫定報告と残作業見積もり |

3 日は初回トリアージの見積もりであり、全件監査の固定納期ではない。Phase 1 の台帳で
ページ、API、Server Actions、RPC、ASVS 適用要件の件数を確定した後、Phase ごとの
工数と担当を再見積もりする。延長する場合は、完了済み、未確認、対象外と理由を
暫定報告に明示する。時間切れを理由に未確認項目を「問題なし」と扱わない。
