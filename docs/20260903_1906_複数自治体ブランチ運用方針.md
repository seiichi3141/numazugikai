# 複数自治体ブランチ運用方針

## 目的

`seiichi3141/numazugikai` が `team-mirai/mirai-gikai` の GitHub fork であることを
保ちながら、沼津市・静岡県と今後追加する自治体のコード、データ、公開環境を
混同せずに管理する。アプリケーションは単一の共通 trunk で発展させ、
自治体 lifecycle branch の差分を外部環境の統合とリリースに限定する。

## 基本原則

- `develop` を共通 trunk とする。共通機能だけでなく、各自治体の
  profile、adapter、ブランド、出典、データ取得実装も `develop` で管理する。
- `sites/<site>/develop` と `sites/<site>/main` は、その自治体専用環境の
  統合確認とリリースのための薄い lifecycle branch とする。
- 共通変更は `develop` から各 `sites/<site>/develop` へのみ反映する。
  reverse merge と site branch 間の merge は行わない。
- DB schema と生成型を含むアプリケーションの正本は常に `develop` に置く。
- 移行期間中の `develop` / `main` は、それぞれ沼津市の staging /
  production デプロイを兼ねる。既存の沼津市用デプロイ条件と
  既定の沼津市 profile の挙動は変えない。

### 既存の静岡県 Phase 0 branch の移行

`sites/shizuoka-pref/develop` には、独立環境を安全に準備するための
Phase 0 の root 設定と fail-closed ガードが一時的に残っている。今後の
promotion では、対応する差分を trunk の profile / adapter と自治体別環境の
仕組みに置き換える。競合解消でガードを単に削除せず、trunk 側の同等以上の
保護とテストが確認できてから旧実装を外す。同等の保護がまだなければ、
先に `develop` 宛て PR で追加する。最終的な target tree の `develop` との差分は、
自治体専用の外部環境設定だけに縮小する。

## ブランチ構成

| ブランチ | 役割 |
| --- | --- |
| `develop` | 共通 trunk。移行期間中は沼津市 staging も兼ねる |
| `main` | 沼津市 production（移行期間中の既存名） |
| `<type>/<topic>` | 共通機能や自治体 profile / adapter を実装する短期 branch |
| `hotfix/<topic>` | 既存の沼津市 production だけの緊急修正 |
| `sites/<site>/develop` | `develop` を自治体専用環境で確認する統合先 |
| `sites/<site>/main` | 自治体版のリリース先。公開環境の準備完了時に作る |
| `sites/<site>/fix/<topic>` | 自治体 staging 環境だけの修正 |
| `sites/<site>/hotfix/<topic>` | 自治体 production 環境だけの緊急修正 |

`<site>` は小文字 ASCII とハイフンだけを使い、同名の市と県を区別できるよう
行政区分を末尾に付ける。現在の識別子は次のとおり。

| 対象 | `<site>` |
| --- | --- |
| 沼津市 | `numazu-city` |
| 静岡県 | `shizuoka-pref` |

`sites/<site>` というブランチ自体は作らない。Git の ref 名は、同名の branch と
その配下の branch を同時に持てないためである。
通常の短期 branch の `<type>` は `feat`、`fix`、`chore`、`docs`、
`refactor`、`test` を推奨し、`develop` から分岐する。Linear が発行する branch 名も
共有 `develop` 宛てで使用できる。site-scoped branch は自治体専用の外部環境修正に
限り、`fix` と `hotfix` 以外の種別、lifecycle branch と衝突する名前、異なる
自治体への PR は Branch Policy CI で拒否する。

## 開発、promotion、リリース

1. 再利用可能な機能、自治体 profile / adapter、データ取得、DB schema は
   `develop` から短期 branch を作り、`develop` 宛ての PR で実装する。
2. 共通 CI と沼津市の後方互換性を確認して `develop` へ取り込む。
3. `develop` から `sites/<site>/develop` へ promotion PR を作り、
   自治体専用環境で統合確認する。競合は promotion PR 上で解消し、
   site branch の修正を `develop` へ reverse merge しない。`develop` の祖先関係を
   保つため merge commit で取り込み、squash / rebase merge は使わない。
4. 沼津市のリリースは従来どおり `develop` から `main` への PR で行う。
   その他の自治体は `sites/<site>/develop` から `sites/<site>/main` への
   PR を merge commit で取り込んでリリースする。

- `sites/<site>/main` は DB、Vercel、worker、ドメイン、GitHub Environment が
  その自治体専用に分離されるまで作成しない。
- `develop` / `main` の改名は、沼津市の staging / production 設定を移行する
  別作業として行う。それまではこの2ブランチを削除・改名しない。
- `sites/<site>/fix/<topic>` は対応する `sites/<site>/develop` から分岐し、
  staging 環境固有の接続・デプロイ設定だけを同 branch へ戻す。
- `sites/<site>/hotfix/<topic>` は対応する `sites/<site>/main` から分岐し、
  production 環境固有の緊急修正だけを同 branch へ戻す。
- 既存の沼津市 production hotfix は `main` から `hotfix/<topic>` を分岐し、
  `main` へ戻す。アプリケーションにも必要な修正は `develop` 上でも実装し、
  通常の `develop` から `main` へのリリース経路へ収束させる。
- site-scoped の fix / hotfix にアプリケーションコード、profile / adapter、
  migration、生成型を含めない。共通化すべき変更は `develop` 上の別 PR で
  実装し、次の promotion で反映する。
- 異なる site branch 間の merge と、site branch から `develop` への reverse
  merge を禁止する。
- `main` と site lifecycle branch 宛ての PR は、`seiichi3141/numazugikai` 内の
  branch だけを head にできる。外部 fork からの通常 contribution は、短期 branch
  から共有 `develop` 宛てに作成する。同名 branch による promotion の偽装は
  Branch Policy CI で拒否する。
- 日常的な cherry-pick は取り込み漏れと再競合を生むため禁止する。
  障害対応など切り離された緊急変更に限り、PR に理由、反映元と反映先、
  trunk との整合方法を記録して `git cherry-pick -x` を使用できる。
- 独立リポジトリで作成済みの履歴を初回移植する場合は、移植 commit を
  `git merge --no-ff` で feature branch に結合し、PR に `preserve-history` label を
  付けて merge commit で取り込む。squash/rebase で元の commit SHA を失わない。
  label が未作成なら、移植前に次を一度だけ実行する。

  ```bash
  gh label create preserve-history --repo seiichi3141/numazugikai \
    --color 5319E7 --description "Merge commit required to preserve imported history"
  ```

## 外部サービスの隔離

- 現在の `develop` / `main` 向けデプロイはそれぞれ沼津市 staging /
  production 用として維持し、この運用変更で条件や secrets を変更しない。
- 共通 CI（lint、typecheck、build、test、integration）は
  `sites/*/develop` と `sites/*/main` でも実行する。
- Branch Policy CI は default branch の信頼済み validator を実行し、
  `develop` から `main` への既存の沼津市 release、`develop` から site develop
  への promotion、site develop から同じ site main への release、環境 fix /
  hotfix から対応する lifecycle branch への PR だけを許可する。reverse merge、
  site 間 merge、feature から main への直接 PR は拒否する。PR 側の validator は
  実行しない。
- 現在の Vercel Git 連携は沼津市専用であり、`sites/*` のビルドを拒否する。
- 現在の Supabase Preview workflow は `develop` / `main` 宛て PR だけを扱い、
  `sites/*` 宛て PR では job 自体を実行しない。
- deploy、worker、OGP 更新を他自治体で有効にする場合は、branch 条件だけでなく
  自治体専用の GitHub Environment と secrets を用意する。沼津市用 secrets を
  流用しない。
- `.env`、Supabase project ID、ローカルポートは自治体ごとに分離する。

## DB migration と生成型

- `supabase/migrations/` は `develop` で単一の時系列として管理する。
- `packages/supabase/types/supabase.types.ts` などの生成型は、対応する migration
  と同じ `develop` 宛て PR で更新する。
- 自治体ごとに Supabase project とデータは分離するが、schema 履歴は
  分岐させない。各 project に promotion 済み commit の同じ migration を適用する。
- 特定自治体で必要になった schema 拡張も、既存自治体と後方互換の
  共通 migration として設計する。site branch だけの migration は作成しない。

## 新しい自治体を追加する手順

1. 衝突しない `<site>` を決める。
2. `develop` から短期 branch を作り、自治体 profile / adapter、名称、
   出典、データ取得、seed の差分を共通 trunk に追加する。profile は自治体ごとの
   ファイルへ置き、共有 registry は登録だけに限定する。
3. 既存自治体のデフォルト挙動を保ったまま、新しい profile / adapter の
   単体・統合テストを追加して `develop` へマージする。
4. 検証済みの `develop` commit から `sites/<site>/develop` を作成し、
   branch protection を設定する。既存 branch なら promotion PR で更新する。
5. 自治体専用の DB、Vercel、worker、secrets、ドメインを分離し、
   `sites/<site>/develop` で統合確認する。準備が揃うまで deploy は no-op にする。
6. 公開直前に `sites/<site>/main` を作り、同等の branch protection を設定する。

branch protection の required checks には `lint-and-typecheck`、`integration-test`、
`branch-policy` を含める。bootstrap PR のマージ後は既存の `develop` / `main` にも
`branch-policy` を追加し、site lifecycle branch は作成直後に同じ設定を適用する。

## 見直し条件

自治体を追加するたびに、新規要件を既存 profile / adapter 契約で表現できるか
確認する。site branch へのアプリケーション差分、migration の分岐、または
繰り返しの緊急 cherry-pick が必要になった場合は、共通 profile / adapter 境界か
自治体別ビルド・デプロイ設計を見直し、trunk へ収束させる。
